# 分布式存储

## 定义

分布式存储是将数据分散存储在多个独立的设备上，通过网络互联，对外提供统一存储服务的系统。它利用多台存储服务器分担存储负荷，提高系统的可靠性、可用性和扩展性。

核心目标：
- **可扩展性**：通过增加节点线性扩展存储容量和性能
- **高可用性**：数据多副本或纠删码，节点故障不丢失数据
- **高性能**：并行读写，聚合带宽和IOPS
- **数据一致性**：保证多副本数据一致，或提供明确的一致性模型

## 核心概念

### 1. 存储类型

**块存储（Block Storage）**
- 提供裸磁盘或分区，操作系统需格式化文件系统
- 特点：低延迟、高IOPS、支持随机读写
- 典型协议：iSCSI、Fibre Channel
- 应用场景：数据库、虚拟机磁盘

**文件存储（File Storage）**
- 提供文件系统接口，支持目录树结构
- 特点：POSIX兼容、支持文件锁、目录操作
- 典型协议：NFS、CIFS/SMB、POSIX
- 应用场景：共享文件系统、NAS

**对象存储（Object Storage）**
- 提供REST API，将数据作为对象存储
- 特点：无限扩展、元数据丰富、无目录树
- 典型协议：S3、Swift、OSS
- 应用场景：图片视频、备份归档、静态网站

**表格存储（Table Storage）**
- 提供NoSQL表格接口，按行键访问
- 特点：海量数据、水平扩展、最终一致性
- 典型系统：HBase、BigTable、DynamoDB
- 应用场景：时序数据、日志存储、用户画像

### 2. 数据分布策略

**哈希分布（Hash Distribution）**
- 对key计算哈希值，按哈希值分配到不同节点
- 优点：数据分布均匀、查找效率高
- 缺点：扩容需大量数据迁移（一致性哈希解决部分问题）

**范围分布（Range Distribution）**
- 按key范围分配到不同节点（如字典序）
- 优点：支持范围查询、扩容迁移数据少
- 缺点：可能数据倾斜、需元数据记录范围映射

**一致性哈希（Consistent Hashing）**
- 将哈希空间组织为虚拟环，节点映射到环上
- 优点：扩容时仅影响相邻节点、数据迁移量少
- 缺点：可能数据倾斜、需虚拟节点解决

**CRUSH算法（Controlled Replication Under Scalable Hashing）**
- Ceph专用，基于层次化设备映射和伪随机算法
- 优点：无需中心元数据、支持权重、故障域感知
- 缺点：算法复杂、调试困难

### 3. 数据冗余策略

**副本复制（Replication）**
- 数据复制到多个节点，通常3副本
- 优点：读性能好、故障恢复快
- 缺点：存储成本高（3倍）

**纠删码（Erasure Code, EC）**
- 将数据分片，计算校验片，允许部分片丢失恢复
- 典型配置：RS(6,3) —— 6个数据片+3个校验片，允许3个片丢失
- 优点：存储成本低（1.5倍 vs. 副本的3倍）
- 缺点：写放大、故障恢复慢、计算开销

**混合策略**
- 热数据用副本：低延迟、高吞吐
- 冷数据用纠删码：降低成本
- 典型实现：Ceph、MinIO

### 4. 一致性模型

**强一致性（Strong Consistency）**
- 读操作总能读到最新写入
- 实现：同步复制、Paxos/Raft共识
- 优点：数据准确
- 缺点：延迟高、可用性低

**最终一致性（Eventual Consistency）**
- 写入后，副本最终会一致，但中间可能读到旧数据
- 实现：异步复制、版本向量、冲突解决
- 优点：低延迟、高可用
- 缺点：可能读到脏数据

**因果一致性（Causal Consistency）**
- 有因果关系的操作保证顺序，无因果关系的并发操作允许不一致
- 实现：向量时钟、版本向量
- 优点：平衡一致性和性能
- 缺点：实现复杂

**读写一致性（Read-your-writes Consistency）**
- 保证客户端能读到自己最新写入
- 实现：会话粘滞、版本号
- 优点：用户体验好
- 缺点：仅保证自身写入可见

## 详细内容

### 1. 分布式文件系统

**HDFS（Hadoop Distributed File System）**
- 架构：NameNode（主节点，管理元数据）+ DataNode（从节点，存储数据块）
- 存储策略：大文件切分为128MB/256MB块，每个块3副本
- 读写流程：
  - 写文件 → 客户端向NameNode申请，获得DataNode列表，建立流水线写入
  - 读文件 → 客户端向NameNode查询块位置，直接从DataNode读取
- 优点：高吞吐、适合大文件、与Hadoop生态集成
- 缺点：NameNode单点、不适合小文件、不支持随机写

**CephFS**
- 架构：MON（监视器，管理集群映射）+ OSD（对象存储设备）+ MDS（元数据服务器）
- 存储策略：数据存为对象，MDS管理文件元数据
- 优点：POSIX兼容、支持快照、动态扩容
- 缺点：MDS可能成为瓶颈、调优复杂

**GlusterFS**
- 架构：无元数据服务器，每个节点平等
- 存储策略：弹性哈希算法定位文件，无需元数据查询
- 优点：无单点、易扩展、适合大文件顺序读写
- 缺点：小文件性能差、元数据操作慢

### 2. 分布式对象存储

**MinIO**
- 架构：对称架构，无元数据服务，所有节点对等
- 存储策略：纠删码（EC）保护数据，支持副本模式
- 优点：高性能（单集群可达TB/s）、S3兼容、易部署
- 缺点：无多租户、无分级存储

**Ceph RADOSGW**
- 架构：基于Ceph RADOS，提供S3/Swift兼容接口
- 存储策略：数据存为RADOS对象，网关转换协议
- 优点：与Ceph统一存储、支持多租户、动态扩容
- 缺点：性能不如专用对象存储、配置复杂

**AWS S3（参考架构）**
- 架构：存储网关 + 存储节点 + 元数据服务
- 存储策略：数据多AZ存储，纠删码保护
- 优点：无限扩展、11个9的持久性、丰富生态
- 缺点：私有云需自研或采用兼容方案

### 3. 分布式块存储

**Ceph RBD（RADOS Block Device）**
- 架构：将块设备映射到RADOS对象，支持快照、克隆
- 存储策略：数据条带化到多个对象，多副本或纠删码
- 优点：高性能（支持客户端缓存）、与OpenStack/K8s集成
- 缺点：依赖Ceph集群、故障影响面广

**iSCSI分布式实现**
- 架构：iSCSI目标端（Target）运行在存储节点，发起端（Initiator）挂载
- 存储策略：后端存储可以是本地文件系统或分布式存储
- 优点：通用协议、操作系统原生支持
- 缺点：网络开销大、无高可用（需配合HA）

### 4. 分布式表格存储

**HBase**
- 架构：HMaster（主节点，管理Region）+ RegionServer（从节点，服务Region）
- 存储策略：表按行键范围切分为Region，每个Region多个列族
- 读写流程：
  - 写流程 → 先写WAL（预写日志），再写MemStore（内存），刷写为HFile
  - 读流程 → 先查MemStore，再查HFile，支持BlockCache缓存
- 优点：海量数据、水平扩展、强一致性（单行）
- 缺点：复杂查询弱、依赖ZooKeeper和HDFS

**BigTable（Google）**
- 架构：Master（主节点）+ TabletServer（从节点）+ GFS（底层存储）
- 存储策略：表按行键范围切分为Tablet，SSTable格式存储
- 优点：Google内部验证、支持PB级数据
- 缺点：闭源、需自研或采用HBase

**Cassandra**
- 架构：无主节点，所有节点对等（P2P）
- 存储策略：数据按哈希分布，多副本（可配置副本策略）
- 优点：无单点、高可用、写入性能高
- 缺点：一致性较弱、复杂查询弱

## 示例/应用场景

### 示例1：搭建MinIO对象存储集群
**场景**：公司需要搭建内部对象存储，存储图片、视频等静态资源

**部署方案**：
1. 服务器规划：4台服务器，每台3块硬盘
2. 部署模式：分布式模式，纠删码RS(6,2)（6数据+2校验）
3. 安装：每台服务器运行MinIO服务，组成单一集群
4. 配置：域名解析、负载均衡（Nginx）、TLS证书
5. 使用：应用程序通过S3 API读写对象

**关键配置**：
- 存储类：STANDARD（副本） vs. REDUCED_REDUNDANCY（纠删码）
- 生命周期：热数据存标准存储，冷数据转冷归档存储
- 访问控制：IAM策略、桶策略、预签名URL

### 示例2：HDFS存储日志文件
**场景**：公司每天产生10TB日志，需存储并供后续分析

**方案设计**：
1. 集群规划：NameNode高可用（主备），10台DataNode，每台12块8TB硬盘
2. 文件策略：日志按小时切分文件，每个文件128MB~256MB
3. 写入：日志收集系统（Flume）写入HDFS，每隔小时创建新文件
4. 读取：分析系统（Spark）直接读取HDFS文件，并行处理
5. 清理：过期日志（超过90天）删除或归档到冷存储

**关键优化**：
- 小文件合并：将多个小日志文件合并为大文件（HAR、CombineFileInputFormat）
- 副本策略：热数据3副本，冷数据2副本或纠删码
- 存储策略：不同节点存不同副本，保证机架感知

### 示例3：Ceph提供统一存储
**场景**：公司需要统一存储方案，同时支持块存储、文件存储、对象存储

**方案设计**：
1. 集群规划：3台MON节点（奇数，保证共识），10台OSD节点（每台12块硬盘）
2. 存储池：创建不同存储池，分别用于RBD、CephFS、RADOSGW
3. 配置：副本数3，CRUSH规则保证副本在不同机架
4. 客户端：
   - 块存储：虚拟机通过librbd挂载RBD镜像
   - 文件存储：通过CephFS内核客户端或FUSE挂载
   - 对象存储：通过S3 API访问
5. 监控：使用Prometheus + Grafana监控集群状态

**关键考量**：
- 性能调优：OSD缓存、日志分离、网络配置
- 故障恢复：监控OSD状态，及时替换故障盘
- 扩容：增加OSD节点，CRUSH算法自动重平衡

## 【对应领域考点】

1. **CAP定理在分布式存储中的体现**
   - CP系统：HBase、MongoDB（强一致性、分区容错性）
   - AP系统：Cassandra、DynamoDB（高可用、分区容错性，最终一致性）
   - CA系统：传统关系型数据库（单机或小型集群）

2. **副本 vs. 纠删码**
   - 副本：存储成本高（3倍），但读写性能好，适合热数据
   - 纠删码：存储成本低（1.5倍），但写放大、恢复慢，适合冷数据
   - 混合：热数据用副本，冷数据用纠删码

3. **数据分布策略选择**
   - 哈希分布：适合随机读写，但扩容需迁移数据
   - 范围分布：适合范围查询，但可能数据倾斜
   - 一致性哈希：适合动态扩容，但需虚拟节点解决倾斜
   - CRUSH：适合大规模集群，无需中心元数据

4. **分布式存储一致性级别**
   - 强一致性：读总能读到最新写入，但延迟高
   - 最终一致性：可能读到旧数据，但低延迟、高可用
   - 根据业务选择：金融交易用强一致，日志收集用最终一致

5. **分布式存储高可用架构**
   - 主备：主节点故障，备节点接管（HDFS NameNode）
   - 多活：多个节点同时服务，无单点（Ceph MON、MinIO）
   - 无主：所有节点对等，无单点（Cassandra、DynamoDB）

## 最佳实践

1. **合理选择存储类型**
   - 块存储：数据库、虚拟机磁盘（低延迟、高IOPS）
   - 文件存储：共享文件系统、NAS（POSIX兼容、目录结构）
   - 对象存储：图片视频、备份归档（无限扩展、S3 API）
   - 表格存储：时序数据、日志、用户画像（海量数据、水平扩展）

2. **容量规划**
   - 副本策略：热数据3副本，冷数据2副本或纠删码
   - 存储利用率：副本策略利用率33%，纠删码可达80%
   - 扩容计划：提前规划，避免紧急扩容影响业务

3. **性能优化**
   - 数据本地性：计算任务调度到数据所在节点
   - 缓存策略：客户端缓存、块缓存、元数据缓存
   - 并行读写：多线程、多连接并发读写
   - 小文件优化：合并小文件、使用元数据索引

4. **高可用设计**
   - 多副本：关键数据至少3副本，跨机架/可用区
   - 故障检测：心跳检测、自动故障转移
   - 备份恢复：定期备份元数据，演练恢复流程
   - 监控告警：监控容量、性能、故障，及时告警

5. **数据安全**
   - 加密：传输加密（TLS）、存储加密（静态加密）
   - 访问控制：认证（IAM）、授权（ACL、桶策略）、审计
   - 防数据丢失：快照、版本控制、跨地域复制

## 【常见错误】

1. **错误：小文件存储到HDFS**
   - 现象：HDFS存储大量小文件，NameNode内存耗尽
   - 原因：HDFS每个文件对应一个元数据对象，小文件过多耗尽NameNode内存
   - 解决：合并小文件（HAR、CombineFileInputFormat）、使用对象存储

2. **错误：副本数设置不合理**
   - 现象：存储成本高，或数据可靠性低
   - 原因：副本数过多（成本浪费），副本数过少（可靠性低）
   - 解决：热数据3副本，冷数据2副本或纠删码；根据业务重要性设置

3. **错误：数据倾斜**
   - 现象：某些节点存储或访问远高于其他节点
   - 原因：哈希函数不均匀、热点key、范围分布不当
   - 解决：优化哈希函数、使用一致性哈希、预分区分片

4. **错误：网络成为瓶颈**
   - 现象：存储集群网络拥塞，性能下降
   - 原因：存储节点之间大量数据复制、恢复流量占用带宽
   - 解决：独立存储网络、限制恢复带宽、使用RDMA网络

5. **错误：一致性级别设置不当**
   - 现象：数据不一致，或延迟高
   - 原因：强一致性设置导致延迟高，最终一致性导致脏读
   - 解决：根据业务选择一致性级别；关键数据用强一致，非关键用最终一致

## 总结

分布式存储是分布式系统的核心组件，核心在于：
1. **存储类型**：块存储、文件存储、对象存储、表格存储，各有适用场景
2. **数据分布**：哈希、范围、一致性哈希、CRUSH，需平衡均匀性、可扩展性和查询效率
3. **数据冗余**：副本（高性能、高成本）vs. 纠删码（低成本、恢复慢）
4. **一致性模型**：强一致性、最终一致性、因果一致性，需根据业务权衡
5. **典型系统**：HDFS（文件系统）、Ceph（统一存储）、MinIO（对象存储）、HBase（表格存储）

实际应用中，需根据数据类型、访问模式、性能要求、成本预算选择合适的分布式存储方案。
