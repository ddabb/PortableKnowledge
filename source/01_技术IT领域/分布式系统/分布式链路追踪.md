# 分布式链路追踪

## 定义

分布式链路追踪是一种用于监控和诊断分布式系统性能问题的技术。它通过跟踪一个请求在多个服务之间的完整调用链路，帮助开发者理解请求流程、识别性能瓶颈、定位故障原因。

核心目标：
- **全链路可见**：完整记录请求在所有服务间的调用路径
- **性能分析**：识别慢调用、瓶颈服务
- **故障定位**：快速定位故障服务、故障原因
- **依赖分析**：分析服务间依赖关系、调用频率

## 核心概念

### 1. 追踪模型

**Trace（追踪）**
- 一个完整请求的调用链路
- 包含多个Span，形成树状结构
- 全局唯一Trace ID，贯穿整个调用链

**Span（跨度）**
- 一次服务调用或操作
- 包含：Span ID、父Span ID、操作名、开始时间、结束时间、标签、日志
- 多个Span组成Trace

**Span上下文（Span Context）**
- 跨服务传递的上下文信息
- 包含：Trace ID、Span ID、采样标志、 baggage（附加信息）
- 通过RPC头部传递

### 2. 采样策略

**全采样（Full Sampling）**
- 所有请求都采样
- 优点：数据完整
- 缺点：性能开销大、存储成本高
- 适用：开发测试环境

**固定速率采样（Fixed Rate Sampling）**
- 按固定比例采样（如1%）
- 优点：性能开销小
- 缺点：可能遗漏重要请求
- 适用：生产环境

**动态采样（Dynamic Sampling）**
- 根据请求特征动态调整采样率
- 如：慢请求全采样、错误请求全采样
- 优点：平衡性能和数据完整性
- 缺点：实现复杂

**限流采样（Rate Limiting Sampling）**
- 限制每秒采样数量
- 优点：避免采样过多
- 缺点：可能遗漏重要请求
- 适用：高流量系统

### 3. 数据上报

**Agent上报**
- 应用通过Agent（如Java Agent）上报追踪数据
- 优点：对应用透明、无需修改代码
- 缺点：Agent可能不稳定
- 典型实现：SkyWalking Agent

**SDK上报**
- 应用通过SDK（如OpenTelemetry SDK）上报
- 优点：灵活、支持多语言
- 缺点：需修改代码（侵入式）
- 典型实现：Jaeger SDK、Zipkin SDK

**Sidecar上报**
- 通过Sidecar代理上报（Service Mesh场景）
- 优点：对应用完全透明
- 缺点：依赖Service Mesh
- 典型实现：Istio + Jaeger

### 4. 存储后端

**内存存储**
- 追踪数据存储在内存
- 优点：快
- 缺点：数据量小、重启丢失
- 适用：开发测试

**关系型数据库**
- 追踪数据存储在MySQL、PostgreSQL
- 优点：易查询
- 缺点：性能差、不适合大规模
- 适用：小规模系统

**NoSQL**
- 追踪数据存储在Elasticsearch、Cassandra
- 优点：可扩展、高性能
- 缺点：运维复杂
- 适用：大规模生产环境

**时序数据库**
- 追踪数据存储在Prometheus、InfluxDB
- 优点：适合指标查询
- 缺点：不适合全链路详情查询
- 适用：性能监控

## 详细内容

### 1. Zipkin

**架构**
- Collector：收集追踪数据
- Storage：存储追踪数据（内存、MySQL、Elasticsearch）
- API：查询追踪数据
- UI：展示追踪数据

**核心机制**
- 应用通过HTTP或MQ上报追踪数据
- 支持多种语言（Java、Go、Python等）
- 与Spring Cloud Sleuth集成好

**优点**
- 简单易用
- 社区活跃
- 与Spring生态集成好

**缺点**
- 功能不如SkyWalking丰富
- 性能不如Jaeger

### 2. Jaeger

**架构**
- Client：应用通过SDK上报
- Agent：可选，本地Agent收集数据
- Collector：收集追踪数据
- Query：查询服务
- UI：展示追踪数据
- Storage：存储（Cassandra、Elasticsearch）

**核心机制**
- 基于OpenTracing标准
- 支持高可用、可扩展
- Uber开源，经历大规模验证

**优点**
- 高性能
- 可扩展
- 支持OpenTracing标准

**缺点**
- 配置复杂
- 学习曲线陡

### 3. SkyWalking

**架构**
- Probe：Agent收集数据
- OAP Server：分析、聚合、存储
- Storage：存储（Elasticsearch、MySQL）
- UI：展示监控数据

**核心机制**
- 非侵入式Agent
- 支持服务地图、性能指标、告警
- 国产，文档友好

**优点**
- 功能丰富（链路追踪+监控+告警）
- 非侵入式
- 国产，文档友好

**缺点**
- 性能不如Jaeger
- 社区不如Zipkin、Jaeger活跃

### 4. OpenTelemetry

**架构**
- API：标准API，语言无关
- SDK：实现API，上报数据
- Collector：收集、处理、导出数据
- Exporter：导出到后端（Jaeger、Zipkin、Prometheus）

**核心机制**
- 统一可观测性标准（链路追踪、指标、日志）
- 厂商中立，避免锁定
- 逐步成为行业标准

**优点**
- 标准统一
- 厂商中立
- 支持多后端

**缺点**
- 新标准，生态不如老系统成熟
- 学习曲线陡

## 示例/应用场景

### 示例1：电商下单链路追踪
**场景**：电商系统下单慢，需定位瓶颈

**方案设计**：
1. 接入链路追踪：所有服务接入SkyWalking Agent
2. 生成订单请求：用户下单，生成Trace ID
3. 链路追踪：
   - 网关 → 订单服务 → 库存服务 → 支付服务 → 物流服务
   - 每个服务调用为一个Span
4. 分析：通过SkyWalking UI查看调用链路、每个Span耗时
5. 定位瓶颈：发现支付服务调用慢（耗时2秒）

**关键考量**：
- 采样策略：生产环境用动态采样，慢请求全采样
- 存储：使用Elasticsearch存储追踪数据
- 告警：配置慢调用告警

### 示例2：微服务故障定位
**场景**：微服务系统，用户反馈部分请求失败

**方案设计**：
1. 接入链路追踪：所有服务接入Jaeger
2. 用户反馈：提供Trace ID（从响应头获取）
3. 查询链路：通过Jaeger UI，输入Trace ID查询
4. 分析：发现某个Span报错（如数据库连接失败）
5. 定位：故障服务为订单服务，原因为数据库连接池满

**关键考量**：
- 传递Trace ID：前端从响应头获取Trace ID，用户反馈时提供
- 日志集成：链路追踪与日志集成（如ELK），通过Trace ID查询日志
- 告警：配置错误率告警

### 示例3：服务依赖分析
**场景**：系统重构，需了解服务间依赖关系

**方案设计**：
1. 接入链路追踪：所有服务接入Zipkin
2. 收集数据：运行一段时间，收集足够追踪数据
3. 依赖分析：通过Zipkin UI查看服务依赖图
4. 分析：识别核心服务、强依赖服务
5. 重构：根据依赖关系，制定重构计划

**关键考量**：
- 数据量：依赖分析需足够数据量，才能准确
- 动态依赖：依赖关系可能动态变化，需持续监控
- 重构风险：根据依赖关系，评估重构风险

## 【对应领域考点】

1. **Trace和Span的关系**
   - Trace：完整调用链路，包含多个Span
   - Span：一次服务调用或操作
   - 关系：Trace是Span的集合，Span组成树状结构

2. **采样策略选择**
   - 全采样：开发测试环境
   - 固定速率采样：生产环境（如1%）
   - 动态采样：平衡性能和数据完整性
   - 限流采样：高流量系统

3. **链路追踪系统对比**
   - Zipkin：简单易用，Spring生态集成好
   - Jaeger：高性能，可扩展，支持OpenTracing
   - SkyWalking：功能丰富，非侵入式，国产
   - OpenTelemetry：标准统一，厂商中立

4. **链路追踪与日志集成**
   - 目标：通过Trace ID查询日志
   - 实现：日志中打印Trace ID、Span ID
   - 工具：ELK（Elasticsearch + Logstash + Kibana）

5. **链路追踪与监控集成**
   - 目标：链路追踪数据用于监控告警
   - 实现：导出指标到Prometheus
   - 工具：OpenTelemetry Collector

## 最佳实践

1. **合理选择链路追踪系统**
   - 简单场景：Zipkin
   - 高性能场景：Jaeger
   - 全功能场景：SkyWalking
   - 标准场景：OpenTelemetry

2. **采样策略优化**
   - 生产环境：动态采样（慢请求、错误请求全采样）
   - 开发测试：全采样
   - 高流量：限流采样

3. **性能优化**
   - 异步上报：避免阻塞主流程
   - 批量上报：减少网络开销
   - 采样优化：避免全采样

4. **存储优化**
   - 生产环境：Elasticsearch或Cassandra
   - 数据保留：设置保留期限（如7天）
   - 索引优化：按天索引，方便删除

5. **告警和监控**
   - 慢调用告警：配置慢调用阈值
   - 错误率告警：配置错误率阈值
   - 依赖告警：关键服务故障告警

## 【常见错误】

1. **错误：全采样导致性能问题**
   - 现象：应用性能下降，链路追踪数据量大
   - 原因：生产环境全采样
   - 解决：使用动态采样或固定速率采样

2. **错误：链路追踪数据丢失**
   - 现象：查询不到追踪数据
   - 原因：上报失败、存储失败
   - 解决：检查上报配置、存储配置

3. **错误：链路追踪与日志未集成**
   - 现象：无法通过Trace ID查询日志
   - 原因：日志中未打印Trace ID
   - 解决：日志框架集成链路追踪（如Logback + SkyWalking）

4. **错误：采样率设置不合理**
   - 现象：重要请求未采样，或采样数据太多
   - 原因：采样率固定，未动态调整
   - 解决：使用动态采样

5. **错误：链路追踪系统成为瓶颈**
   - 现象：链路追踪系统性能差，影响应用
   - 原因：同步上报、未批量上报
   - 解决：异步上报、批量上报

## 总结

分布式链路追踪是分布式系统可观测性的核心组件，核心在于：
1. **追踪模型**：Trace（完整链路）、Span（单次调用）
2. **采样策略**：全采样、固定速率、动态采样、限流采样
3. **核心系统**：Zipkin（简单）、Jaeger（高性能）、SkyWalking（全功能）、OpenTelemetry（标准）
4. **应用场景**：性能分析、故障定位、依赖分析

实际应用中，需根据系统规模、性能要求、功能需求选择合适的链路追踪系统，并遵循最佳实践。
