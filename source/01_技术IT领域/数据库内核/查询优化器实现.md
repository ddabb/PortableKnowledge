# 查询优化器实现

## 定义

**查询优化器（Query Optimizer）**是数据库内核的"大脑"，负责将**SQL查询语句**转换成**最优执行计划**。它的核心目标是：**在所有可能执行计划中，找到代价最小的那个**。

类比：你要从北京到上海，导航软件会给你多条路线（高铁、飞机、自驾），并推荐时间最短/费用最低的那条。查询优化器就是数据库的"导航软件"。

查询优化器是数据库性能的关键，一个糟糕的执行计划可能导致查询从毫秒级变成小时级。

## 核心概念

### 1. 执行计划（Execution Plan）
执行计划是查询优化器的输出，描述了**如何执行查询**：
- **访问路径**：全表扫描、索引扫描、索引查找
- **连接方式**：NESTED LOOP JOIN、HASH JOIN、MERGE JOIN
- **连接顺序**：多表JOIN时，先连哪两张表
- **数据流动方式**：火山模型、向量化执行、编译执行

### 2. 优化器类型
| 优化器类型 | 全称 | 核心思想 | 代表数据库 |
|------------|------|----------|------------|
| **RBO** | Rule-Based Optimizer（基于规则的优化器） | 按预定义规则转换查询（如：总是先用索引） | 早期Oracle、MySQL |
| **CBO** | Cost-Based Optimizer（基于代价的优化器） | 估算每个执行计划的代价，选择代价最小的 | 现代数据库（Oracle、PostgreSQL、TiDB） |

### 3. 代价模型（Cost Model）
代价模型用于**估算执行计划的代价**，通常包括：
- **I/O代价**：读取磁盘页的次数
- **CPU代价**：CPU计算时间
- **内存代价**：内存使用量
- **网络代价**（分布式数据库）：数据传输量

代价单位通常是**磁盘页读取次数**（PAGE READ）或**时间**（毫秒）。

### 4. 统计信息（Statistics）
统计信息是代价估算的基础，包括：
- **表统计信息**：行数、页数、行平均长度
- **列统计信息**：不同值数量（NDV）、最大/最小值、空值比例、直方图
- **索引统计信息**：索引高度、叶子节点数、索引选择性

## 详细内容

### 查询优化器的处理流程

一个完整的查询优化过程分为**逻辑优化**和**物理优化**两个阶段。

#### 阶段1：逻辑优化（Logical Optimization）
逻辑优化的目标是**生成一个逻辑上等价但更优的查询表达式**，不改变查询结果，只改变查询结构。

**主要优化技术**：

1. **谓词下推（Predicate Pushdown）**
   - **原理**：将过滤条件尽可能下推到数据读取层，减少后续处理的数据量
   - **示例**：`SELECT * FROM (SELECT * FROM orders WHERE order_date > '2023-01-01') AS t WHERE t.amount > 100`
   - **优化后**：`SELECT * FROM orders WHERE order_date > '2023-01-01' AND amount > 100`
   - **效果**：减少子查询的数据量

2. **投影下推（Projection Pushdown）**
   - **原理**：只读取需要的列，减少I/O和内存
   - **示例**：`SELECT name FROM users WHERE age > 18`
   - **优化后**：只读取`name`和`age`列，不读其他列
   - **效果**：减少磁盘I/O，提升缓存命中率

3. **连接顺序重排（Join Reorder）**
   - **原理**：多表JOIN时，调整连接顺序，先连接小表
   - **示例**：`SELECT * FROM orders, users, products WHERE orders.user_id = users.id AND orders.product_id = products.id`
   - **优化后**：先连接最小的表，再连接大表
   - **效果**：减少中间结果集大小

4. **子查询消除（Subquery Elimination）**
   - **原理**：将子查询转换成JOIN，提升性能
   - **示例**：`SELECT * FROM users WHERE id IN (SELECT user_id FROM orders WHERE amount > 100)`
   - **优化后**：`SELECT DISTINCT users.* FROM users JOIN orders ON users.id = orders.user_id WHERE orders.amount > 100`
   - **效果**：避免子查询的重复执行

5. **视图展开（View Merging）**
   - **原理**：将视图定义展开到主查询中，获得更多优化机会
   - **示例**：`CREATE VIEW v_orders AS SELECT * FROM orders WHERE status = 'completed'; SELECT * FROM v_orders WHERE amount > 100`
   - **优化后**：`SELECT * FROM orders WHERE status = 'completed' AND amount > 100`
   - **效果**：避免视图的物化（Materialization）

#### 阶段2：物理优化（Physical Optimization）
物理优化的目标是**为每个逻辑操作选择最优的物理实现算法**，生成最优执行计划。

**主要优化技术**：

1. **访问路径选择（Access Path Selection）**
   - **全表扫描（Full Table Scan）**：适合小表或大部分数据都满足过滤条件
   - **索引扫描（Index Scan）**：适合有索引且选择性高的查询
   - **索引查找（Index Seek）**：适合等值查询或范围查询
   - **选择依据**：代价模型估算哪种访问路径代价最小

2. **连接方式选择（Join Method Selection）**
   - **NESTED LOOP JOIN**：适合小表驱动大表，外表有索引
   - **HASH JOIN**：适合大表连接，无索引，内存充足
   - **MERGE JOIN**：适合两表都已按连接键排序
   - **选择依据**：表大小、索引情况、内存大小、数据分布

3. **连接顺序选择（Join Order Selection）**
   - **动态规划（Dynamic Programming）**：枚举所有可能的连接顺序，选择代价最小的（适合表数≤10）
   - **贪心算法（Greedy Algorithm）**：每次选择代价最小的连接（适合表数>10）
   - **遗传算法（Genetic Algorithm）**：模拟进化过程，寻找近似最优解（适合复杂查询）

4. **并行度选择（Parallelism Degree）**
   - **原理**：决定查询是否并行执行，以及并行度多少
   - **依据**：表大小、CPU核心数、内存大小、系统负载

### 代价估算（Cost Estimation）

代价估算是查询优化器的核心能力，直接影响执行计划的质量。

#### 1. 基数估算（Cardinality Estimation）
基数估算是估算**一个操作会输出多少行**，这是代价估算的基础。

**主要技术**：
- **直方图（Histogram）**：将列值分成多个桶，统计每个桶的行数
- **采样（Sampling）**：对大表进行采样，估算数据分布
- **机器学习模型**：利用机器学习预测基数（如PostgreSQL的ndistinct系数）

**挑战**：
- **关联列**：多个列之间有相关性，独立假设会导致估算错误
- **数据倾斜**：某些值出现次数远超平均值，导致估算偏差
- **大表**：统计信息收集成本高，可能过时

#### 2. 代价计算公式
不同操作的代价计算公式不同，以下是典型公式：

**全表扫描代价**：
```
代价 = 表页数 × 单页读取代价 + CPU代价
```

**索引查找代价**：
```
代价 = 索引高度 × 单页读取代价 + 回表页数 × 单页读取代价 + CPU代价
```

**HASH JOIN代价**：
```
代价 = 构建哈希表代价 + 探测代价 + CPU代价
构建哈希表代价 = 小表页数 × 单页读取代价
探测代价 = 大表页数 × 单页读取代价
```

### 查询优化器的实现架构

#### 1. 优化器框架
现代数据库的查询优化器通常采用** Volcano/Cascades框架**：

**Volcano框架**：
- 将查询计划表示成**树状结构**
- 每个节点代表一个操作符（Scan、Filter、Join等）
- 自底向上或自顶向下搜索最优计划

**Cascades框架**：
- 将查询计划表示成**规则-任务**形式
- 通过应用转换规则生成等价计划
- 使用记忆化（Memoization）避免重复计算
- 代表：Microsoft SQL Server的优化器

#### 2. 优化器与执行器的关系
- **优化器**：生成最优执行计划（逻辑计划 → 物理计划）
- **执行器**：按照执行计划，实际执行查询
- **接口**：优化器输出执行计划树，执行器递归执行每个节点

## 示例/应用场景

### 示例1：电商系统的订单查询优化
**场景**：电商系统有1亿个订单，查询"2023年1月完成后支付金额大于100的订单"。

**原始查询**：
```sql
SELECT * FROM orders 
WHERE order_date BETWEEN '2023-01-01' AND '2023-01-31'
  AND status = 'completed'
  AND amount > 100;
```

**优化过程**：
1. **谓词下推**：将三个过滤条件合并，一次性过滤
2. **索引选择**：
   - 有索引：`(order_date, status, amount)`复合索引
   - 代价估算：索引查找代价 < 全表扫描代价
   - 选择：使用复合索引
3. **执行计划**：
   - 使用复合索引查找满足条件的订单ID
   - 回表获取完整记录
   - 返回结果

**性能提升**：从全表扫描（1亿行）到索引查找（约1万行），性能提升10000倍。

### 示例2：多表JOIN查询优化
**场景**：查询"购买了'iPhone 15'的用户信息和订单详情"。

**原始查询**：
```sql
SELECT users.*, orders.*, products.name
FROM users, orders, products
WHERE users.id = orders.user_id
  AND orders.product_id = products.id
  AND products.name = 'iPhone 15';
```

**优化过程**：
1. **连接顺序重排**：
   - 原始顺序：users → orders → products
   - 优化后：products → orders → users（products表最小，先过滤）
2. **连接方式选择**：
   - products ↔ orders：HASH JOIN（products表小，适合构建哈希表）
   - 结果 ↔ users：NESTED LOOP JOIN（users表有主键索引）
3. **访问路径选择**：
   - products：使用`name`上的索引查找'iPhone 15'
   - orders：使用`product_id`上的索引查找订单
   - users：使用主键索引查找用户信息

**性能提升**：从笛卡尔积（用户数×订单数×商品数）到高效的三表连接，性能提升百万倍。

### 示例3：分布式数据库的查询优化
**场景**：分布式数据库有3个分片，查询"各地区的销售总额"。

**原始查询**：
```sql
SELECT region, SUM(amount) FROM orders GROUP BY region;
```

**优化过程**：
1. **谓词下推**：在每个分片上先执行局部聚合（LOCAL AGGREGATE）
2. **数据传输优化**：只传输聚合结果，不传输原始数据
3. **并行执行**：3个分片并行执行局部聚合，协调节点执行全局聚合
4. **执行计划**：
   - 分片1：局部聚合，输出(region, SUM(amount))
   - 分片2：局部聚合，输出(region, SUM(amount))
   - 分片3：局部聚合，输出(region, SUM(amount))
   - 协调节点：全局聚合，合并结果

**性能提升**：从传输1亿行原始数据到传输3行聚合结果，网络传输量减少千万倍。

## 最佳实践

### 1. 索引设计最佳实践
- **让优化器优先使用索引**：在过滤条件、连接条件、排序字段上建索引
- **避免索引失效**：不在索引列上使用函数、避免类型转换、避免前导模糊查询
- **使用复合索引**：遵循最左前缀原则，将选择性高的列放在前面

### 2. 查询编写最佳实践
- **避免使用SELECT ***：只查询需要的列，减少I/O和内存
- **使用参数化查询**：避免SQL注入，提升计划缓存命中率
- **避免大数据量IN列表**：IN列表过大会导致优化器选择错误执行计划，考虑使用JOIN或临时表
- **合理使用子查询**：简单子查询可以消除，复杂子查询可能更适合保留

### 3. 统计信息维护最佳实践
- **定期更新统计信息**：数据分布变化后，及时更新统计信息
- **使用直方图**：对数据分布不均匀的列，使用直方图提升基数估算准确性
- **避免统计信息过时**：设置自动更新统计信息的策略

### 4. 执行计划分析最佳实践
- **使用EXPLAIN分析执行计划**：理解优化器选择的执行计划，判断是否最优
- **关注代价高的操作**：全表扫描、大表连接、排序操作通常是性能瓶颈
- **对比不同执行计划**：使用 optimizer hints 强制使用不同执行计划，对比性能

## 【常见错误】

### 1. 索引使用错误
- **错误1：索引列上使用函数**
  - 表现：`WHERE YEAR(create_time) = 2023`导致索引失效
  - 原因：对索引列进行函数运算，优化器无法使用索引
  - 解决：改为范围查询`WHERE create_time >= '2023-01-01' AND create_time < '2024-01-01'`

- **错误2：类型转换导致索引失效**
  - 表现：`WHERE user_id = '123'`（user_id是INT）导致索引失效
  - 原因：字符串和数字比较会发生类型转换，优化器无法使用索引
  - 解决：确保查询条件类型与列类型一致

### 2. 查询编写错误
- **错误1：使用SELECT ***
  - 表现：查询所有列，导致I/O和内存浪费
  - 原因：不理解只需要部分列
  - 解决：只查询需要的列

- **错误2：大数据量IN列表**
  - 表现：IN列表有上万个值，查询极慢
  - 原因：优化器无法准确估算基数，选择错误执行计划
  - 解决：使用JOIN或临时表替代大数据量IN列表

### 3. 统计信息维护错误
- **错误1：长期不更新统计信息**
  - 表现：数据分布已变化，但优化器仍使用旧统计信息，选择错误执行计划
  - 原因：不了解统计信息的重要性
  - 解决：定期更新统计信息，或设置自动更新

- **错误2：统计信息采样率过低**
  - 表现：大表的统计信息不准确，优化器选择错误执行计划
  - 原因：为了节省时间，使用过低采样率
  - 解决：对大表使用较高采样率（如10%或更高）

### 4. 执行计划分析错误
- **错误1：不看执行计划，盲目优化**
  - 表现：凭感觉添加索引，效果不佳
  - 原因：不了解执行计划，无法定位性能瓶颈
  - 解决：使用EXPLAIN分析执行计划，找到代价最高的操作

- **错误2：过度依赖optimizer hints**
  - 表现：大量使用hints强制使用特定执行计划
  - 原因：不了解优化器的代价模型，盲目干预
  - 解决：先让优化器自己选择，只有确认优化器选择错误时才使用hints

## 总结

查询优化器是数据库内核的"大脑"，理解其实现原理和优化技术，是成为数据库内核开发专家或数据库性能优化专家的必经之路。

**核心要点回顾**：
1. **查询优化分为两个阶段**：逻辑优化（改变查询结构）和物理优化（选择物理算法）
2. **代价模型是优化器的核心**：基于统计信息估算执行计划的代价，选择代价最小的
3. **索引设计直接影响优化器选择**：合理的索引设计可以引导优化器选择最优执行计划
4. **统计信息是关键**：统计信息不准确，优化器就会选择错误的执行计划

**未来发展趋势**：
- **AI驱动的查询优化**：利用机器学习预测基数、选择最优执行计划（如Oracle的SQL Plan Management）
- **自适应查询执行**：执行过程中根据实际情况动态调整执行计划（如Apache Calcite的自适应优化）
- **硬件感知的优化**：利用SSD、持久化内存（PMEM）、GPU等硬件特性优化查询执行

掌握查询优化器实现原理，让你能够深入理解数据库性能调优的本质，设计出高性能的数据库应用系统。
