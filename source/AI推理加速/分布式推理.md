# 分布式推理

## 定义

**分布式推理**是指将大语言模型（LLM）推理任务分布到多个计算设备（如多个GPU、多台机器）上执行，以突破单设备显存和计算能力限制，支持更大模型或更高吞吐量的推理。

**核心目标**：
- **突破显存限制**：支持单卡放不下的超大模型（如GPT-3 175B）
- **提升吞吐量**：通过并行处理提升整体推理吞吐量
- **降低延迟**：通过流水线并行降低单个请求的延迟

---

## 核心概念

### 1. 分布式推理并行策略

| 并行策略 | 原理 | 适用场景 |
|----------|------|----------|
| **张量并行（Tensor Parallelism, TP）** | 将模型的每一层（如Attention、FFN）切分到多个GPU上 | 模型太大，单GPU显存放不下 |
| **流水线并行（Pipeline Parallelism, PP）** | 将模型的不同层切分到多个GPU上，形成流水线 | 模型层数多，单GPU显存放不下 |
| **序列并行（Sequence Parallelism, SP）** | 将序列维度切分到多个GPU上 | 序列很长，单GPU显存放不下KV Cache |
| **数据并行（Data Parallelism, DP）** | 将数据（请求）切分到多个GPU上，每个GPU运行相同模型 | 高吞吐量场景，模型能单卡放下 |
| **专家并行（Expert Parallelism, EP）** | 针对MoE模型，不同专家放置在不同GPU上 | MoE模型推理 |

### 2. 通信模式

| 通信模式 | 说明 | 使用场景 |
|----------|------|----------|
| **All-Reduce** | 所有节点归约（求和、平均）后广播结果 | 数据并行梯度同步 |
| **All-Gather** | 所有节点收集数据，拼接成完整张量 | 张量并行中收集结果 |
| **Reduce-Scatter** | 归约后散射到各节点 | 张量并行中分发输入 |
| **Point-to-Point** | 节点间点对点通信 | 流水线并行中传递激活值 |

### 3. 分布式推理框架对比

| 框架 | 支持并行策略 | 优势 | 适用场景 |
|------|--------------|------|----------|
| **Megatron-LM** | TP、PP、SP | 通信优化好，性能高 | 超大模型推理 |
| **DeepSpeed-Inference** | TP、PP、EP | 易用性好，与训练框架统一 | 训练和推理统一场景 |
| **vLLM** | TP | 易用性好，高吞吐 | 在线服务 |
| **TensorRT-LLM** | TP、PP、SP、EP | 性能极致，NVIDIA硬件专用 | 低延迟、高吞吐场景 |

## 详细内容

### 一、张量并行（Tensor Parallelism）

#### 1.1 原理

**核心思想**：将模型的每一层（如Linear、Attention）切分到多个GPU上，各GPU计算部分结果，然后通过通信整合结果。

**以Linear层为例**：
- 权重矩阵 `W` 按列切分：`W = [W1, W2]`
- GPU 0 计算：`Y1 = X * W1`
- GPU 1 计算：`Y2 = X * W2`
- 通信：All-Gather 拼接 `Y = [Y1, Y2]`

**以Attention层为例**：
- 多头注意力（Multi-Head Attention）中，不同头切分到不同GPU
- GPU 0 计算头1、头2；GPU 1 计算头3、头4
- 通信：All-Gather 拼接所有头的输出

#### 1.2 实现细节

**Megatron-LM张量并行**：
- 使用 `torch.distributed` 的 `all_reduce`、`all_gather` 等通信原语
- 对Linear、LayerNorm、Attention、FFN等层进行张量并行改造

**代码示例（简化）**：
```python
# 张量并行Linear层
class ColumnParallelLinear(nn.Module):
    def __init__(self, in_features, out_features, world_size):
        super().__init__()
        self.world_size = world_size
        self.rank = torch.distributed.get_rank()
        
        # 按列切分输出维度
        assert out_features % world_size == 0
        self.out_features_per_partition = out_features // world_size
        
        # 本地权重：只保存部分权重
        self.weight = nn.Parameter(
            torch.empty(self.out_features_per_partition, in_features)
        )
    
    def forward(self, x):
        # 本地计算：部分输出
        output_parital = F.linear(x, self.weight)
        
        # 通信：All-Gather拼接完整输出
        output_full = torch.distributed.all_gather(
            [torch.empty_like(output_parital) for _ in range(self.world_size)],
            output_parital
        )
        output_full = torch.cat(output_full, dim=-1)
        
        return output_full
```

#### 1.3 通信开销

**问题**：张量并行需要频繁通信（每层都要通信），通信开销大。

**优化方法**：
- **通信与计算重叠**：使用CUDA流（Stream）将通信和计算并行
- **减少通信量**：使用激活值重计算（Activation Checkpointing）减少通信
- **使用高速互联**：NVLink、InfiniBand

### 二、流水线并行（Pipeline Parallelism）

#### 2.1 原理

**核心思想**：将模型的不同层切分到多个GPU上，形成流水线，不同GPU处理不同batch。

**示例**：4层模型，2个GPU
- GPU 0：Layer 1、Layer 2
- GPU 1：Layer 3、Layer 4

**工作流程**：
1. GPU 0 计算Layer 1、Layer 2
2. 将激活值（Activation）发送给GPU 1
3. GPU 1 计算Layer 3、Layer 4
4. 返回结果

#### 2.2 流水线调度策略

**GPipe调度**：
- 前向传播：依次通过所有stage
- 后向传播：依次通过所有stage（反向）
- 问题：GPU空闲时间多（气泡大）

**1F1B调度（One Forward One Backward）**：
- 交错执行前向和后向
- 减少气泡时间
- 示例：PipeDream、Megatron-LM

#### 2.3 实现细节

**Megatron-LM流水线并行**：
- 将模型按层切分为多个stage
- 使用 `torch.distributed` 的 `send`、`recv` 进行点对点通信
- 支持1F1B调度

**代码示例（简化）**：
```python
# 流水线并行：Stage 0
class PipelineStage0(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = nn.Sequential(
            Layer1(),
            Layer2()
        )
    
    def forward(self, x):
        x = self.layers(x)
        # 发送激活值到下一个stage
        torch.distributed.send(x, dst=1)
        return x

# 流水线并行：Stage 1
class PipelineStage1(nn.Module):
    def __init__(self):
        super().__init__()
        self.layers = nn.Sequential(
            Layer3(),
            Layer4()
        )
    
    def forward(self, x):
        # 接收激活值 from previous stage
        torch.distributed.recv(x, src=0)
        x = self.layers(x)
        return x
```

#### 2.4 气泡问题

**问题**：流水线并行中，部分GPU会空闲（等待前序stage完成），称为气泡（bubble）。

**优化方法**：
- **增加microbatch数量**：将一个batch切分为多个microbatch，填满流水线
- **使用1F1B调度**：减少气泡时间
- **优化stage划分**：使各stage计算时间均衡

### 三、序列并行（Sequence Parallelism）

#### 3.1 原理

**核心思想**：将序列维度切分到多个GPU上，每个GPU处理部分序列，减少KV Cache显存占用。

**适用场景**：序列很长（如32K、128K），单GPU显存放不下KV Cache。

**示例**：序列长度2048，2个GPU
- GPU 0：处理token 0-1023
- GPU 1：处理token 1024-2047

#### 3.2 实现细节

**Megatron-LM序列并行**：
- 对LayerNorm、Dropout等操作，按序列维度切分
- 对Attention、FFN等操作，需要All-Gather和Reduce-Scatter通信

**通信开销**：
- 序列并行需要额外的All-Gather和Reduce-Scatter通信
- 但减少了KV Cache显存占用，支持更长序列

### 四、数据并行（Data Parallelism）

#### 4.1 原理

**核心思想**：将数据（请求）切分到多个GPU上，每个GPU运行相同模型，独立处理不同请求。

**适用场景**：模型能单卡放下，需要高吞吐量。

**示例**：batch size=128，4个GPU
- GPU 0：处理请求0-31
- GPU 1：处理请求32-63
- GPU 2：处理请求64-95
- GPU 3：处理请求96-127

#### 4.2 实现细节

**PyTorch数据并行**：
- 使用 `torch.nn.DataParallel` 或 `torch.nn.DistributedDataParallel`
- 每个GPU有完整模型副本
- 前向传播：各GPU独立计算
- 后向传播：梯度All-Reduce同步

**分布式推理中的数据并行**：
- 不同GPU处理不同请求
- 无需梯度同步（推理不更新权重）
- 只需确保各GPU模型权重一致

### 五、通信优化

#### 5.1 通信与计算重叠

**原理**：使用CUDA流（Stream）将通信和计算并行执行。

**示例**：
```python
# 创建CUDA流
stream_compute = torch.cuda.Stream()
stream_comm = torch.cuda.Stream()

# 计算部分
with torch.cuda.stream(stream_compute):
    output = model(input)

# 通信部分（与计算并行）
with torch.cuda.stream(stream_comm):
    torch.distributed.all_reduce(output)

# 等待所有流完成
torch.cuda.synchronize()
```

#### 5.2 梯度累积（Gradient Accumulation）

**原理**：将大batch切分为多个microbatch，逐步累积梯度，减少通信次数。

**适用场景**：数据并行中，减少梯度同步通信次数。

#### 5.3 使用高速互联

**硬件**：
- **NVLink**：GPU间高速互联（带宽~600 GB/s）
- **InfiniBand**：机器间高速互联（带宽~200 Gb/s）
- **PCIe 5.0**：GPU与CPU间互联（带宽~64 GB/s）

**优化**：
- 尽量使用NVLink互联的GPU进行张量并行
- 跨机器推理使用InfiniBand互联

## 示例/应用场景

### 示例1：使用Megatron-LM进行张量并行推理

**场景**：部署Llama-2-70B模型，使用4张A100 GPU张量并行推理。

**步骤**：
1. **安装Megatron-LM**：
   ```bash
   git clone https://github.com/NVIDIA/Megatron-LM.git
   cd Megatron-LM
   pip install -e .
   ```

2. **转换模型为Megatron格式**：
   ```bash
   python tools/convert_checkpoint.py \
       --model_type llama \
       --load_dir meta-llama/Llama-2-70b-hf \
       --save_dir llama-2-70b-megatron \
       --target_tensor_parallel_size 4
   ```

3. **启动推理**：
   ```bash
   mpiexec -np 4 python inference.py \
       --model-type llama \
       --load llama-2-70b-megatron \
       --tensor-model-parallel-size 4 \
       --pipeline-model-parallel-size 1 \
       --num-layers 80 \
       --hidden-size 8192 \
       --num-attention-heads 64 \
       --max-position-embeddings 4096 \
       --fp16
   ```

**效果**：
- 支持70B模型推理（4张A100 GPU）
- 延迟：150ms（比单卡快4倍）

### 示例2：使用DeepSpeed-Inference进行流水线并行推理

**场景**：部署GPT-3 175B模型，使用8张A100 GPU流水线并行推理。

**步骤**：
1. **安装DeepSpeed**：
   ```bash
   pip install deepspeed
   ```

2. **配置DeepSpeed推理配置**：
   ```json
   {
     "tensor_parallel": {
       "tp_size": 4
     },
     "pipeline_parallel": {
       "pp_size": 2
     },
     "dtype": "fp16"
   }
   ```

3. **启动推理**：
   ```bash
   deepspeed --num_gpus 8 inference.py \
       --deepspeed_config ds_config.json \
       --model gpt-3-175b
   ```

**效果**：
- 支持175B模型推理（8张A100 GPU）
- 延迟：300ms（比单卡快8倍）

## 最佳实践

### 1. 系统化分布式推理部署流程

**不推荐**（随意选择并行策略）：
```text
不分析模型和硬件，随意选择并行策略，导致性能不佳
```

**推荐**（系统化流程）：
```text
1. 分析模型大小和硬件：
   - 模型能否单卡放下？
   - 序列长度是否很长？
   - GPU间互联带宽（NVLink/InfiniBand/PCIe）？
2. 选择并行策略：
   - 模型太大：张量并行 + 流水线并行
   - 序列很长：序列并行
   - 高吞吐量：数据并行
   - MoE模型：专家并行
3. 选择分布式推理框架：
   - 性能优先：Megatron-LM、TensorRT-LLM
   - 易用性优先：DeepSpeed-Inference、vLLM
4. 配置和调优：
   - 设置合适的并行度（tp_size、pp_size）
   - 优化通信（通信与计算重叠）
   - 监控性能（延迟、吞吐量、GPU利用率）
5. 测试和优化：
   - 测试不同并行策略的性能
   - 优化并行策略配置
   - 持续监控和调优
```

### 2. 优化通信开销

**不推荐**（忽略通信开销）：
```text
不进行通信优化，导致通信成为瓶颈，性能不佳
```

**推荐**（优化通信开销）：
```text
- 通信与计算重叠：使用CUDA流将通信和计算并行
- 减少通信量：使用激活值重计算（Activation Checkpointing）
- 使用高速互联：NVLink、InfiniBand
- 优化通信模式：选择合适的通信原语（All-Reduce、All-Gather等）
```

### 3. 平衡并行策略和硬件限制

**不推荐**（忽略硬件限制）：
```text
选择的并行策略超过硬件限制（如GPU数量不足、互联带宽低），导致无法部署或性能不佳
```

**推荐**（根据硬件限制选择策略）：
```text
- GPU数量不足：减少并行度（tp_size、pp_size）
- 互联带宽低：减少通信密集型并行策略（如减少张量并行，增加流水线并行）
- 显存不足：使用激活值重计算（Activation Checkpointing）
```

### 4. 监控和调优性能

**不推荐**（不监控性能）：
```text
不监控性能，导致问题发现晚，性能不佳
```

**推荐**（监控和调优）：
```text
- 监控关键指标：延迟、吞吐量、GPU利用率、通信时间占比
- 分析性能瓶颈：是计算瓶颈还是通信瓶颈？
- 调优并行策略：调整tp_size、pp_size、microbatch数量
- 持续监控和调优：根据硬件更新、模型更新调整优化策略
```

## 【常见错误】

### 1. 并行策略选择错误

**错误示例**：
```text
模型能单卡放下，却使用张量并行，导致通信开销大，性能反而下降
```

**正确做法**：
```text
- 模型能单卡放下：使用数据并行（高吞吐量）
- 模型太大：使用张量并行 + 流水线并行
- 序列很长：使用序列并行
```

### 2. 忽略通信开销

**错误示例**：
```text
不进行通信优化，导致通信成为瓶颈，性能不佳
```

**正确做法**：
```text
- 通信与计算重叠：使用CUDA流将通信和计算并行
- 减少通信量：使用激活值重计算
- 使用高速互联：NVLink、InfiniBand
```

### 3. 硬件限制分析不足

**错误示例**：
```text
选择的并行策略超过硬件限制（如GPU数量不足、互联带宽低），导致无法部署或性能不佳
```

**正确做法**：
```text
- 分析GPU数量：选择合适的并行度（tp_size、pp_size）
- 分析互联带宽：选择合适的并行策略（通信密集型 vs 计算密集型）
- 分析显存大小：使用激活值重计算（Activation Checkpointing）
```

### 4. 不监控和调优性能

**错误示例**：
```text
不监控性能，导致问题发现晚，性能不佳
```

**正确做法**：
```text
- 监控关键指标：延迟、吞吐量、GPU利用率、通信时间占比
- 分析性能瓶颈：是计算瓶颈还是通信瓶颈？
- 调优并行策略：调整tp_size、pp_size、microbatch数量
- 持续监控和调优：根据硬件更新、模型更新调整优化策略
```

## 总结

分布式推理是支持超大模型推理的关键技术，涉及张量并行、流水线并行、序列并行、数据并行等多种并行策略，以及通信优化、框架选择、性能调优等多个方面。要做好分布式推理，需要：

1. **理解分布式推理核心概念**：并行策略、通信模式、框架对比
2. **掌握并行策略原理和实现**：张量并行、流水线并行、序列并行、数据并行
3. **系统化部署流程**：分析模型和硬件 → 选择并行策略 → 选择框架 → 配置调优 → 测试优化
4. **优化通信开销**：通信与计算重叠、减少通信量、使用高速互联
5. **监控和调优性能**：监控关键指标、分析瓶颈、调优策略、持续优化

随着LLM模型越来越大、应用场景越来越复杂，分布式推理技术将持续发展，包括更高效的并行策略、更智能的通信优化、更完善的框架支持。
