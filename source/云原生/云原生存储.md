# 云原生存储

## 定义

云原生存储是**为容器化应用设计的持久化存储方案**，需满足容器动态调度、弹性扩展、跨节点访问等云原生特性。

**核心挑战**：
- **动态性**：Pod可能在任意节点启动，存储需动态挂载
- **持久性**：Pod重建后数据不丢失
- **性能**：高IOPS、低延迟，满足数据库等性能敏感型应用
- **可用性**：存储层高可用，避免单点故障

**核心价值**：
- 解耦存储与计算，独立扩展
- 动态供给，自动化运维
- 多租户隔离，安全可控

## 核心概念

### 1. 存储抽象层
**PersistentVolume（PV）**：
- **定义**：集群级存储资源，由管理员创建或动态供给
- **生命周期**：独立于Pod，Pod删除后PV可保留
- **绑定状态**：Available（可用）→ Bound（已绑定）→ Released（已释放）→ Available（可回收）

**PersistentVolumeClaim（PVC）**：
- **定义**：用户对存储的请求（类似Pod消耗节点资源，PVC消耗PV资源）
- **绑定机制**：PVC绑定满足条件的PV（容量、访问模式、StorageClass）
- **使用方式**：Pod通过PVC挂载存储

**StorageClass**：
- **定义**：描述存储类，支持动态供给PV
- **核心价值**：按需创建PV，无需预分配
- **参数**：provisioner（供给器）、parameters（存储参数）、reclaimPolicy（回收策略）

### 2. 访问模式
**ReadWriteOnce（RWO）**：
- 单节点读写，最常见模式
- 适用场景：数据库、文件系统

**ReadOnlyMany（ROX）**：
- 多节点只读
- 适用场景：静态资源、文档库

**ReadWriteMany（RWX）**：
- 多节点读写
- 适用场景：共享文件系统（NFS、CephFS）
- **注意**：云厂商块存储（EBS、Azure Disk）不支持RWX

### 3. 存储供给方式
**静态供给**：
- 管理员预先创建PV
- PVC绑定现有PV
- 适用场景：预分配存储、特定性能要求

**动态供给**：
- StorageClass自动创建PV
- 无需预分配，按需创建
- 适用场景：大规模集群、多租户环境

### 4. 存储回收策略
**Retain（保留）**：
- PV删除后，数据保留，需手动清理
- 适用场景：重要数据、合规性要求

**Delete（删除）**：
- PV删除后，底层存储一并删除
- 适用场景：临时数据、测试环境

**Recycle（回收）**：
- 已废弃，执行`rm -rf /volume/*`清理数据
- 不安全，不推荐使用

## 详细内容

### Kubernetes存储架构

```
Pod
 ↓
PVC (PersistentVolumeClaim)
 ↓
PV (PersistentVolume)
 ↓
StorageClass (动态供给)
 ↓
存储供给器（Provisioner）
 ↓
底层存储（AWS EBS、Azure Disk、GCE PD、Ceph RBD、NFS）
```

**关键组件**：
- **PV Controller**：监听PVC，绑定PV
- **Volume Manager**：Pod调度到节点后，挂载存储
- **Attachment & Mount 控制器**：处理存储卷挂载/卸载
- **CSI Driver**：容器存储接口驱动，对接底层存储

### CSI（Container Storage Interface）

**设计目标**：
- 标准化存储插件接口
- 解耦Kubernetes与存储厂商实现
- 支持第三方存储插件

**三大组件**：
1. **CSI Controller Service**：
   - 创建/删除卷（CreateVolume/DeleteVolume）
   - 附加/分离卷（ControllerPublishVolume/ControllerUnpublishVolume）
   - 快照管理（CreateSnapshot/DeleteSnapshot）

2. **CSI Node Service**：
   - 挂载/卸载卷（NodeStageVolume/NodeUnstageVolume）
   - 获取节点信息（NodeGetInfo）

3. **CSI Identity Service**：
   - 获取插件信息（GetPluginInfo）
   - 插件健康检查（Probe）

**主流CSI驱动**：
- **云厂商**：AWS EBS CSI、Azure Disk CSI、GCP PD CSI
- **开源存储**：Ceph CSI、GlusterFS CSI、MinIO CSI
- **商业存储**：Pure Storage CSI、NetApp Trident

### 存储性能优化

#### 性能关键指标
- **IOPS**：每秒读写次数（SSD可达数万IOPS）
- **吞吐量**：每秒读写数据量（MB/s）
- **延迟**：读写响应时间（SSD < 1ms，HDD > 5ms）

#### 优化策略
1. **选择合适的存储类型**：
   - 数据库：高性能SSD（io1/io2）
   - 日志存储：吞吐优化HDD（st1）
   - 冷数据：归档存储（Glacier、Azure Archive）

2. **本地SSD（Local PV）**：
   - 直接使用节点本地NVMe SSD
   - 性能最优（< 100μs延迟）
   - 风险：节点故障数据丢失，需应用层副本

3. **缓存加速**：
   - 使用Redis/Memcached缓存热点数据
   - 减少存储层读取压力

4. **连接池优化**：
   - 数据库连接池配置（最大连接数、空闲连接）
   - 避免频繁建立连接

### 存储安全

#### 数据加密
**静态加密（Encryption at Rest）**：
- **云厂商方案**：AWS EBS加密、Azure Disk加密、GCP PD加密
- **自建方案**：LUKS加密、dm-crypt

**传输加密（Encryption in Transit）**：
- **TLS/SSL**：客户端到存储的传输加密
- **IPsec**：存储网络传输加密

#### 访问控制
**RBAC**：
- 限制PVC创建/删除权限
- 按Namespace隔离存储资源

**StorageClass权限**：
- 限制用户可使用的StorageClass
- 防止滥用高性能/高成本存储

#### 数据隔离
**多租户隔离**：
- 每个租户独立StorageClass
- PVC绑定到特定Namespace

**快照隔离**：
- VolumeSnapshot独立命名空间
- 防止跨租户数据恢复

## 示例/应用场景

### 场景1：数据库持久化存储
**需求**：MySQL主从复制，数据持久化，高性能SSD

**方案**：
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: mysql-pvc
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: gp2-ssd
  resources:
    requests:
      storage: 100Gi
```

**关键点**：
- 使用RWO访问模式（单节点读写）
- 选择高性能SSD StorageClass
- StatefulSet + PVC模板，每个Pod独立PV

### 场景2：共享文件系统
**需求**：多个Pod共享配置文件、静态资源

**方案**：
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: shared-pvc
spec:
  accessModes:
  - ReadWriteMany
  storageClassName: nfs-client
  resources:
    requests:
      storage: 500Gi
```

**关键点**：
- 使用RWX访问模式（多节点读写）
- 选择支持RWX的存储（NFS、CephFS）
- 适用场景：配置文件、静态资源、AI训练数据共享

### 场景3：AI训练数据存储
**需求**：AI训练需要高速读取大量数据，本地SSD性能最优

**方案**：
```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: local-ssd-pv
spec:
  capacity:
    storage: 1Ti
  accessModes:
  - ReadWriteOnce
  local:
    path: /mnt/ssd  # 节点本地SSD挂载路径
  nodeAffinity:
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values:
          - gpu-node-1
```

**关键点**：
- 使用Local PV，直接访问节点本地SSD
- 性能最优（< 100μs延迟）
- 需配置nodeAffinity，固定Pod调度到特定节点
- 风险：节点故障数据丢失，需应用层副本（如Ceph副本）

## 【对应领域考点】

1. **PV/PVC绑定机制**：匹配条件（容量、访问模式、StorageClass、标签选择器）
2. **StorageClass动态供给**：provisioner、parameters、reclaimPolicy
3. **访问模式对比**：RWO、ROX、RWX适用场景和底层存储支持
4. **CSI架构**：Controller Service、Node Service、Identity Service三大组件
5. **存储性能优化**：IOPS、吞吐量、延迟指标，本地SSD vs 网络存储
6. **存储安全**：静态加密、传输加密、RBAC访问控制
7. **Local PV**：本地SSD性能优势，nodeAffinity配置
8. **VolumeSnapshot**：创建卷快照，数据备份与恢复

## 最佳实践

### 1. 存储选型
- **数据库**：高性能SSD（io1/io2），RWO访问模式
- **日志存储**：吞吐优化HDD（st1），RWO访问模式
- **共享文件**：NFS/CephFS，RWX访问模式
- **AI训练**：本地NVMe SSD，性能最优

### 2. 容量规划
- **初始容量**：预留30%增长空间
- **监控告警**：存储使用率超80%告警
- **自动扩容**：云厂商支持在线扩容（需文件系统支持）

### 3. 备份恢复
- **VolumeSnapshot**：创建卷快照
- **Velero**：备份PVC和PV到对象存储（S3、Azure Blob）
- **定期演练**：恢复流程验证，确保备份可用

### 4. 性能调优
- **数据库**：使用本地SSD，避免网络存储延迟
- **缓存层**：Redis/Memcached缓存热点数据
- **连接池**：优化数据库连接池配置

### 5. 安全加固
- **加密**：启用静态加密和传输加密
- **RBAC**：限制PVC操作权限
- **网络隔离**：存储网络与业务网络隔离

## 【常见错误】

### 错误1：使用emptyDir存储重要数据
**表现**：Pod内数据存储到emptyDir
**后果**：Pod重建数据丢失
**正确做法**：使用PVC持久化存储

### 错误2：忽视存储性能
**表现**：数据库使用网络存储（如EBS gp2）
**后果**：I/O延迟高，数据库性能差
**正确做法**：数据库使用本地SSD或高性能云盘（io1/io2）

### 错误3：PVC容量规划不足
**表现**：PVC初始容量小，后续需扩容
**后果**：部分文件系统不支持在线扩容，需停机
**正确做法**：初始容量预留30%增长空间，选择支持在线扩容的StorageClass

### 错误4：跨可用区存储访问
**表现**：Pod在可用区A，PV在可用区B
**后果**：跨可用区访问延迟高，成本高
**正确做法**：使用拓扑感知调度（topologyKey: topology.kubernetes.io/zone）

### 错误5：忽视存储成本
**表现**：所有应用使用高性能SSD
**后果**：存储成本过高
**正确做法**：按业务重要性分级，高性能存储仅用于核心数据库

## 总结

云原生存储是**有状态应用的基石**，需平衡性能、可用性、成本、安全四大要素。

**关键要点**：
1. **抽象层**：PV/PVC/StorageClass解耦存储与计算
2. **动态供给**：StorageClass按需创建PV，自动化运维
3. **CSI标准**：统一存储插件接口，支持第三方存储
4. **性能优化**：本地SSD > 网络存储，缓存层减少I/O压力
5. **安全加固**：加密、RBAC、网络隔离三位一体

**学习路径**：
1. 理解PV/PVC/StorageClass核心概念
2. 掌握CSI架构和主流驱动
3. 实践存储性能优化和安全加固
4. 学习存储备份恢复（VolumeSnapshot、Velero）
5. 参与CNCF存储项目（Rook、Ceph CSI）

云原生存储复杂度高，但掌握后能为有状态应用提供坚实的存储基础。
