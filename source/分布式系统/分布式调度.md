# 分布式调度

## 定义

分布式调度是指在分布式系统中，对定时任务、周期性任务或一次性任务进行统一管理和调度的机制。它解决单机调度无法扩展、单点故障、任务重复执行等问题。

核心目标：
- **高可用**：调度中心无单点，故障自动转移
- **可扩展**：调度能力随集群规模线性扩展
- **任务管理**：统一的任务管理界面，方便运维
- **避免重复**：同一任务在同一时间仅被一个节点执行
- **失败重试**：任务执行失败，支持重试或告警

## 核心概念

### 1. 调度类型

**定时调度（Cron Scheduling）**
- 基于Cron表达式，按固定时间执行
- 典型场景：每天凌晨数据对账、每周一生成报表
- 特点：时间固定、可预测

**周期性调度（Periodic Scheduling）**
- 固定间隔执行，如每5分钟执行一次
- 典型场景：每5分钟拉取数据、每10分钟同步缓存
- 特点：间隔固定、与时间无关

**一次性调度（One-Time Scheduling）**
- 在指定时间执行一次
- 典型场景：指定时间发送通知、延迟任务
- 特点：仅执行一次

**工作流调度（Workflow Scheduling）**
- 多个任务按依赖关系顺序执行
- 典型场景：ETL流程（抽取→转换→加载）
- 特点：任务有依赖、需编排

### 2. 调度策略

**轮询调度（Round Robin）**
- 任务按顺序分配到不同节点
- 优点：简单、均匀
- 缺点：不考虑节点负载

**负载均衡调度（Load Balanced Scheduling）**
- 根据节点负载（CPU、内存、任务数）分配任务
- 优点：合理利用资源
- 缺点：需监控节点负载

**故障转移调度（Failover Scheduling）**
- 节点故障，任务转移到其他节点执行
- 优点：高可用
- 缺点：需检测节点故障

**分片调度（Sharding Scheduling）**
- 任务分片，不同节点执行不同分片
- 优点：并行执行、提高吞吐
- 缺点：分片逻辑复杂

### 3. 任务执行策略

**单机执行**
- 任务仅在一个节点执行
- 适用：不允许并发的任务

**广播执行**
- 任务在所有节点执行
- 适用：本地缓存刷新、本地配置更新

**分片执行**
- 任务分片，不同节点执行不同分片
- 适用：大规模数据并行处理

### 4. 失败处理策略

**失败重试**
- 任务执行失败，按配置重试N次
- 适用：临时故障（网络抖动、数据库锁）

**失败告警**
- 任务执行失败，发送告警通知
- 适用：关键任务，需人工介入

**失败转移**
- 任务执行失败，转移到其他节点执行
- 适用：节点故障导致的失败

## 详细内容

### 1. 集中式调度架构

**架构特点**
- 调度中心统一管理任务，执行器执行任务
- 调度中心：管理任务、触发调度、监控执行
- 执行器：注册到调度中心，接收调度请求，回调执行结果

**优点**
- 统一管理：任务管理、监控、日志集中
- 避免重复：调度中心保证同一任务同一时间仅触发一次
- 易于扩展：增加执行器，调度中心自动发现

**缺点**
- 调度中心单点：需做高可用（主备、集群）
- 调度中心瓶颈：任务量大时，调度中心压力大

**典型实现**
- XXL-JOB：国内流行，管理界面友好
- Elastic-JOB：当当网开源，支持分片
- Azkaban：LinkedIn开源，工作流调度

### 2. 去中心化调度架构

**架构特点**
- 无中心调度节点，所有节点平等
- 每个节点都能调度任务，通过选举或共识避免冲突
- 典型实现：Quartz集群、Spring Scheduler集群

**优点**
- 无单点：所有节点平等，无中心瓶颈
- 高可用：任意节点故障，其他节点接管

**缺点**
- 配置复杂：需解决任务重复执行问题
- 一致性难：集群状态同步复杂

**典型实现**
- Quartz集群：数据库锁实现，避免重复调度
- Spring Scheduler集群：需配合分布式锁

### 3. 任务分片

**分片原理**
- 将任务拆分为多个子任务（分片）
- 不同节点执行不同分片
- 分片参数：总分片数、当前分片项

**分片策略**
- 平均分配：总分片数 / 节点数
- 自定义分配：根据业务规则分配（如按地区、按用户ID取模）

**优点**
- 并行处理：提高任务执行速度
- 处理大数据：单节点无法处理，分片后并行处理

**典型场景**
- 每天处理1亿条数据，分10片，每片处理1000万条
- 每个分片独立处理，最后汇总结果

### 4. 工作流调度

**工作流定义**
- 多个任务按依赖关系组成DAG（有向无环图）
- 支持顺序、并行、分支、条件判断

**调度策略**
- 依赖调度：前置任务成功，才调度后续任务
- 失败策略：失败停止、失败继续、失败重试

**典型实现**
- Azkaban：LinkedIn开源，支持工作流调度
- Airflow：Airbnb开源，Python定义工作流
- DolphinScheduler：中国开源，易用性强

## 示例/应用场景

### 示例1：电商每日数据对账（定时调度）
**场景**：电商系统每天凌晨2点对账，比对订单系统与支付系统数据

**方案设计**：
1. 调度中心：XXL-JOB调度中心，配置定时任务（Cron：0 0 2 * * ?）
2. 执行器：订单系统、支付系统分别部署执行器
3. 任务逻辑：
   - 步骤1：从订单系统导出昨日订单数据（分片：按订单ID取模，10个分片）
   - 步骤2：从支付系统导出昨日支付数据（分片：按支付ID取模，10个分片）
   - 步骤3：比对订单与支付数据，生成对账报告
   - 步骤4：对账异常数据，发送告警邮件
4. 监控：调度中心查看任务执行日志、执行结果

**关键考量**：
- 任务分片：大规模数据，分片并行处理
- 失败重试：网络故障导致导出失败，重试3次
- 监控告警：对账异常，发送告警邮件

### 示例2：缓存预热（周期性调度）
**场景**：电商首页缓存，每5分钟更新一次

**方案设计**：
1. 调度中心：Quartz集群，配置周期性任务（间隔5分钟）
2. 执行器：应用节点，每个节点都是执行器
3. 任务逻辑：
   - 查询数据库，获取首页商品数据
   - 更新Redis缓存
   - 记录执行日志
4. 避免重复：Quartz集群使用数据库锁，保证同一时间仅一个节点执行

**关键考量**：
- 避免重复：数据库锁或分布式锁
- 缓存更新策略：先更新数据库，再更新缓存；或先删缓存，再更新数据库
- 监控：缓存命中率、更新耗时

### 示例3：工作流调度（ETL流程）
**场景**：数据仓库ETL流程，每天凌晨执行

**方案设计**：
1. 调度系统：DolphinScheduler
2. 工作流定义：
   - 任务1：抽取订单数据（Sqoop）
   - 任务2：抽取用户数据（Sqoop）
   - 任务3：数据清洗（Spark）
   - 任务4：数据加载（Hive）
   - 任务5：数据质量检查（SQL）
   - 任务6：发送执行报告（邮件）
3. 依赖关系：任务1、2并行 → 任务3 → 任务4 → 任务5 → 任务6
4. 失败策略：任务3失败，停止后续任务，发送告警

**关键考量**：
- 依赖管理：DAG定义任务依赖
- 失败处理：失败停止或失败继续（根据业务）
- 监控：工作流执行状态、每个任务执行日志

## 【对应领域考点】

1. **分布式调度 vs. 单机调度**
   - 单机调度：Quartz、Spring Scheduler，无法扩展、单点故障
   - 分布式调度：XXL-JOB、Elastic-JOB，高可用、可扩展、统一管理

2. **如何避免任务重复执行**
   - 集中式调度：调度中心保证同一任务同一时间仅触发一次
   - 去中心化调度：数据库锁（Quartz）、分布式锁（Redis/ZooKeeper）

3. **任务分片的作用**
   - 并行处理：提高任务执行速度
   - 处理大数据：单节点无法处理，分片后并行处理
   - 典型场景：大规模数据对账、数据同步

4. **调度中心高可用**
   - 主备模式：主节点故障，备节点接管（XXL-JOB）
   - 集群模式：多个调度中心节点，选举Leader（Elastic-JOB）

5. **工作流调度 vs. 定时调度**
   - 定时调度：单个任务，按时间执行
   - 工作流调度：多个任务，按依赖关系执行

## 最佳实践

1. **合理选择调度框架**
   - 简单定时任务：Spring Scheduler、Quartz
   - 分布式调度：XXL-JOB（易用）、Elastic-JOB（分片）
   - 工作流调度：DolphinScheduler（易用）、Airflow（灵活）

2. **避免任务重复执行**
   - 集中式调度：使用成熟框架（XXL-JOB、Elastic-JOB）
   - 去中心化调度：使用数据库锁或分布式锁

3. **任务失败处理**
   - 失败重试：临时故障，重试3-5次
   - 失败告警：关键任务，发送告警邮件/短信
   - 失败转移：节点故障，转移到其他节点

4. **任务监控**
   - 监控指标：任务执行次数、成功率、失败次数、执行耗时
   - 告警：任务失败、执行超时、调度中心故障
   - 日志：任务执行日志、调度日志，方便排查问题

5. **任务分片策略**
   - 平均分片：简单、均匀
   - 自定义分片：根据业务规则（如按地区、按用户ID取模）
   - 分片数：根据数据量和节点数合理设置

## 【常见错误】

1. **错误：任务重复执行**
   - 现象：同一任务在同一时间被执行多次
   - 原因：无中心调度，多个节点同时触发
   - 解决：使用分布式锁或集中式调度框架

2. **错误：调度中心单点故障**
   - 现象：调度中心故障，所有任务无法执行
   - 原因：调度中心单机部署
   - 解决：调度中心集群部署，主备或选举

3. **错误：任务执行超时**
   - 现象：任务执行时间超过预期，影响后续任务
   - 原因：数据量增大、逻辑复杂、资源不足
   - 解决：任务分片、优化逻辑、增加超时时间

4. **错误：任务失败未告警**
   - 现象：任务失败，无人知晓，影响业务
   - 原因：未配置告警
   - 解决：配置失败告警（邮件、短信、钉钉）

5. **错误：工作流依赖死锁**
   - 现象：工作流任务互相等待，无法执行
   - 原因：依赖关系配置错误，形成环
   - 解决：检查DAG，确保无环

## 总结

分布式调度是分布式系统的重要组件，核心在于：
1. **调度类型**：定时调度、周期性调度、一次性调度、工作流调度
2. **调度策略**：轮询、负载均衡、故障转移、分片
3. **架构模式**：集中式（XXL-JOB）、去中心化（Quartz集群）
4. **核心机制**：任务分片、失败重试、高可用、避免重复执行
5. **典型框架**：XXL-JOB（易用）、Elastic-JOB（分片）、DolphinScheduler（工作流）

实际应用中，需根据任务类型、规模、依赖关系选择合适的调度框架和策略。
