# 分布式限流

## 定义

分布式限流是指在分布式系统中，对服务、接口或用户的请求频率进行限制的机制。它防止系统被突发流量冲垮，保证系统稳定性、可用性。

核心目标：
- **保护系统**：防止过载，保证可用性
- **公平使用**：防止单个用户/服务占用过多资源
- **流量控制**：平滑流量，避免突发
- **降级兜底**：限流作为降级手段

## 核心概念

### 1. 限流算法

**固定窗口计数（Fixed Window）**
- 在固定时间窗口内计数，超过阈值则限流
- 优点：简单
- 缺点：窗口边界突发流量（两个窗口各放一半）
- 适用：简单场景

**滑动窗口计数（Sliding Window）**
- 滑动时间窗口内计数，超过阈值则限流
- 优点：比固定窗口平滑
- 缺点：实现复杂，需记录每个请求时间
- 适用：需要较平滑限流的场景

**漏桶算法（Leaky Bucket）**
- 请求进桶，桶以固定速率漏水（处理请求）
- 优点：流量平滑，输出速率固定
- 缺点：无法应对突发流量（即使系统有空闲）
- 适用：需要严格限制输出速率的场景

**令牌桶算法（Token Bucket）**
- 令牌以固定速率放入桶，请求需拿令牌才能通过
- 优点：允许突发流量（桶内令牌可一次拿完）
- 缺点：实现较复杂
- 适用：大多数场景（主流方案）

**滑动日志（Sliding Log）**
- 记录每个请求时间戳，统计窗口内请求数
- 优点：精确
- 缺点：内存占用大
- 适用：精确限流场景

### 2. 限流粒度

**接口级限流**
- 对单个接口限流
- 典型：每秒最多100次调用
- 适用：保护关键接口

**用户级限流**
- 对单个用户限流
- 典型：单个用户每秒最多10次调用
- 适用：防止单个用户刷接口

**应用级限流**
- 对整个应用限流
- 典型：整个应用每秒最多1000次调用
- 适用：保护整个应用

**集群级限流**
- 对整个集群限流
- 典型：整个集群每秒最多10000次调用
- 适用：保护整个集群

### 3. 限流架构

**单机限流**
- 限流逻辑在单机上，不共享状态
- 优点：简单、无网络开销
- 缺点：集群环境下，每个节点单独限流，总流量 = 单节点阈值 × 节点数
- 适用：单机应用、或集群环境下允许超额

**分布式限流**
- 限流状态集中存储（如Redis），所有节点共享
- 优点：集群环境下精确限流
- 缺点：依赖集中存储、网络开销
- 适用：集群环境、需精确限流

**多级限流**
- 多级限流组合（如：接入层限流 + 服务层限流）
- 优点：多层防护
- 缺点：配置复杂
- 适用：大型系统

### 4. 限流策略

**拒绝策略**
- 超过阈值，直接拒绝请求
- 适用：保护系统，快速失败

**排队策略**
- 超过阈值，请求排队等待
- 适用：允许延迟的场景

**降级策略**
- 超过阈值，返回降级结果（如默认数据、缓存数据）
- 适用：保证基本可用

**熔断策略**
- 超过阈值，直接熔断，一段时间后才允许重试
- 适用：防止雪崩

## 详细内容

### 1. 基于Redis的分布式限流

**令牌桶实现**
- 使用Redis + Lua脚本原子操作
- Key：限流维度（如接口、用户）
- Value：令牌数量
- Lua脚本：
  1. 计算时间差，补充令牌
  2. 判断令牌是否足够
  3. 足够则减去令牌，返回成功；否则返回失败

**滑动窗口实现**
- 使用Redis ZSet（有序集合）
- Key：限流维度
- Score：请求时间戳
- Value：请求唯一ID
- 逻辑：
  1. 移除窗口外的请求（ZRemRangeByScore）
  2. 统计窗口内请求数（ZCard）
  3. 超过阈值则限流，否则添加当前请求（ZAdd）

**优点**
- 分布式环境下精确限流
- 高性能（Redis内存操作）
- 灵活（支持多种限流算法）

**缺点**
- 依赖Redis，Redis故障影响限流
- 网络开销（每次请求需访问Redis）
- Lua脚本调试复杂

### 2. 基于Sentinel的限流

**架构**
- Sentinel Core：限流逻辑
- Sentinel Dashboard：管理控制台
- 支持：QPS限流、线程数限流、熔断降级

**核心机制**
- 滑动窗口：统计QPS
- 令牌桶：控制流速
- 熔断：根据响应时间、异常比例熔断

**优点**
- 功能丰富（限流、熔断、降级）
- 与Spring Cloud集成好
- 阿里开源，经历双11考验

**缺点**
- 依赖Sentinel Dashboard
- 配置复杂

### 3. 基于Nginx的限流

**模块**
- ngx_http_limit_req_module：限制请求频率
- ngx_http_limit_conn_module：限制并发连接数

**配置示例**
```nginx
# 限制每个IP每秒最多10次请求
limit_req_zone $binary_remote_addr zone=one:10m rate=10r/s;
limit_req zone=one burst=20 nodelay;
```

**优点**
- 接入层限流，保护后端
- 性能好（Nginx高性能）
- 配置简单

**缺点**
- 功能不如Sentinel丰富
- 仅限Nginx接入层

### 4. 基于Gateway的限流

**Spring Cloud Gateway + Redis**
- 使用Redis + Lua脚本实现分布式限流
- 配置：KeyResolver（限流维度）、ReplenishRate（令牌生成速率）、BurstCapacity（令牌桶容量）

**优点**
- 与Spring Cloud集成好
- 分布式限流
- 灵活配置

**缺点**
- 依赖Redis
- 仅限Gateway层

## 示例/应用场景

### 示例1：API接口限流（防止刷接口）
**场景**：公开API接口，需防止被刷

**方案设计**：
1. 限流维度：每个API Key每秒最多100次调用
2. 限流算法：令牌桶
3. 实现：Redis + Lua脚本
4. 配置：
   - 令牌生成速率：100个/秒
   - 令牌桶容量：200个（允许突发200个请求）
5. 限流响应：返回429 Too Many Requests

**关键考量**：
- 限流维度：API Key、IP、用户ID，根据场景选择
- 令牌桶容量：根据系统能力设置
- 限流响应：明确错误码和错误信息

### 示例2：用户操作限流（防止恶意操作）
**场景**：用户发送验证码、登录等操作，需防止恶意刷

**方案设计**：
1. 限流维度：每个用户每分钟最多5次发送验证码
2. 限流算法：固定窗口
3. 实现：Redis计数
4. 配置：
   - 时间窗口：1分钟
   - 最大请求数：5次
5. 限流响应：提示"操作过于频繁，请稍后再试"

**关键考量**：
- 限流粒度：用户级、IP级，根据场景选择
- 时间窗口：根据业务设置（如1分钟、5分钟）
- 用户体验：限流后明确提示，避免用户困惑

### 示例3：秒杀限流（保护系统）
**场景**：电商秒杀活动，瞬时流量极大

**方案设计**：
1. 多级限流：
   - 第一级：Nginx限流（限制每个IP每秒最多10次请求）
   - 第二级：Gateway限流（限制整个集群每秒最多10000次请求）
   - 第三级：秒杀服务限流（限制每秒最多1000次下单）
2. 限流算法：令牌桶
3. 实现：
   - Nginx：ngx_http_limit_req_module
   - Gateway：Redis + Lua
   - 秒杀服务：Sentinel
4. 限流响应：
   - Nginx：返回503 Service Unavailable
   - Gateway：返回"秒杀已结束"
   - 秒杀服务：返回"秒杀队列已满，请稍后再试"

**关键考量**：
- 多级限流：多层防护，避免单点失效
- 限流阈值：根据系统能力设置，逐步限流
- 用户体验：前端友好提示，引导用户

## 【对应领域考点】

1. **限流算法对比**
   - 固定窗口：简单，边界突发
   - 滑动窗口：平滑，复杂
   - 漏桶：输出速率固定，无法突发
   - 令牌桶：允许突发，主流方案

2. **分布式限流 vs. 单机限流**
   - 单机限流：简单，集群环境不精确
   - 分布式限流：精确，依赖集中存储

3. **Redis + Lua实现分布式限流**
   - 原子性：Lua脚本保证原子操作
   - 性能：Redis内存操作，高性能
   - 灵活：支持多种限流算法

4. **Sentinel的功能**
   - 限流：QPS、线程数
   - 熔断：响应时间、异常比例
   - 降级：返回降级结果

5. **限流粒度选择**
   - 接口级：保护关键接口
   - 用户级：防止单个用户刷接口
   - 应用级：保护整个应用
   - 集群级：保护整个集群

## 最佳实践

1. **合理选择限流算法**
   - 大多数场景：令牌桶（允许突发）
   - 严格限制输出速率：漏桶
   - 简单场景：固定窗口

2. **合理设置限流阈值**
   - 压测：通过压测确定系统能力
   - 逐步调整：根据线上实际情况调整
   - 留有余地：限流阈值 < 系统最大能力

3. **多级限流**
   - 接入层限流：Nginx、Gateway
   - 服务层限流：Sentinel、Hystrix
   - 多层防护，避免单点失效

4. **限流响应友好**
   - 明确错误码：429 Too Many Requests
   - 明确错误信息："操作过于频繁，请稍后再试"
   - 前端引导：提示用户稍后重试

5. **监控和告警**
   - 监控指标：限流次数、限流率
   - 告警：限流次数异常增高
   - 分析：限流原因（正常流量激增 or 被攻击）

## 【常见错误】

1. **错误：限流阈值设置不合理**
   - 现象：系统被冲垮，或限流过于严格
   - 原因：未压测，凭感觉设置
   - 解决：压测确定系统能力，逐步调整

2. **错误：分布式限流依赖单机**
   - 现象：集群环境下，总流量超标
   - 原因：使用单机限流，每个节点单独限流
   - 解决：使用分布式限流（Redis + Lua）

3. **错误：限流后未友好响应**
   - 现象：用户不知道为什么请求失败
   - 原因：仅返回错误码，无错误信息
   - 解决：返回明确错误信息，前端友好提示

4. **错误：限流算法选择不当**
   - 现象：流量不平滑，或无法应对突发
   - 原因：算法选择不符合场景
   - 解决：根据场景选择（大多数场景用令牌桶）

5. **错误：未监控限流情况**
   - 现象：限流异常，未及时发现
   - 原因：未监控限流指标
   - 解决：监控限流次数、限流率，配置告警

## 总结

分布式限流是分布式系统保护的重要手段，核心在于：
1. **限流算法**：令牌桶（主流）、漏桶、滑动窗口、固定窗口
2. **限流粒度**：接口级、用户级、应用级、集群级
3. **限流架构**：单机限流（简单）、分布式限流（精确）、多级限流（多层防护）
4. **实现方式**：Redis + Lua（主流）、Sentinel（功能丰富）、Nginx（接入层）
5. **限流策略**：拒绝、排队、降级、熔断

实际应用中，需根据场景（接口保护、用户限流、秒杀）选择合适的限流算法、粒度和实现方式。
