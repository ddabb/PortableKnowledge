# 云原生可观测性

## 定义

可观测性（Observability）是通过系统**外部输出数据**（指标、日志、追踪）理解系统内部状态的能力。云原生可观测性是**监控、日志、分布式追踪**的三位一体。

**三大支柱**：
- **Metrics（指标）**：数值型时间序列数据，反映系统状态
- **Logs（日志）**：结构化/非结构化文本记录，记录事件
- **Traces（追踪）**：请求在全链路的调用关系，定位性能瓶颈

**核心价值**：
- 快速故障定位（MTTR降低）
- 性能优化依据（找到慢查询、热点路径）
- 容量规划基础（资源使用趋势）
- 安全审计线索（访问日志、审计日志）

## 核心概念

### 1. 指标（Metrics）
- **定义**：数值型时间序列数据，用于监控系统状态
- **关键指标类型**：Counter（计数器）、Gauge（仪表盘）、Histogram（直方图）、Summary（摘要）
- **代表技术**：Prometheus、Victoria Metrics、M3DB

### 2. 日志（Logs）
- **定义**：结构化/非结构化文本记录，记录系统事件
- **日志级别**：DEBUG、INFO、WARN、ERROR、FATAL
- **代表技术**：ELK（Elasticsearch + Logstash + Kibana）、EFK（Elasticsearch + Fluentd + Kibana）、Loki

### 3. 分布式追踪（Distributed Tracing）
- **定义**：记录请求在分布式系统中的调用链
- **关键概念**：Trace（追踪）、Span（跨度）、SpanContext（跨度上下文）
- **代表技术**：Jaeger、Zipkin、SkyWalking

### 4. 可观测性标准
- **OpenTelemetry**：统一指标、日志、追踪的数据模型和采集API
- **OpenMetrics**：Prometheus指标格式标准
- **OpenTracing**：分布式追踪API标准（已合并到OpenTelemetry）

## 详细内容

### Prometheus架构与原理

#### 架构组件
```
Prometheus Server:
  - Retrieval (采集)
  - TSDB (时序数据库)
  - HTTP Server (查询API)
       ↓
   Service Discovery (服务发现)
       ↓
   Targets (Exporters/应用/服务)
```

**核心组件**：
- **Prometheus Server**：主服务，负责采集、存储、查询
- **Exporter**：暴露指标给Prometheus（Node Exporter、MySQL Exporter）
- **Pushgateway**：短生命周期任务推送指标
- **Alertmanager**：告警管理（去重、分组、路由）
- **Service Discovery**：自动发现采集目标（Kubernetes、Consul）

#### 数据采集模型
- **Pull模型**：Prometheus主动拉取目标指标
- **优势**：集中控制、目标健康检查
- **劣势**：目标数量大时压力大
- **解决方案**：分片（Sharding）、联邦（Federation）

#### PromQL查询语言
**核心概念**：
- **瞬时向量（Instant Vector）**：最近一个时间点的指标值
- **范围向量（Range Vector）**：一段时间内的指标值
- **标量（Scalar）**：数字常量

**常用函数**：
- `rate()`：计算计数器每秒增长率（最常用）
- `increase()`：计算计数器在一段时间内的增量
- `histogram_quantile()`：计算直方图的分位数（P50、P90、P99）
- `up`：目标是否可达（1=可达，0=不可达）

### 日志收集架构

#### ELK/EFK栈
```
应用容器 → Fluentd/Fluent Bit → Elasticsearch → Kibana
                  ↓
              Kafka (可选，缓冲)
```

**组件说明**：
- **Fluentd/Fluent Bit**：日志收集器（Fluent Bit更轻量，适合边缘）
- **Elasticsearch**：日志存储和搜索引擎
- **Kibana**：日志可视化Dashboard
- **Kafka**：日志缓冲队列（高吞吐场景）

#### Loki架构
```
应用容器 → Promtail → Loki → Grafana
```

**优势**：
- **轻量级**：不索引日志全文，仅索引元数据（标签）
- **与Prometheus集成**：同一Grafana查看指标和日志
- **成本更低**：存储成本仅为Elasticsearch的1/10

#### 日志最佳实践
- **结构化日志**：JSON格式，便于查询（`{"level":"ERROR","msg":"DB connection failed","ts":"2026-06-03T15:22:00Z"}`）
- **日志轮转**：防止磁盘占满（logrotate）
- **日志级别控制**：生产环境INFO，排查时DEBUG
- **敏感信息脱敏**：密码、Token不记录到日志

### 分布式追踪原理

#### 追踪模型
```
Trace (整个请求):
  Span1 (API Gateway) → Span2 (用户服务) → Span3 (订单服务)
       ↓                       ↓                    ↓
   Span1.1 (认证)      Span2.1 (DB查询)      Span3.1 (支付)
```

**关键概念**：
- **TraceID**：整个请求的唯一标识
- **SpanID**：单个操作的唯一标识
- **ParentSpanID**：父操作的SpanID（构建调用链）
- **Baggage**：跨服务传递的上下文信息

#### OpenTelemetry架构
```
应用代码 → OTel SDK → OTel Collector → 后端 (Jaeger/Zipkin/Prometheus)
```

**核心组件**：
- **API**：定义指标、日志、追踪的接口
- **SDK**：API的实现（多语言支持）
- **Collector**：接收、处理、导出遥测数据（支持多种后端）

#### 采样策略
- **固定采样（Constant Sampling）**：采样所有请求或都不采样
- **概率采样（Probabilistic Sampling）**：按固定概率采样（如1%）
- **限流采样（Rate Limiting Sampling）**：限制每秒采样数
- **动态采样（Dynamic Sampling）**：根据请求属性（错误、延迟）动态调整采样率

## 示例/应用场景

### 场景1：Kubernetes集群监控
**需求**：监控集群节点、Pod、容器资源使用率

**方案**：
1. **Node Exporter**：收集节点指标（CPU、内存、磁盘、网络）
2. **Kube-state-metrics**：收集Kubernetes对象状态（Deployment副本数、Pod状态）
3. **cAdvisor**：收集容器资源使用率（集成在Kubelet中）
4. **Prometheus**：采集所有指标
5. **Grafana**：可视化Dashboard（Node Exporter Dashboard、Kubernetes Cluster Monitoring）

**关键告警规则**：
- 节点CPU使用率 > 80%（持续5分钟）
- Pod内存使用率 > 90%
- 容器重启次数 > 3次/小时

### 场景2：微服务故障排查
**需求**：用户投诉订单服务慢，需定位瓶颈

**方案**：
1. **分布式追踪**：Jaeger UI查看Trace，发现支付服务耗时最长
2. **日志关联**：通过TraceID查询支付服务日志，发现DB连接池耗尽错误
3. **指标确认**：Prometheus查看支付服务DB连接池指标（`db_connection_pool_active`高）
4. **根因定位**：DB连接池配置过小，调整连接池大小后恢复正常

### 场景3：AI推理服务监控（对应岗位要求）
**需求**：监控LLM推理服务性能，优化推理延迟

**方案**：
1. **指标监控**：
   - 推理QPS（`inference_qps`）
   - 推理延迟P99（`inference_latency_p99`）
   - GPU利用率（`gpu_utilization`）
   - 显存使用率（`gpu_memory_usage`）
2. **日志收集**：推理请求日志（Prompt长度、生成Token数、耗时）
3. **追踪**：推理请求全链路（API Gateway → 推理服务 → 模型加载）
4. **告警**：推理延迟P99 > 5秒告警，GPU显存使用率 > 90%告警

## 最佳实践

### 1. 指标设计
- **使用标签（Labels）**：按维度拆分指标（`http_requests_total{method="POST",status="200"}`）
- **避免高基数标签**：如user_id作为标签会导致指标爆炸
- **RED方法**：Rate（请求速率）、Errors（错误率）、Duration（延迟）
- **USE方法**：Utilization（利用率）、Saturation（饱和度）、Errors（错误）

### 2. 日志管理
- **结构化日志**：JSON格式，便于查询和告警
- **日志级别规范**：生产环境INFO，排查时DEBUG
- **日志轮转**：防止磁盘占满（logrotate配置）
- **敏感信息脱敏**：密码、Token不记录

### 3. 追踪实施
- **低采样率**：生产环境1-5%采样率，避免性能影响
- **关键路径追踪**：仅追踪关键业务路径（下单、支付）
- **TraceID传递**：通过HTTP Header、gRPC Metadata传递TraceID

### 4. 告警配置
- **分级告警**：P0（紧急）、P1（重要）、P2（警告）
- **告警收敛**：相同告警5分钟内仅发送一次
- **告警闭环**：告警 → 工单 → 修复 → 验证

### 5. 成本控制
- **指标保留策略**：高频指标保留7天，低频指标保留30天
- **日志压缩存储**：使用Loki替代ELK，成本降低90%
- **追踪采样**：动态调整采样率，仅采样慢请求和错误请求

## 【常见错误】

### 错误1：高基数标签导致Prometheus崩溃
**表现**：使用user_id、session_id作为Prometheus标签
**后果**：指标数量爆炸，Prometheus内存耗尽
**正确做法**：高基数数据记录到日志，Prometheus仅使用低基数标签

### 错误2：日志未结构化
**表现**：日志格式不统一，关键字随意
**后果**：无法高效查询和告警
**正确做法**：统一JSON格式，包含timestamp、level、message、trace_id

### 错误3：追踪采样率过高
**表现**：生产环境100%采样
**后果**：性能影响大，存储成本高
**正确做法**：生产环境1-5%采样率，仅采样慢请求和错误请求

### 错误4：告警规则过于敏感
**表现**：CPU使用率超50%就告警
**后果**：告警风暴，运维人员麻木
**正确做法**：基于历史数据设置合理阈值（如P99延迟超阈值）

### 错误5：可观测性数据未关联
**表现**：指标、日志、追踪数据孤立
**后果**：故障排查效率低
**正确做法**：通过TraceID、SpanID关联指标、日志、追踪

## 总结

云原生可观测性是**系统稳定运行的眼睛**，三大支柱（指标、日志、追踪）缺一不可。

**关键要点**：
1. **指标监控**：Prometheus + Grafana，RED/USE方法
2. **日志收集**：ELK/EFK/Loki，结构化日志
3. **分布式追踪**：Jaeger/Zipkin，OpenTelemetry标准
4. **告警体系**：分级告警、告警收敛、告警闭环
5. **成本控制**：合理保留策略、采样率调整

**学习路径**：
1. 掌握Prometheus和PromQL
2. 实践日志收集（EFK/Loki）
3. 部署分布式追踪（Jaeger）
4. 学习OpenTelemetry标准
5. 建设可观测性体系（指标+日志+追踪关联）

可观测性不是附属品，而是云原生系统的**必需品**。
