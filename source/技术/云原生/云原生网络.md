# 云原生网络

## 定义

云原生网络是**为容器化应用设计的网络架构**，需满足Pod动态IP、服务发现、跨主机通信、网络策略等云原生特性。

**核心挑战**：
- **动态性**：Pod频繁创建销毁，IP动态变化
- **扁平网络**：所有Pod在同一平面网络，可直接通信
- **服务抽象**：Service屏蔽后端Pod变化
- **网络隔离**：NetworkPolicy控制流量

**核心价值**：
- 透明服务发现
- 跨主机容器通信
- 网络策略安全隔离
- 高性能网络转发

## 核心概念

### 1. CNI（Container Network Interface）
- **定义**：容器网络标准接口，Kubernetes调用CNI插件配置Pod网络
- **工作流程**：创建Pod → 调用CNI插件分配IP → 配置veth pair → 配置路由/桥接
- **主流插件**：Flannel、Calico、Weave Net、Cilium

### 2. Pod网络模型
- **扁平网络**：所有Pod在同一IP空间，无需NAT直接通信
- **IP-per-Pod**：每个Pod独立IP，容器共享Pod网络命名空间
- **跨主机通信**：Overlay网络（封装）或路由模式（BGP）

### 3. Service抽象
- **定义**：为一组Pod提供稳定网络访问入口
- **实现机制**：Label Selector匹配Pod，kube-proxy配置转发规则
- **服务发现**：DNS解析Service名称到ClusterIP

### 4. Ingress
- **定义**：HTTP/HTTPS路由规则，七层负载均衡
- **核心价值**：统一入口，SSL终止，路径/域名路由
- **实现**：Ingress Controller（Nginx、Traefik、HAProxy）

### 5. NetworkPolicy
- **定义**：Pod级防火墙规则，控制入站/出站流量
- **核心价值**：零信任网络，最小权限访问控制
- **实现**：依赖CNI插件支持（Calico、Cilium）

## 详细内容

### CNI插件对比

| CNI插件 | 网络模式 | 性能 | 网络策略 | 适用场景 |
|---------|---------|------|---------|---------|
| Flannel | Overlay(VXLAN) | 中 | ❌ | 简单集群、快速部署 |
| Calico | BGP路由 | 高 | ✅ | 生产环境、大规模集群 |
| Weave Net | Overlay | 中 | ✅ | 简单部署、中小规模 |
| Cilium | eBPF | 极高 | ✅ | 高性能、安全敏感 |

#### Flannel
**原理**：
- 使用Overlay网络（VXLAN或host-gw）
- VXLAN：封装二层帧到UDP包，跨主机通信
- host-gw：通过路由表直接转发，性能更优（需二层可达）

**优势**：简单易部署
**劣势**：不支持NetworkPolicy，Overlay有性能损耗

#### Calico
**原理**：
- 使用BGP协议分发路由
- 每个节点作为BGP Speaker，通告Pod网段
- 支持IPIP模式（跨子网Overlay）

**优势**：高性能（无Overlay）、支持NetworkPolicy、大规模集群
**劣势**：配置相对复杂

#### Cilium
**原理**：
- 基于eBPF技术，内核级数据转发
- 支持L7策略（HTTP/gRPC路由）
- 服务网格集成（Cilium Service Mesh）

**优势**：极致性能、L7策略、服务网格能力
**劣势**：内核版本要求高（≥4.19）

### Service实现机制

#### kube-proxy三种模式

**1. userspace模式**（已废弃）
- kube-proxy监听Service和Endpoints变化
- 每个服务开启代理端口，流量转发到后端Pod
- **问题**：用户空间到内核空间频繁切换，性能差

**2. iptables模式**（默认）
- kube-proxy监听Service和Endpoints变化，写入iptables规则
- 流量到达Service ClusterIP后，iptables随机选择一个Pod转发
- **优势**：性能好，无需用户空间代理
- **劣势**：规则多时性能下降，负载均衡算法简单（随机）

**3. IPVS模式**（推荐）
- kube-proxy监听Service和Endpoints变化，写入IPVS规则
- 支持多种负载均衡算法（轮询、最少连接、哈希等）
- **优势**：规则数量不影响性能，支持高级负载均衡算法
- **劣势**：需要内核支持IPVS模块

#### Service DNS解析
**CoreDNS工作流程**：
1. Pod内DNS配置指向CoreDNS Service IP（/etc/resolv.conf）
2. 应用解析Service名称（如my-svc.my-namespace.svc.cluster.local）
3. CoreDNS返回Service ClusterIP
4. 应用访问ClusterIP，kube-proxy转发到后端Pod

### Ingress详解

#### Ingress资源示例
```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: example-ingress
spec:
  tls:
  - hosts:
    - example.com
    secretName: example-tls
  rules:
  - host: example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: web-service
            port:
              number: 80
```

#### Ingress Controller对比

| Ingress Controller | 性能 | 功能 | 配置复杂度 |
|-------------------|------|------|-----------|
| Nginx Ingress | 高 | 丰富 | 中 |
| Traefik | 高 | 自动化 | 低 |
| HAProxy Ingress | 极高 | 丰富 | 高 |
| Istio Ingress Gateway | 中 | 服务网格集成 | 高 |

### NetworkPolicy详解

#### 策略模型
**默认行为**：
- 无NetworkPolicy：Pod接受所有流量
- 有NetworkPolicy：仅允许策略允许的流量

**策略类型**：
- **Ingress**：控制入站流量
- **Egress**：控制出站流量（1.8+）

#### 示例策略
```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-frontend
spec:
  podSelector:
    matchLabels:
      app: backend
  ingress:
  - from:
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080
```

**含义**：仅允许带`app: frontend`标签的Pod访问带`app: backend`标签的Pod的8080端口

## 示例/应用场景

### 场景1：微服务间通信
**需求**：前端服务访问后端服务，需服务发现和负载均衡

**方案**：
- 后端Deployment + Service（ClusterIP）
- 前端Pod通过Service DNS名称访问（`http://backend-svc:8080`）
- kube-proxy（IPVS模式）负责负载均衡到后端Pod

### 场景2：外部访问集群服务
**需求**：用户通过域名访问Web服务

**方案**：
- Web Deployment + Service（ClusterIP）
- Ingress资源定义路由规则（`host: example.com, path: /`）
- Ingress Controller（Nginx）监听Ingress资源，配置Nginx反向代理
- DNS解析example.com到Ingress Controller Service LoadBalancer IP

### 场景3：零信任网络安全
**需求**：仅允许前端访问后端，数据库仅允许后端访问

**方案**：
- 创建NetworkPolicy：
  - 后端Pod：仅允许前端Pod访问
  - 数据库Pod：仅允许后端Pod访问
- 使用Calico或Cilium CNI插件（支持NetworkPolicy）
- 默认拒绝所有流量，仅开放必要端口

## 【对应领域考点】

1. **CNI工作流程**：创建Pod时调用CNI插件分配IP、配置veth pair
2. **Service实现机制**：kube-proxy iptables/IPVS模式，转发规则
3. **DNS解析流程**：CoreDNS配置，Service DNS记录格式
4. **Ingress vs LoadBalancer**：Ingress七层路由，LoadBalancer四层负载均衡
5. **NetworkPolicy实现**：依赖CNI插件，策略匹配规则
6. **Overlay网络原理**：VXLAN封装，性能损耗点
7. **BGP路由原理**：Calico分发路由，避免Overlay
8. **eBPF优势**：内核级数据转发，避免用户空间/内核空间切换

## 最佳实践

### 1. CNI插件选型
- **小规模集群**：Flannel（简单快速）
- **生产环境**：Calico（高性能+NetworkPolicy）
- **性能敏感**：Cilium（eBPF极致性能）
- **混合云**：Calico（支持IPIP跨子网）

### 2. Service配置
- **使用IPVS模式**：`kube-proxy --mode=ipvs`
- **避免ClusterIP段冲突**：规划好Service CIDR（如10.96.0.0/12）
- **DNS配置优化**：CoreDNS副本数≥2，配置HPA自动扩缩容

### 3. Ingress配置
- **启用SSL终止**：TLS证书通过Secret挂载
- **配置健康检查**：`readinessProbe`确保后端Pod就绪
- **限流防护**：配置Nginx限流模块（`limit-req-zone`）

### 4. NetworkPolicy配置
- **默认拒绝**：先创建拒绝所有流量的NetworkPolicy，再按需开放
- **按需开放**：仅开放必要端口和来源
- **标签管理**：使用统一标签策略（app、tier、env）

### 5. 性能优化
- **使用IPVS**：避免iptables规则过多性能下降
- **Calico BGP模式**：避免Overlay性能损耗
- **Cilium eBPF**：内核级转发，性能极致

## 【常见错误】

### 错误1：CNI插件选择不当
**表现**：大规模集群使用Flannel
**后果**：无法支持NetworkPolicy，性能瓶颈
**正确做法**：生产环境使用Calico或Cilium

### 错误2：Service CIDR与Pod CIDR冲突
**表现**：Service ClusterIP与Pod IP在同一网段
**后果**：路由冲突，服务不可达
**正确做法**：规划好Service CIDR和Pod CIDR，避免重叠

### 错误3：忽视Ingress Controller高可用
**表现**：单副本Ingress Controller
**后果**：Ingress Controller故障导致外部流量无法接入
**正确做法**：Ingress Controller副本数≥2，配置反亲和性

### 错误4：NetworkPolicy配置过于宽松
**表现**：使用过于宽泛的标签选择器
**后果**：安全风险，未授权访问
**正确做法**：最小权限原则，精确匹配标签

### 错误5：DNS配置不当
**表现**：CoreDNS副本数过少，未配置HPA
**后果**：DNS解析超时，服务发现失败
**正确做法**：CoreDNS副本数≥2，配置HPA，监控DNS解析延迟

## 总结

云原生网络是**容器编排的神经系统**，需平衡性能、安全、可维护性。

**关键要点**：
1. **CNI标准**：插件化架构，Flannel/Calico/Cilium各有适用场景
2. **Service抽象**：屏蔽后端Pod变化，DNS服务发现
3. **Ingress路由**：七层负载均衡，统一入口管理
4. **NetworkPolicy**：零信任网络，最小权限访问控制
5. **性能优化**：IPVS模式、BGP路由、eBPF技术

**学习路径**：
1. 理解Pod网络模型和CNI工作机制
2. 掌握Service实现机制（iptables/IPVS）
3. 实践Ingress路由配置
4. 配置NetworkPolicy安全策略
5. 深入CNI插件原理（Overlay、BGP、eBPF）

云原生网络复杂度高，但掌握后能为容器化应用提供坚实网络基础。
