# 服务网格

## 定义

服务网格（Service Mesh）是**专门处理服务间通信的基础设施层**，负责服务发现、负载均衡、故障恢复、监控、安全等跨领域关注点。

**核心思想**：将服务通信逻辑从业务代码中剥离，下沉到Sidecar代理中，实现**透明通信治理**。

**核心价值**：
- **解耦**：业务逻辑与通信逻辑分离
- **透明**：对业务代码无侵入
- **统一**：统一治理所有微服务通信
- **可观测**：自动收集metrics、logs、traces

## 核心概念

### 1. 架构模式
**控制平面（Control Plane）**：
- **职责**：管理配置、策略、证书
- **功能**：服务发现、负载均衡策略、安全策略、证书管理
- **代表产品**：Istio（Pilot + Citadel + Galley）、Linkerd（controller）

**数据平面（Data Plane）**：
- **职责**：处理实际的服务间流量
- **实现**：Sidecar代理（Envoy、Linkerd-proxy）
- **功能**：流量转发、负载均衡、重试、熔断、监控

### 2. 核心功能
**流量管理**：
- 路由规则（Virtual Service）
- 目的地规则（Destination Rule）
- 故障注入（Fault Injection）
- 超时/重试（Timeout/Retry）
- 熔断（Circuit Breaker）

**安全**：
- mTLS（双向TLS认证）
- 证书管理（Cert Manager）
- 授权策略（Authorization Policy）
- 认证策略（Authentication Policy）

**可观测性**：
- 指标（Metrics）：QPS、延迟、错误率
- 日志（Logs）：访问日志、审计日志
- 分布式追踪（Distributed Tracing）：调用链追踪

### 3. 关键抽象
**Istio核心CRD**：
- **VirtualService**：定义路由规则
- **DestinationRule**：定义流量策略（负载均衡、熔断器）
- **Gateway**：定义入口流量（替代Kubernetes Ingress）
- **ServiceEntry**：注册外部服务到网格
- **PeerAuthentication**：mTLS配置
- **AuthorizationPolicy**：访问控制

## 详细内容

### 服务网格工作原理

```
业务Pod:
  +------------------+
  |  业务容器        |
  |  (Spring Boot)   |
  +--------+---------+
           |
           | 127.0.0.1:8080
           ↓
  +--------+---------+
  | Sidecar代理     |
  | (Envoy)         |
  +--------+---------+
           |
           | 出站流量 → 其他Pod的Sidecar → 目标业务容器
           ↓
  +--------+---------+
  |  控制平面        |
  | (Istio Pilot)    |
  +------------------+
```

**流量流向**：
1. 业务容器发起请求 → 127.0.0.1:8080（Sidecar）
2. Sidecar检查路由规则（VirtualService）
3. Sidecar选择目标实例（DestinationRule负载均衡）
4. Sidecar将请求转发到目标Pod的Sidecar
5. 目标Pod的Sidecar转发到业务容器

### 流量管理详解

#### 路由规则（VirtualService）
**核心功能**：
- **基于权重的路由**：灰度发布、A/B测试
- **基于请求内容的路由**：Canary发布、用户标签路由
- **超时/重试**：提高服务可用性
- **故障注入**：测试系统容错能力

**示例场景**：
- 将90%流量路由到v1，10%路由到v2（灰度发布）
- 将Header包含"user-type: vip"的请求路由到vip服务
- 超时3秒，重试3次（提高可用性）

#### 目的地规则（DestinationRule）
**核心功能**：
- **负载均衡策略**：ROUND_ROBIN、LEAST_CONN、RANDOM
- **连接池设置**：最大连接数、最大请求数
- **熔断器**：连续错误阈值、基线Ejection时间
- **TLS设置**：模式（DISABLE、SIMPLE、MUTUAL）

### 安全机制详解

#### mTLS（双向TLS认证）
**目标**：服务间通信加密，防止中间人攻击

**工作流程**：
1. 控制平面（Citadel）为每个服务颁发证书
2. Sidecar之间建立TLS连接时使用证书认证
3. 通信数据加密传输

**模式**：
- **PERMISSIVE**：同时接受明文和TLS流量（迁移过渡）
- **STRICT**：仅接受TLS流量（生产环境）

#### 授权策略（AuthorizationPolicy）
**核心功能**：
- **基于属性的访问控制**（ABAC）
- **允许/拒绝规则**
- **条件匹配**：源IP、请求头、路径、方法

### 可观测性详解

#### 指标（Metrics）
**关键指标**：
- **请求量（Request Volume）**：QPS、RPS
- **延迟（Latency）**：P50、P90、P99、平均延迟
- **错误率（Error Rate）**：4xx、5xx比例
- **饱和度（Saturation）**：资源使用率

**收集方式**：
- Sidecar自动上报指标到Prometheus
- 通过Grafana可视化

#### 分布式追踪（Distributed Tracing）
**核心原理**：
- 请求入口处生成TraceID
- 每个服务处理时传递TraceID
- Sidecar自动上报Span到Jaeger/Zipkin

**价值**：
- 定位性能瓶颈（哪个服务慢）
- 理解调用链（服务依赖关系）
- 故障排查（哪个服务出错）

## 示例/应用场景

### 场景1：灰度发布
**需求**：新版本v2逐步放量，先10%流量，观察无异常后全量

**Istio方案**：
```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: my-service
spec:
  hosts:
  - my-service
  http:
  - route:
    - destination:
        host: my-service
        subset: v1
      weight: 90
    - destination:
        host: my-service
        subset: v2
      weight: 10
```

**优势**：
- 无需修改业务代码
- 可实时调整流量比例
- 结合监控快速回滚

### 场景2：熔断保护
**需求**：防止下游服务故障时上游服务被拖垮

**Istio方案**：
```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: my-service
spec:
  host: my-service
  trafficPolicy:
    outlierDetection:
      consecutive5xxErrors: 5  # 连续5次5xx错误
      interval: 30s             # 检查间隔
      baseEjectionTime: 30s     # 熔断时间
      maxEjectionPercent: 50    # 最多熔断50%实例
```

**优势**：
- 自动熔断故障实例
- 保护系统整体可用性
- 可配置熔断阈值

### 场景3：服务安全加固
**需求**：服务间通信加密，防止中间人攻击

**Istio方案**：
```yaml
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: default
spec:
  mtls:
    mode: STRICT  # 强制mTLS
```

**优势**：
- 零信任网络（Zero Trust）
- 自动证书轮换
- 对业务透明

## 【对应领域考点】

1. **服务网格架构**：控制平面 vs 数据平面职责分离
2. **Sidecar模式**：透明代理，流量拦截原理（iptables/IPVS）
3. **Istio核心CRD**：VirtualService、DestinationRule、Gateway、AuthorizationPolicy
4. **流量管理**：路由规则、负载均衡策略、超时重试、熔断
5. **安全机制**：mTLS原理、证书管理、授权策略
6. **可观测性**：指标类型、分布式追踪原理、日志收集
7. **性能影响**：Sidecar资源开销、延迟增加（通常在毫秒级）
8. **服务网格选型**：Istio（功能全）vs Linkerd（轻量级）vs Consul Connect（集成Consul）

## 最佳实践

### 1. 渐进式采用
- **先核心服务**：优先网格化核心业务服务
- **mTLS渐进**：先PERMISSIVE模式，再STRICT模式
- **监控先行**：先建立监控体系，再开启高级特性

### 2. 配置管理
- **版本控制**：所有Istio CRD配置存入Git（GitOps）
- **命名规范**：VirtualService/DestinationRule命名与Service对应
- **注释清晰**：标注路由规则用途、负责人

### 3. 性能优化
- **资源限制**：设置Sidecar CPU/内存limits
- **连接池调优**：根据服务QPS调整最大连接数
- **采样率调整**：分布式追踪采样率生产环境设为1-5%

### 4. 监控告警
- **关键指标**：4黄金信号（延迟、流量、错误、饱和度）
- **告警规则**：P99延迟超阈值、错误率超5%告警
- **可视化**：Grafana Dashboard展示服务拓扑和关键指标

### 5. 安全加固
- **最小权限**：AuthorizationPolicy默认拒绝所有，显式允许必要流量
- **证书管理**：定期轮换根证书，使用Cert Manager自动化
- **审计日志**：记录所有服务间访问决策

## 【常见错误】

### 错误1：过度使用服务网格
**表现**：所有服务都注入Sidecar，无差别启用高级特性
**后果**：资源开销大（每个Pod增加2-3% CPU、30-50MB内存），延迟增加
**正确做法**：按业务重要性分级，核心服务优先网格化

### 错误2：mTLS模式切换过快
**表现**：直接从PERMISSIVE切换到STRICT
**后果**：部分服务无法通信，业务中断
**正确做法**：先观察PERMISSIVE模式下TLS流量比例，逐步切换

### 错误3：路由规则配置错误
**表现**：VirtualService路由规则冲突、通配符匹配错误
**后果**：流量路由到错误版本，业务异常
**正确做法**：使用istioctl analyze校验配置，先在测试环境验证

### 错误4：忽视Sidecar资源限制
**表现**：未设置Sidecar资源请求和限制
**后果**：Sidecar资源耗尽，影响业务容器
**正确做法**：通过Sidecar CRD设置资源限制

### 错误5：监控体系缺失
**表现**：未配置Prometheus + Grafana，无告警
**后果**：故障无法及时发现，MTTR长
**正确做法**：先建设监控体系，再启用高级流量管理特性

## 总结

服务网格是云原生时代**服务治理的标准解法**，核心价值是**解耦业务逻辑与通信逻辑**。

**关键要点**：
1. **架构**：控制平面管理配置，数据平面处理流量
2. **功能**：流量管理、安全、可观测性三位一体
3. **透明**：对业务代码无侵入，Sidecar模式透明拦截
4. **标准**：Istio成为事实标准，CRD配置成为通用语言
5. **演进**：从Spring Cloud微服务框架到服务网格，治理逻辑下沉

**学习路径**：
1. 理解服务网格解决什么问题（微服务治理复杂性）
2. 掌握Istio核心概念（VirtualService、DestinationRule、Gateway）
3. 实践流量管理（灰度发布、熔断、超时重试）
4. 配置安全机制（mTLS、授权策略）
5. 建设可观测性（Prometheus + Grafana + Jaeger）

服务网格不是银弹，适合**大规模微服务场景**（>20个服务），小团队可能引入不必要的复杂性。
