# 分布式监控

## 定义

分布式监控是指对分布式系统中所有组件（服务器、服务、中间件、网络）进行实时监控、指标收集、告警通知的体系。它帮助运维和开发人员了解系统状态、发现问题、定位故障。

核心目标：
- **可观测性**：系统状态可见、可理解
- **实时性**：监控数据实时收集、实时展示
- **告警及时**：故障及时发现、及时通知
- **可追溯**：历史数据可查询、可分析

## 核心概念

### 1. 监控层次

**基础设施监控**
- 监控对象：服务器、虚拟机、容器
- 指标：CPU、内存、磁盘、网络、负载
- 工具：Node Exporter、Zabbix Agent

**系统服务监控**
- 监控对象：数据库、消息队列、缓存、Web服务器
- 指标：连接数、QPS、TPS、延迟、错误率
- 工具：MySQL Exporter、Redis Exporter、Kafka Exporter

**应用监控**
- 监控对象：应用程序、微服务
- 指标：QPS、延迟、错误率、JVM指标、GC
- 工具：Prometheus Client、Micrometer、SkyWalking

**业务监控**
- 监控对象：业务指标
- 指标：订单量、支付成功率、用户在线数
- 工具：自定义Exporter、日志分析

### 2. 监控指标类型

**计数器（Counter）**
- 只增不减的指标
- 典型：请求总数、错误总数、订单总数
- 特点：可计算增长率、速率

**仪表盘（Gauge）**
- 可增可减的指标
- 典型：当前内存使用量、当前在线用户数、队列长度
- 特点：反映当前状态

**直方图（Histogram）**
- 统计样本分布
- 典型：请求延迟分布（分位数）
- 特点：可计算P50、P90、P99

**摘要（Summary）**
- 类似直方图，直接计算分位数
- 典型：请求延迟P50、P90、P99
- 特点：客户端计算，服务端压力小

### 3. 监控数据收集方式

**拉模式（Pull）**
- 监控中心主动拉取目标指标
- 优点：集中控制、目标无感知
- 缺点：监控中心压力大、需服务发现
- 典型：Prometheus

**推模式（Push）**
- 目标主动推送指标到监控中心
- 优点：目标控制推送频率、监控中心压力小
- 缺点：需目标安装推送组件、可能丢数据
- 典型：Graphite、InfluxDB

**代理模式（Agent）**
- 目标安装Agent，Agent收集指标并上报
- 优点：对目标应用透明、统一收集
- 缺点：需安装Agent、Agent可能故障
- 典型：Zabbix Agent、Telegraf

### 4. 告警策略

**静态阈值告警**
- 指标超过固定阈值触发告警
- 典型：CPU使用率 > 80%
- 优点：简单、易理解
- 缺点：阈值固定，无法适应动态变化

**动态阈值告警**
- 基于历史数据，动态计算阈值
- 典型：CPU使用率超过过去7天平均值2倍
- 优点：自适应、减少误报
- 缺点：实现复杂、需历史数据

**异常检测告警**
- 基于机器学习，检测异常行为
- 典型：突然流量激增、延迟突然变高
- 优点：发现未知问题
- 缺点：实现复杂、可能有误报

## 详细内容

### 1. Prometheus

**架构**
- Prometheus Server：收集、存储指标数据
- Exporter：暴露指标端点（/metrics）
- Pushgateway：支持短生命周期任务推送指标
- Alertmanager：告警管理（去重、分组、路由）
- Web UI：查询、展示指标

**核心机制**
- 拉模式：定期从Exporter拉取指标
- 多维数据模型：指标 + 标签（Label）
- PromQL：专用查询语言
- 服务发现：支持Consul、Kubernetes、DNS等

**优点**
- 简单易用
- 多维数据模型
- 强大的查询语言（PromQL）
- 社区活跃

**缺点**
- 拉模式，大规模监控中心压力大
- 存储有限（本地TSDB），需远程存储
- 告警规则配置复杂

### 2. Grafana

**架构**
- Grafana Server：可视化平台
- Data Source：数据源（Prometheus、InfluxDB、Elasticsearch等）
- Dashboard：仪表盘，展示图表
- Alerting：告警（支持多种通知渠道）

**核心机制**
- 多数据源支持：统一展示多个监控系统数据
- 仪表盘模板：可复用、可分享
- 告警：支持阈值告警、通知到多种渠道

**优点**
- 可视化能力强
- 多数据源支持
- 仪表盘模板丰富
- 告警通知渠道多

**缺点**
- 仅可视化，不收集指标
- 需配合Prometheus等使用

### 3. Zabbix

**架构**
- Zabbix Server：收集、存储、告警
- Zabbix Agent：安装在目标机器，收集指标
- Proxy：代理，减轻Server压力
- Web UI：管理、展示

**核心机制**
- 代理模式：Agent收集指标，主动或被动上报
- 支持多种监控方式：Agent、SNMP、IPMI、JMX
- 告警：支持邮件、短信、脚本等

**优点**
- 功能全面（监控、告警、可视化）
- 支持多种监控方式
- 成熟稳定

**缺点**
- 配置复杂
- 可视化不如Grafana
- 性能不如Prometheus

### 4. SkyWalking

**架构**
- Probe：Agent收集指标、追踪数据
- OAP Server：分析、聚合、存储
- Storage：存储（Elasticsearch、MySQL）
- UI：展示监控、追踪、告警

**核心机制**
- 非侵入式Agent
- 支持链路追踪、性能指标、告警
- 国产，文档友好

**优点**
- 功能丰富（监控+追踪+告警）
- 非侵入式
- 国产，文档友好

**缺点**
- 性能不如Prometheus
- 社区不如Prometheus活跃

## 示例/应用场景

### 示例1：电商系统监控（Prometheus + Grafana）
**场景**：电商系统需监控系统性能、业务指标

**方案设计**：
1. 监控组件：
   - Prometheus：收集指标
   - Grafana：展示仪表盘
   - Alertmanager：告警
2. Exporter：
   - Node Exporter：服务器指标
   - MySQL Exporter：数据库指标
   - Redis Exporter：缓存指标
   - Spring Boot Actuator：应用指标
3. 仪表盘：
   - 基础设施仪表盘：CPU、内存、磁盘、网络
   - 应用仪表盘：QPS、延迟、错误率、JVM
   - 业务仪表盘：订单量、支付成功率
4. 告警规则：
   - CPU使用率 > 80%，持续5分钟
   - 应用错误率 > 5%，持续1分钟
   - 订单量同比下降50%

**关键考量**：
- 监控覆盖：所有关键组件都要监控
- 告警阈值：合理设置，避免误报、漏报
- 仪表盘：直观展示，一眼看出问题

### 示例2：Kubernetes集群监控（Prometheus + Grafana）
**场景**：Kubernetes集群需监控节点、Pod、容器

**方案设计**：
1. 监控组件：
   - Prometheus：收集指标
   - Grafana：展示仪表盘
2. Exporter：
   - Node Exporter：节点指标
   - Kube-State-Metrics：Kubernetes资源指标
   - cAdvisor：容器指标
3. 服务发现：Prometheus自动发现Kubernetes服务、Pod
4. 仪表盘：
   - 集群仪表盘：节点状态、Pod状态、资源使用
   - 应用仪表盘：Pod重启次数、容器资源使用

**关键考量**：
- 服务发现：Kubernetes动态环境，需自动发现
- 标签：利用Kubernetes标签，聚合指标
- 存储：Kubernetes集群监控数据量大，需远程存储

### 示例3：应用性能监控（SkyWalking）
**场景**：微服务系统需监控应用性能、调用链路

**方案设计**：
1. 监控组件：
   - SkyWalking Probe：Agent收集指标、追踪数据
   - SkyWalking OAP Server：分析、聚合
   - SkyWalking UI：展示
2. Agent：
   - Java Agent：监控Java应用
   - 其他语言Agent：监控其他语言应用
3. 仪表盘：
   - 应用性能仪表盘：响应时间、吞吐量、错误率
   - 服务地图：服务依赖关系
   - 链路追踪：调用链路详情

**关键考量**：
- 非侵入式：Agent方式，无需修改代码
- 性能影响：Agent对应用性能影响小
- 链路追踪：与监控结合，快速定位问题

## 【对应领域考点】

1. **监控层次**
   - 基础设施监控：服务器、网络
   - 系统服务监控：数据库、消息队列
   - 应用监控：应用程序、微服务
   - 业务监控：业务指标

2. **监控指标类型**
   - Counter：只增不减
   - Gauge：可增可减
   - Histogram：统计分布
   - Summary：直接计算分位数。

3. **Prometheus vs. Zabbix**
   - Prometheus：拉模式、多维数据、PromQL、云原生友好
   - Zabbix：代理模式、功能全面、传统运维友好

4. **拉模式 vs. 推模式**
   - 拉模式：监控中心主动拉取，集中控制
   - 推模式：目标主动推送，监控中心压力小

5. **告警策略**
   - 静态阈值：简单、固定
   - 动态阈值：自适应、复杂
   - 异常检测：机器学习、发现未知问题

## 最佳实践

1. **合理选择监控工具**
   - 云原生环境：Prometheus + Grafana
   - 传统环境：Zabbix
   - 需要链路追踪：SkyWalking

2. **监控覆盖全面**
   - 基础设施：服务器、网络
   - 系统服务：数据库、消息队列
   - 应用：应用程序、微服务
   - 业务：业务指标

3. **告警阈值合理**
   - 避免误报：阈值设置合理，多次检测后告警
   - 避免漏报：关键指标都要告警
   - 告警分级：紧急、重要、一般

4. **仪表盘直观**
   - 关键指标放前面
   - 使用图表（折线图、柱状图、仪表盘）
   - 支持下钻：从总览到下钻到细节

5. **监控数据存储**
   - 短期数据：本地存储（Prometheus TSDB）
   - 长期数据：远程存储（InfluxDB、Thanos）

## 【常见错误】

1. **错误：监控覆盖不全**
   - 现象：系统故障，但监控未告警
   - 原因：监控未覆盖关键组件
   - 解决：全面梳理监控项，覆盖所有关键组件。

2. **错误：告警阈值不合理**
   - 现象：频繁误报，或故障未告警
   - 原因：阈值设置不合理
   - 解决：根据历史数据，调整阈值。

3. **错误：监控数据丢失**
   - 现象：查询历史数据，数据缺失
   - 原因：存储配置不当、数据过期
   - 解决：配置合理的数据保留策略、远程存储。

4. **错误：监控中心成为瓶颈**
   - 现象：监控数据延迟、丢失
   - 原因：监控中心性能不足
   - 解决：扩容监控中心、使用联邦集群。

5. **错误：告警通知不及时**
   - 现象：故障发生很久，才收到告警
   - 原因：告警通知渠道不畅、告警规则配置不当
   - 解决：优化告警规则、使用多种通知渠道。

## 总结

分布式监控是分布式系统可观测性的核心，核心在于：
1. **监控层次**：基础设施、系统服务、应用、业务
2. **指标类型**：Counter、Gauge、Histogram、Summary
3. **收集方式**：拉模式（Prometheus）、推模式（Graphite）、代理模式（Zabbix）
4. **核心工具**：Prometheus（收集）、Grafana（展示）、Zabbix（全面）、SkyWalking（全功能）
5. **告警策略**：静态阈值、动态阈值、异常检测

实际应用中，需根据环境（云原生/传统）、需求（监控/追踪/告警）选择合适的监控工具和策略。
