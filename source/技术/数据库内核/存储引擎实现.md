# 存储引擎实现

## 定义

**存储引擎**是数据库内核中负责数据持久化存储的核心组件，管理数据在磁盘和内存中的组织、存储和访问。

**核心目标**：
- **高效存储**：优化磁盘空间利用率
- **快速访问**：减少I/O次数，提升查询性能
- **数据一致性**：保证事务ACID特性
- **崩溃恢复**：故障后恢复数据到一致状态

---

## 核心概念

### 1. 存储引擎架构对比

| 存储引擎 | 数据结构 | 写性能 | 读性能 | 适用场景 |
|----------|----------|--------|--------|----------|
| **InnoDB** | B+树 | 中等 | 高 | OLTP、事务处理 |
| **MyISAM** | B+树 | 中等 | 中等 | 读多写少 |
| **RocksDB** | LSM-Tree | 极高 | 中等 | 写多读少、大数据 |
| **WiredTiger** | B+树/LSM | 高 | 高 | 文档数据库 |

### 2. InnoDB关键组件

| 组件 | 功能 | 关键数据结构 |
|------|------|--------------|
| **缓冲池（Buffer Pool）** | 缓存数据页 | LRU列表、Flush列表 |
| **重做日志（Redo Log）** | 保证持久性 | 日志缓冲区、日志文件 |
| **撤销日志（Undo Log）** | 支持MVCC、回滚 | 回滚段、Undo页 |
| **页（Page）** | 最小I/O单位 | 页头、记录堆、页目录 |
| **索引（Index）** | 加速查询 | B+树索引、自适应哈希索引 |

### 3. RocksDB关键组件

| 组件 | 功能 | 关键数据结构 |
|------|------|--------------|
| **MemTable** | 内存中的可变数据 | 跳表（Skiplist） |
| **SSTable** | 磁盘上的不可变数据 | 分层存储（L0-L6） |
| **WAL** | 预写日志 | 日志文件 |
| **Bloom Filter** | 快速判断Key是否存在 | 布隆过滤器 |
| **Compaction** | 合并SSTable | 多种策略（Level、Size、FIFO） |

## 详细内容

### 一、InnoDB存储引擎实现

#### 1.1 缓冲池（Buffer Pool）实现

**核心数据结构**：
- **缓冲池实例**：多个实例减少锁竞争
- **LRU列表**：管理页的淘汰
- **Flush列表**：管理脏页刷新
- **Free列表**：管理空闲页

**LRU算法优化**：
- ** midpoint insertion**：新读入的页插入LRU列表的midpoint（不是表头）
- **young/old列表**：避免全表扫描污染LRU

**示例伪代码**：
```c++
// 读取页
Page* buf_page_get(page_id, ...) {
    // 1. 查找缓冲池
    Page* page = buf_pool->lookup(page_id);
    if (page != nullptr) {
        // 命中，移动到LRU young列表头部
        buf_pool->lru_move_to_head(page);
        return page;
    }
    
    // 2. 未命中，从磁盘读取
    page = buf_pool->alloc();
    read_page_from_disk(page_id, page);
    
    // 3. 插入LRU midpoint
    buf_pool->lru_add(page, LRU_MIDPOINT);
    
    return page;
}
```

#### 1.2 页结构（Page Structure）

**InnoDB页结构**（16KB）：
```
+---------------------------------------+
| Page Header (38 bytes)               |
+---------------------------------------+
| Infimum + Supremum Records (26 bytes) |
+---------------------------------------+
| User Records (变长)                   |
+---------------------------------------+
| Free Space                            |
+---------------------------------------+
| Page Directory (槽位)                 |
+---------------------------------------+
| File Trailer (8 bytes)               |
+---------------------------------------+
```

**记录格式**（Compact格式）：
- **变长字段长度列表**：记录变长字段长度
- **NULL标志位**：记录哪些字段为NULL
- **记录头信息**：next_record指针、删除标记等
- **列数据**：实际数据

#### 1.3 B+树索引实现

**B+树结构**：
- **非叶子节点**：存储键值+子页指针
- **叶子节点**：存储键值+记录数据（或主键）

**索引查找**：
```c++
// B+树查找
Record* btr_search(index_id, key) {
    // 1. 从根页开始
    page_t* page = get_root_page(index_id);
    
    while (!page->is_leaf()) {
        // 2. 在非叶子节点中查找
        page_id_t child_page_id = page->search(key);
        page = read_page(child_page_id);
    }
    
    // 3. 在叶子节点中查找
    Record* rec = page->search(key);
    return rec;
}
```

**索引插入**：
- 可能触发页分裂（Page Split）
- 可能触发树高增加

**索引删除**：
- 可能触发页合并（Page Merge）
- 可能触发树高减少

#### 1.4 日志系统（Log System）

**Redo Log结构**：
- **日志类型**：MLOG_1BYTE、MLOG_2BYTES、MLOG_4BYTES、MLOG_WRITE_STRING等
- **日志序列号（LSN）**：唯一标识日志记录

**WAL（Write-Ahead Logging）**：
- 修改数据前，必须先写Redo Log
- 保证持久性

**日志写入流程**：
```c++
// 事务提交
void trx_commit(trx_t* trx) {
    // 1. 写Redo Log
    log_write(trx->redo_log);
    
    // 2. 刷盘（根据innodb_flush_log_at_trx_commit）
    if (innodb_flush_log_at_trx_commit == 1) {
        log_flush();
    }
    
    // 3. 事务提交完成
    trx->state = TRX_STATE_COMMITTED;
}
```

#### 1.5 事务与MVCC实现

**Undo Log结构**：
- **回滚段（Rollback Segment）**：存储Undo Log
- **Undo Log类型**：INSERT_UNDO、UPDATE_UNDO

**MVCC实现**：
- **隐藏列**：DB_TRX_ID（事务ID）、DB_ROLL_PTR（回滚指针）
- **Read View**：事务开始时创建，判断记录可见性

**记录可见性判断**：
```c++
// 判断记录对当前事务是否可见
bool rec_visible(rec_t* rec, read_view_t* view) {
    trx_id_t rec_trx_id = rec->trx_id;
    
    // 1. 如果记录事务ID < view->up_limit_id，可见
    if (rec_trx_id < view->up_limit_id) {
        return true;
    }
    
    // 2. 如果记录事务ID >= view->low_limit_id，不可见
    if (rec_trx_id >= view->low_limit_id) {
        return false;
    }
    
    // 3. 如果在view->trx_ids中，不可见；否则可见
    if (view->contains(rec_trx_id)) {
        return false;
    }
    
    return true;
}
```

### 二、RocksDB存储引擎实现

#### 2.1 LSM-Tree结构

**LSM-Tree（Log-Structured Merge-Tree）**：
- **MemTable**：内存中的可变数据（跳表）
- **Immutable MemTable**：内存中不可变数据（等待刷盘）
- **SSTable（Sorted String Table）**：磁盘上的不可变数据

**分层存储**：
- **L0**：文件可能重叠
- **L1-L6**：文件有序，不重叠

#### 2.2 写入流程

**写入流程**：
1. **写WAL**：预写日志，保证持久性
2. **写MemTable**：写入内存中的跳表
3. **MemTable满**：转换为Immutable MemTable，创建新MemTable
4. **刷盘（Flush）**：Immutable MemTable写入L0 SSTable
5. **Compaction**：合并SSTable，减少层数

**代码示例**（简化）：
```cpp
// 写入操作
Status Write(const WriteOptions& options, WriteBatch* batch) {
    // 1. 写WAL
    if (options.sync) {
        log_writer_->AddRecord(batch->data_, true);
    } else {
        log_writer_->AddRecord(batch->data_, false);
    }
    
    // 2. 写MemTable
    for (auto& record : batch->records_) {
        memtable_->Add(record.key, record.value);
    }
    
    return Status::OK();
}
```

#### 2.3 读取流程

**读取流程**：
1. **读MemTable**：从内存中的跳表读取
2. **读Immutable MemTable**：从不可变MemTable读取
3. **读SSTable**：从L0到L6依次读取
4. **使用Bloom Filter**：快速判断Key是否在某层SSTable中

**代码示例**（简化）：
```cpp
// 读取操作
Status Get(const ReadOptions& options, const Slice& key, std::string* value) {
    // 1. 读MemTable
    if (memtable_->Get(key, value)) {
        return Status::OK();
    }
    
    // 2. 读Immutable MemTable
    if (imm_memtable_ != nullptr && imm_memtable_->Get(key, value)) {
        return Status::OK();
    }
    
    // 3. 读SSTable（从L0到L6）
    for (int level = 0; level < config::kNumLevels; level++) {
        // 使用Bloom Filter过滤
        if (!bloom_filter_[level]->MayContain(key)) {
            continue;
        }
        
        // 读取SSTable文件
        if (sstable_[level]->Get(key, value)) {
            return Status::OK();
        }
    }
    
    return Status::NotFound();
}
```

#### 2.4 Compaction策略

**Compaction类型**：
- **Minor Compaction**：MemTable → L0 SSTable
- **Major Compaction**：合并不同层SSTable

**Compaction策略**：
- **Level Compaction**：按层合并，保证L1+层文件不重叠
- **Size Compaction**：按大小触发合并
- **FIFO Compaction**：按时间淘汰旧数据

**Level Compaction流程**：
1. **选择待合并文件**：从L0选择文件，与L1文件合并
2. **合并排序**：多路归并排序
3. **生成新文件**：写入L1新文件
4. **删除旧文件**：删除L0和L1旧文件

## 示例/应用场景

### 示例1：InnoDB缓冲池调优

**场景**：调整InnoDB缓冲池大小，优化查询性能。

**步骤**：
1. **查看当前缓冲池大小**：
   ```sql
   SHOW VARIABLES LIKE 'innodb_buffer_pool_size';
   ```

2. **调整缓冲池大小**：
   ```sql
   SET GLOBAL innodb_buffer_pool_size = 4294967296;  -- 4GB
   ```

3. **监控缓冲池命中率**：
   ```sql
   SHOW ENGINE INNODB STATUS;
   -- 查看Buffer pool hit rate
   ```

**效果**：
- 缓冲池命中率 > 99%
- 查询性能提升显著

### 示例2：RocksDB Compaction策略选择

**场景**：根据工作负载选择RocksDB Compaction策略。

**步骤**：
1. **写多读少场景**：选择Level Compaction
   ```cpp
   Options options;
   options.compaction_style = kCompactionStyleLevel;
   options.num_levels = 7;
   ```

2. **读多写少场景**：选择FIFO Compaction
   ```cpp
   Options options;
   options.compaction_style = kCompactionStyleFIFO;
   options.compaction_options_fifo.max_table_files_size = 1024 * 1024 * 1024;  // 1GB
   ```

3. **监控Compaction**：
   ```cpp
   // 获取Compaction统计信息
   std::string stats;
   db->GetProperty("rocksdb.compaction.stats", &stats);
   ```

**效果**：
- 写多读少：Level Compaction减少写放大
- 读多写少：FIFO Compaction减少读放大

## 【常见错误】

### 1. 缓冲池配置不当

**错误示例**：
```text
缓冲池配置过小，导致缓冲命中率低，查询性能差
```

**正确做法**：
```text
- 根据可用内存配置缓冲池大小（通常为物理内存的70-80%）
- 监控缓冲池命中率（目标>99%）
- 调整缓冲池实例数（减少锁竞争）
```

### 2. Compaction策略选择不当

**错误示例**：
```text
写多读少场景使用FIFO Compaction，导致读性能差
```

**正确做法**：
```text
- 写多读少：使用Level Compaction
- 读多写少：使用FIFO Compaction
- 根据工作负载选择Compaction策略
- 监控Compaction统计信息，持续调优
```

### 3. 日志配置不当

**错误示例**：
```text
不配置Redo Log刷盘策略，导致性能差或数据丢失风险
```

**正确做法**：
```text
- 根据一致性要求配置innodb_flush_log_at_trx_commit
- 设置为1：最高一致性（每次提交刷盘）
- 设置为2：高性能（每秒刷盘）
- 设置为0：最高性能（不刷盘，风险大）
```

### 4. 忽略性能监控和优化

**错误示例**：
```text
不监控存储引擎性能，导致性能问题发现晚
```

**正确做法**：
```text
- 监控关键指标（QPS、TPS、延迟、缓冲命中率、Compaction统计）
- 分析慢查询（慢查询日志、执行计划）
- 优化存储引擎配置
- 持续监控和调优
```
