# 数据库安全实现

## 定义

**数据库安全（Database Security）**是保护数据库免受**未授权访问、数据泄露、篡改、破坏**的一系列技术、策略和流程。其核心目标是保证数据的**机密性（Confidentiality）、完整性（Integrity）、可用性（Availability）**（CIA三元组）。

类比：数据库安全就像**银行的安保系统**——门禁（访问控制）、监控（审计日志）、保险箱（数据加密）、防抢演练（入侵检测）。

数据库安全是**合规要求**（如：GDPR、等保2.0、HIPAA），也是企业生存的底线（数据泄露可能导致巨额罚款甚至破产）。

## 核心概念

### 1. 访问控制（Access Control）
访问控制是数据库安全的第一道防线，决定**谁可以访问哪些数据**。

| 访问控制模型 | 原理 | 优点 | 缺点 | 适用场景 |
|--------------|------|------|------|----------|
| **DAC（自主访问控制）** | 资源所有者决定谁可以访问 | 灵活、易用 | 权限传播难以控制 | 文件系统、小型数据库 |
| **MAC（强制访问控制）** | 系统强制实施安全策略（如：密级） | 安全性高 | 配置复杂、不灵活 | 军事、政府系统 |
| **RBAC（基于角色的访问控制）** | 将权限分配给角色，用户通过角色获得权限 | 易管理、易审计 | 角色爆炸（角色过多） | 企业数据库（最常用） |
| **ABAC（基于属性的访问控制）** | 根据属性（用户属性、资源属性、环境属性）动态决定 | 灵活、细粒度 | 策略复杂、性能开销 | 复杂企业环境、云数据库 |

### 2. 数据加密（Data Encryption）
数据加密是防止数据泄露的最后一道防线，即使数据被窃取，也无法解读。

| 加密类型 | 加密位置 | 优点 | 缺点 | 适用场景 |
|----------|----------|------|------|----------|
| **传输加密（TLS/SSL）** | 客户端与服务器之间 | 防止网络窃听 | 性能开销 | 所有数据库连接 |
| **存储加密（TDE）** | 数据文件在磁盘上加密 | 防止磁盘被盗 | 无法防止DBA偷数据 | 合规要求（GDPR、等保） |
| **列级加密** | 敏感列在应用层加密 | 防止DBA偷数据 | 应用层复杂、无法按列查询 | 密码、信用卡号 |
| **备份加密** | 备份文件加密 | 防止备份泄露 | 备份/恢复性能开销 | 所有备份 |

### 3. 审计日志（Audit Logging）
审计日志记录**谁、在什么时间、做了什么**，用于安全审计和事后追溯。

| 审计级别 | 记录内容 | 用途 |
|----------|----------|------|
| **语句级审计** | 记录所有SQL语句 | 性能分析、安全审计 |
| **对象级审计** | 记录对特定表/列的访问 | 敏感数据保护 |
| **会话级审计** | 记录连接/断开连接 | 入侵检测 |
| **管理操作审计** | 记录DDL、权限变更 | 合规要求 |

### 4. SQL注入防护（SQL Injection Protection）
SQL注入是Web应用最常见的漏洞，攻击者通过构造恶意SQL获取/篡改数据。

| 防护技术 | 原理 | 优点 | 缺点 |
|----------|------|------|------|
| **参数化查询（Prepared Statement）** | SQL和参数分离，参数不会被解释为SQL | 完全防止SQL注入 | 需要应用层支持 |
| **输入验证** | 对用户输入进行白名单验证 | 额外防护层 | 无法覆盖所有场景 |
| **最小权限原则** | 数据库账户只给必要权限 | 即使注入成功，影响也有限 | 需要精细权限设计 |
| **WAF（Web应用防火墙）** | 在Web层过滤SQL注入攻击 | 无应用改造 | 可能有漏报/误报 |

## 详细内容

### 访问控制实现细节

#### 1. RBAC（基于角色的访问控制）实现
RBAC是现代数据库最常用 的访问控制模型。

**核心组件**：
- **用户（User）**：数据库账户
- **角色（Role）**：权限的集合
- **权限（Privilege）**：对特定对象的操作权限（SELECT、INSERT、UPDATE、DELETE）

**实现步骤**：
1. **创建角色**：`CREATE ROLE read_only;`
2. **分配权限**：`GRANT SELECT ON ALL TABLES IN SCHEMA public TO read_only;`
3. **分配用户到角色**：`GRANT read_only TO user1;`

**优点**：
- 权限管理简单（改角色权限，所有用户生效）
- 易于审计（审计角色权限即可）
- 符合最小权限原则

#### 2. 细粒度访问控制（FGAC）实现
FGAC允许**行级、列级**的访问控制，比传统的表级权限更精细。

**实现技术**：
- **行级安全（Row-Level Security, RLS）**：根据用户属性过滤行（如：PostgreSQL的RLS）
- **列级权限**：只授予特定列的SELECT权限（如：`GRANT SELECT(id, name) ON users TO role1;`）
- **视图（View）**：通过视图限制用户能看到的数据（如：只暴露部分行/列）

**示例（PostgreSQL RLS）**：
```sql
-- 启用行级安全
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- 创建策略：用户只能看到自己的订单
CREATE POLICY orders_policy ON orders
  USING (user_id = current_user_id());
```

### 数据加密实现细节

#### 1. 透明数据加密（TDE）实现
TDE在**存储引擎层**加密数据文件，对应用透明。

**实现原理**：
1. **密钥层级**：
   - **主密钥（Master Key）**：由密钥管理系统（KMS）管理，加密下表空间密钥
   - **下表空间密钥（Tablespace Key）**：加密实际数据文件
2. **加密过程**：
   - 数据页写入磁盘前，用下表空间密钥加密
   - 数据页从磁盘读取时，用下表空间密钥解密
3. **密钥轮换**：
   - 定期轮换下表空间密钥（重新加密数据文件）
   - 主密钥轮换更快（只需重新加密下表空间密钥）

**优点**：
- 对应用透明（无需改造）
- 防止磁盘被盗导致数据泄露

**缺点**：
- 无法防止DBA偷数据（DBA有解密权限）
- 性能开销（通常5-10%）

#### 2. 列级加密实现
列级加密在**应用层**加密敏感数据，数据库只存储密文。

**实现步骤**：
1. **选择加密算法**：AES-256（对称加密）
2. **密钥管理**：密钥存储在密钥管理系统（KMS）或硬件安全模块（HSM）
3. **应用层加密**：
   - 写入时：应用加密数据，再存入数据库
   - 读取时：从数据库读取密文，应用解密
4. **禁止数据库解密**：数据库只存储密文，无法解密

**优点**：
- 即使数据库被攻破，也无法解密敏感数据
- 符合合规要求（GDPR、PCIDSS）

**缺点**：
- 应用层复杂（需要处理加密/解密）
- 无法对加密列进行查询（如：WHERE password = 'xxx'无法使用索引）

### 审计日志实现细节

#### 1. 审计日志的触发时机
| 触发时机 | 说明 | 性能影响 |
|----------|------|----------|
| **语句执行前** | 记录SQL语句和执行计划 | 低 |
| **语句执行后** | 记录执行结果（影响行数、错误码） | 中 |
| **事务提交后** | 记录事务的修改（Before/After值） | 高 |

#### 2. 审计日志的存储
| 存储方式 | 说明 | 优点 | 缺点 |
|----------|------|------|------|
| **文件** | 审计日志写入文件系统 | 简单、性能好 | 容易被篡改 |
| **数据库表** | 审计日志写入数据库表 | 易查询、易审计 | 性能开销、容易被篡改 |
| **远程日志服务器** | 审计日志发送到远程日志服务器（如：Syslog、ELK） | 防篡改、集中管理 | 网络开销 |

#### 3. 审计日志的内容
一条完整的审计日志记录应包含：
- **时间戳**：操作发生的时间
- **用户身份**：哪个数据库用户执行的操作
- **客户端IP**：从哪台机器连接
- **SQL语句**：执行的SQL（或操作类型）
- **影响行数**：SELECT返回多少行，UPDATE/INSERT/DELETE影响多少行
- **执行结果**：成功或失败，错误码
- **事务ID**：哪个事务执行的操作

### SQL注入防护实现细节

#### 1. 参数化查询（Prepared Statement）原理
参数化查询是**唯一能完全防止SQL注入**的技术。

**错误示例（拼接SQL）**：
```java
String sql = "SELECT * FROM users WHERE username = '" + username + "' AND password = '" + password + "'";
Statement stmt = conn.createStatement();
ResultSet rs = stmt.executeQuery(sql);
```

**攻击者输入**：
- username: `admin' --`
- password: `anything`
- 拼接后的SQL: `SELECT * FROM users WHERE username = 'admin' --' AND password = 'anything'`
- `--`是SQL注释，密码检查被绕过

**正确示例（参数化查询）**：
```java
String sql = "SELECT * FROM users WHERE username = ? AND password = ?";
PreparedStatement pstmt = conn.prepareStatement(sql);
pstmt.setString(1, username);
pstmt.setString(2, password);
ResultSet rs = pstmt.executeQuery();
```

**原理**：
- SQL和参数分离，参数不会被解释为SQL
- 数据库会将参数当作**数据**，而不是**代码**

#### 2. 输入验证原则
输入验证是**额外防护层**，但不能替代参数化查询。

**验证原则**：
- **白名单验证**：只允许特定字符/格式（如：用户名只允许字母数字）
- **长度限制**：限制输入长度（如：用户名最多20字符）
- **类型验证**：确保输入是期望的类型（如：年龄必须是整数）
- **特殊字符转义**：对特殊字符（如：`'`、`"`、`;`）进行转义

## 示例/应用场景

### 示例1：电商系统的数据库安全设计
**场景**：电商系统有用户表、订单表、支付表，需要保护用户隐私和支付安全。

**安全设计**：
1. **访问控制**：
   - 创建角色：`customer_service`（客服，只能查订单状态）、`finance`（财务，能查支付信息）、`admin`（管理员，全部权限）
   - 使用RBAC，避免直接给用户赋权
2. **数据加密**：
   - 用户密码：使用bcrypt哈希存储（不可逆）
   - 信用卡号：列级加密（应用层加密）
   - 数据文件：启用TDE，防止磁盘被盗
3. **审计日志**：
   - 记录所有对`payments`表的访问
   - 记录所有权限变更操作
   - 审计日志发送到远程日志服务器（防篡改）
4. **SQL注入防护**：
   - 所有SQL使用参数化查询
   - Web层使用WAF过滤攻击

### 示例2：医疗系统的数据库安全设计
**场景**：医疗系统有患者表、病历表，需要符合HIPAA合规要求。

**安全设计**：
1. **访问控制**：
   - 使用ABAC（基于属性的访问控制）：医生只能访问自己患者的病历
   - 使用RLS（行级安全）：`CREATE POLICY patient_policy ON medical_records USING (doctor_id = current_user_id());`
2. **数据加密**：
   - 患者姓名、病历内容：列级加密（应用层加密）
   - 数据文件：启用TDE
   - 备份文件：启用备份加密
3. **审计日志**：
   - 记录所有对`medical_records`表的访问（包括SELECT）
   - 审计日志不可删除、不可修改
   - 定期审计日志，发现异常访问
4. **SQL注入防护**：
   - 所有SQL使用参数化查询
   - 输入验证：病历ID必须是数字，患者姓名只允许中文/字母

### 示例3：金融系统的数据库安全设计
**场景**：金融系统有账户表、交易表，需要符合PCIDSS合规要求。

**安全设计**：
1. **访问控制**：
   - 使用RBAC+ABAC混合模型
   - 创建角色：`teller`（柜员，能查账户余额）、`manager`（经理，能审批大额交易）、`auditor`（审计员，只读）
   - 使用FGAC（细粒度访问控制）：柜员只能查自己支行的账户
2. **数据加密**：
   - 账户密码：使用PBKDF2哈希存储（加盐、慢哈希）
   - 交易金额：不加密（需要汇总统计），但交易备注列级加密
   - 数据传输：强制TLS 1.3加密
3. **审计日志**：
   - 记录所有对`accounts`和`transactions`表的操作
   - 记录所有登录失败事件
   - 审计日志实时发送到SIEM（安全信息与事件管理）系统
4. **SQL注入防护**：
   - 所有SQL使用参数化查询
   - 使用WAF+IDS（入侵检测系统）多层防护

## 最佳实践

### 1. 访问控制最佳实践
- **使用RBAC**：避免直接给用户赋权，通过角色管理权限
- **最小权限原则**：只给必要的权限，避免使用`GRANT ALL`
- **定期审计权限**：定期清理不必要的权限和角色
- **使用FGAC**：对敏感数据使用行级/列级访问控制

### 2. 数据加密最佳实践
- **传输加密**：所有数据库连接强制TLS加密
- **存储加密**：启用TDE，防止磁盘被盗
- **列级加密**：对密码、信用卡号等敏感数据使用列级加密
- **密钥管理**：使用KMS或HSM管理密钥，定期轮换密钥

### 3. 审计日志最佳实践
- **记录关键操作**：记录所有DDL、权限变更、敏感数据访问
- **防篡改存储**：审计日志发送到远程日志服务器或WORM（一次写入多次读取）存储
- **定期审计**：定期审查审计日志，发现异常行为
- **实时监控**：将审计日志接入SIEM系统，实时告警

### 4. SQL注入防护最佳实践
- **使用参数化查询**：这是唯一能完全防止SQL注入的技术
- **输入验证**：作为额外防护层，但不要依赖它
- **最小权限原则**：数据库账户只给必要权限，即使注入成功，影响也有限
- **使用WAF**：在Web层过滤SQL注入攻击

## 【常见错误】

### 1. 访问控制错误
- **错误1：直接给用户赋权**
  - 表现：权限管理混乱，难以审计
  - 原因：不了解RBAC的优势
  - 解决：使用RBAC，通过角色管理权限

- **错误2：权限过度授予**
  - 表现：应用使用`root`或`sa`账户连接数据库
  - 原因：方便，但风险极大
  - 解决：遵循最小权限原则，只给必要权限

### 2. 数据加密错误
- **错误1：不加密敏感数据**
  - 表现：用户密码明文存储，数据泄露后无法挽回
  - 原因：不了解加密的重要性
  - 解决：对密码使用慢哈希（bcrypt、PBKDF2），对信用卡号使用列级加密

- **错误2：密钥硬编码在代码中**
  - 表现：密钥泄露，所有加密数据可被解密
  - 原因：不了解密钥管理的重要性
  - 解决：使用KMS或HSM管理密钥

### 3. 审计日志错误
- **错误1：不启用审计日志**
  - 表现：安全事件发生后，无法追溯
  - 原因：担心性能开销
  - 解决：启用审计日志，只记录关键操作

- **错误2：审计日志本地存储**
  - 表现：数据库服务器被攻破，审计日志被篡改
  - 原因：不了解审计日志防篡改的重要性
  - 解决：审计日志发送到远程日志服务器

### 4. SQL注入防护错误
- **错误1：使用字符串拼接SQL**
  - 表现：应用存在SQL注入漏洞，被攻击者利用
  - 原因：不了解参数化查询的重要性
  - 解决：所有SQL使用参数化查询

- **错误2：依赖输入验证防SQL注入**
  - 表现：输入验证有遗漏，仍然存在SQL注入漏洞
  - 原因：不了解输入验证的局限性
  - 解决：使用参数化查询，输入验证只作为额外防护层

## 总结

数据库安全是保护数据资产的关键，涉及访问控制、数据加密、审计日志、SQL注入防护等多个方面。

**核心要点回顾**：
1. **访问控制**：使用RBAC或ABAC，遵循最小权限原则
2. **数据加密**：传输加密（TLS）、存储加密（TDE）、列级加密结合使用
3. **审计日志**：记录关键操作，防篡改存储，定期审计
4. **SQL注入防护**：使用参数化查询，这是唯一能完全防止SQL注入的技术

**未来发展趋势**：
- **零信任安全模型**：不再默认信任内网，所有访问都需要验证
- **AI驱动的安全防御**：利用机器学习检测异常访问和SQL注入攻击
- **同态加密（Homomorphic Encryption）**：允许在加密数据上直接计算，彻底解决数据泄露问题

掌握数据库安全实现，让你能够设计出安全、合规的数据库系统，保护企业和用户的数据资产。
