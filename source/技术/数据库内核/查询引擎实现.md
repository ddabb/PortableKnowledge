# 查询引擎实现

## 定义

**查询引擎**是数据库内核中负责处理SQL查询的核心组件，包括查询解析、查询优化和查询执行三个主要阶段。

**核心目标**：
- **正确解析**：将SQL文本转换为逻辑查询计划
- **优化查询**：生成最优物理查询计划
- **高效执行**：快速返回查询结果

---

## 核心概念

### 1. 查询处理流程

| 步骤 | 说明 | 输出 |
|------|------|------|
| **解析（Parsing）** | 语法分析，生成解析树 | 解析树（Parse Tree） |
| **重写（Rewriting）** | 语义分析、视图展开、规则重写 | 逻辑查询计划（Logical Plan） |
| **优化（Optimization）** | 生成最优执行计划（基于统计信息） | 物理查询计划（Physical Plan） |
| **执行（Execution）** | 按执行计划执行，返回结果 | 查询结果 |

### 2. 查询优化分类

| 优化类型 | 说明 | 示例 |
|----------|------|------|
| **基于规则优化（RBO）** | 使用预定义规则重写查询 | 谓词下推、投影下推、子查询展开 |
| **基于代价优化（CBO）** | 估计不同执行计划的代价，选择代价最小的 | 选择连接顺序、选择索引、选择连接算法 |

### 3. 查询执行模型

| 执行模型 | 说明 | 优点 | 缺点 |
|----------|------|------|------|
| **火山模型（Volcano Model）** | 拉取式（Pull-based），每个操作符实现`next()`方法 | 简单，易实现 | 函数调用开销大 |
| **向量化执行（Vectorized Execution）** | 一次处理一批数据（如1024行） | 减少函数调用开销，提升缓存局部性 | 实现复杂 |
| **编译执行（Compiled Execution）** | 将查询计划编译为机器码 | 减少解释执行开销 | 编译开销大 |

## 详细内容

### 一、查询解析（Query Parsing）

#### 1.1 词法分析（Lexical Analysis）

**目标**：将SQL文本拆分为词法单元（Token）。

**示例**：
```sql
SELECT * FROM users WHERE age > 18
```

**Token序列**：
```
SELECT, *, FROM, users, WHERE, age, >, 18
```

**实现工具**：
- **Flex**：生成词法分析器
- **手写的词法分析器**：如PostgreSQL的`scan.l`

#### 1.2 语法分析（Syntax Analysis）

**目标**：根据语法规则，将Token序列转换为解析树。

**语法规则**（简化）：
```
SelectStmt:
    SELECT target_list FROM from_clause WHERE where_clause
```

**解析树示例**（抽象语法树AST）：
```
SelectStmt
├── target_list: *
├── from_clause: users
└── where_clause: age > 18
```

**实现工具**：
- **Bison**：生成语法分析器
- **手写的语法分析器**：如PostgreSQL的`gram.y`

#### 1.3 语义分析（Semantic Analysis）

**目标**：检查解析树的语义正确性。

**检查内容**：
- 表是否存在
- 列是否存在
- 数据类型是否匹配
- 权限检查

**输出**：**查询树（Query Tree）**，包含详细的语义信息。

### 二、查询重写（Query Rewriting）

#### 2.1 视图展开（View Expension）

**示例**：
```sql
CREATE VIEW young_users AS SELECT * FROM users WHERE age <= 35;

SELECT * FROM young_users WHERE city = 'Beijing';
```

**重写后**：
```sql
SELECT * FROM users WHERE age <= 35 AND city = 'Beijing';
```

#### 2.2 谓词下推（Predicate Pushdown）

**原理**：将过滤条件尽可能下推到数据源附近，减少后续处理的数据量。

**示例**：
```sql
SELECT * FROM (SELECT * FROM users WHERE age > 18) AS t WHERE city = 'Beijing';
```

**重写后**：
```sql
SELECT * FROM users WHERE age > 18 AND city = 'Beijing';
```

#### 2.3 投影下推（Projection Pushdown）

**原理**：将投影（列选择）尽可能下推到数据源附近，减少后续处理的数据量。

**示例**：
```sql
SELECT name FROM (SELECT * FROM users WHERE age > 18) AS t;
```

**重写后**：
```sql
SELECT name FROM users WHERE age > 18;
```

#### 2.4 子查询展开（Subquery Unnesting）

**示例**：
```sql
SELECT * FROM users WHERE id IN (SELECT user_id FROM orders WHERE amount > 100);
```

**重写后**（转换为连接）：
```sql
SELECT users.* FROM users JOIN orders ON users.id = orders.user_id WHERE orders.amount > 100;
```

### 三、查询优化（Query Optimization）

#### 3.1 基于规则优化（RBO）

**原理**：使用预定义规则重写查询，规则基于启发式经验。

**常见规则**：
1. **谓词下推**（Predicate Pushdown）
2. **投影下推**（Projection Pushdown）
3. **子查询展开**（Subquery Unnesting）
4. **外连接消除**（Outer Join Elimination）
5. **冗余子表达式消除**（Common Subexpression Elimination）

**优势**：
- 简单快速
- 总是正确（规则基于数学等价变换）

**劣势**：
- 不考虑数据分布和代价
- 可能不是最优执行计划

#### 3.2 基于代价优化（CBO）

**原理**：估计不同执行计划的代价，选择代价最小的执行计划。

**代价模型**：
```
总代价 = I/O代价 + CPU代价 + 网络代价（分布式）
```

**统计信息**：
- **表统计信息**：行数、页数、列基数
- **列统计信息**：最小值、最大值、直方图、最常见值

**优化步骤**：
1. **生成搜索空间**：枚举所有可能的执行计划
2. **估计代价**：使用代价模型和统计信息估计每个执行计划的代价
3. **选择最优计划**：选择代价最小的执行计划

**挑战**：
- 搜索空间巨大（组合爆炸）
- 统计信息可能不准确
- 代价模型可能不准确

#### 3.3 连接顺序选择（Join Order Selection）

**问题**：多表连接时，连接顺序对性能影响巨大。

**动态规划算法**（适用于少量表）：
- 枚举所有连接顺序
- 使用代价模型选择最优

**贪心算法**（适用于大量表）：
- 每次选择代价最小的连接
- 可能不是全局最优

**示例**（3表连接）：
```sql
SELECT * FROM t1, t2, t3 WHERE t1.id = t2.id AND t2.id = t3.id;
```

**可能的连接顺序**：
1. (t1 ⋈ t2) ⋈ t3
2. (t1 ⋈ t3) ⋈ t2
3. (t2 ⋈ t3) ⋈ t1
...

**CBO选择代价最小的连接顺序**。

#### 3.4 索引选择（Index Selection）

**问题**：查询可能涉及多个索引，需要选择最优索引。

**考虑因素**：
- 索引选择性（Selectivity）
- 索引覆盖度（Covering Index）
- 索引访问代价

**示例**：
```sql
SELECT * FROM users WHERE age > 18 AND city = 'Beijing';
```

**可能的索引**：
- `idx_age` (age)
- `idx_city` (city)
- `idx_age_city` (age, city)

**CBO选择代价最小的索引**。

### 四、查询执行（Query Execution）

#### 4.1 火山模型（Volcano Model）

**原理**：拉取式（Pull-based），每个操作符实现`next()`方法，返回下一个元组。

**示例**（扫描+过滤）：
```python
class ScanOperator:
    def __init__(self, table):
        self.table = table
        self.cursor = 0
    
    def next(self):
        if self.cursor >= len(self.table):
            return None
        row = self.table[self.cursor]
        self.cursor += 1
        return row

class FilterOperator:
    def __init__(self, child, predicate):
        self.child = child
        self.predicate = predicate
    
    def next(self):
        while True:
            row = self.child.next()
            if row is None:
                return None
            if self.predicate(row):
                return row
```

**优势**：
- 简单，易实现
- 适合流式处理

**劣势**：
- 函数调用开销大（每个元组都要调用`next()`）
- 缓存局部性差

#### 4.2 向量化执行（Vectorized Execution）

**原理**：一次处理一批数据（如1024行），减少函数调用开销，提升缓存局部性。

**示例**（扫描+过滤）：
```python
class VectorizedScanOperator:
    def __init__(self, table):
        self.table = table
        self.cursor = 0
    
    def next_batch(self, batch_size):
        if self.cursor >= len(self.table):
            return None
        batch = self.table[self.cursor:self.cursor + batch_size]
        self.cursor += batch_size
        return batch

class VectorizedFilterOperator:
    def __init__(self, child, predicate):
        self.child = child
        self.predicate = predicate
    
    def next_batch(self, batch_size):
        while True:
            batch = self.child.next_batch(batch_size)
            if batch is None:
                return None
            filtered = [row for row in batch if self.predicate(row)]
            if filtered:
                return filtered
```

**优势**：
- 减少函数调用开销
- 提升缓存局部性
- 适合SIMD指令优化

**劣势**：
- 实现复杂
- 不适合流式处理（需要攒批）

#### 4.3 编译执行（Compiled Execution）

**原理**：将查询计划编译为机器码，减少解释执行开销。

**示例**（使用LLVM编译执行）：
```cpp
// 查询：SELECT * FROM t WHERE a > 10

// 编译后的机器码（伪代码）：
void query_execution() {
    for (int i = 0; i < t_size; i++) {
        if (t[i].a > 10) {
            emit(t[i]);
        }
    }
}
```

**优势**：
- 减少解释执行开销
- 适合复杂查询

**劣势**：
- 编译开销大
- 实现复杂

## 示例/应用场景

### 示例1：查询优化实战（PostgreSQL）

**场景**：分析一个复杂查询的执行计划。

**查询**：
```sql
EXPLAIN ANALYZE
SELECT u.name, o.order_id
FROM users u
JOIN orders o ON u.id = o.user_id
WHERE u.age > 18 AND o.amount > 100;
```

**执行计划**（简化）：
```
Nested Loop Join (cost=10.0..100.0 rows=100 width=64)
  -> Seq Scan on users u (cost=0.0..10.0 rows=100 width=32)
       Filter: age > 18
  -> Index Scan using idx_order_user_id on orders o (cost=0.0..1.0 rows=10 width=32)
       Index Cond: user_id = u.id
       Filter: amount > 100
```

**分析**：
1. **扫描users表**：使用顺序扫描（Seq Scan），过滤`age > 18`
2. **扫描orders表**：使用索引扫描（Index Scan），使用索引`idx_order_user_id`
3. **连接**：使用嵌套循环连接（Nested Loop Join）

**优化建议**：
- 在`users.age`上创建索引，加速过滤
- 在`orders.user_id`和`orders.amount`上创建复合索引，加速连接和过滤

### 示例2：向量化执行实战（ClickHouse）

**场景**：ClickHouse使用向量化执行加速查询。

**查询**：
```sql
SELECT sum(amount) FROM orders WHERE order_date > '2023-01-01';
```

**向量化执行流程**：
1. **扫描orders表**：一次读取1024行
2. **过滤**：使用SIMD指令并行过滤1024行
3. **聚合**：使用向量化聚合函数（如`sum()`）计算1024行的和
4. **返回结果**：返回聚合结果

**性能对比**：
| 执行模型 | 查询时间 |
|----------|----------|
| 火山模型 | 10s |
| 向量化执行 | 2s |

## 【常见错误】

### 1. 不理解查询执行计划

**错误示例**：
```text
不理解查询执行计划，导致无法优化慢查询
```

**正确做法**：
```text
- 掌握执行计划读取（EXPLAIN命令）
- 理解不同操作符（扫描、过滤、连接、聚合）
- 分析执行计划代价（cost、rows、width）
- 根据执行计划优化查询
```

### 2. 索引设计不当

**错误示例**：
```text
索引设计不当，导致查询性能不佳
```

**正确做法**：
```text
- 选择合适索引类型（B+树、哈希、位图等）
- 设计合适索引列（WHERE、JOIN、ORDER BY、GROUP BY列）
- 避免索引失效（函数、类型转换、前导模糊查询）
- 定期维护索引（重建、重组）
```

### 3. 查询设计不当

**错误示例**：
```text
查询设计不当，导致性能差
```

**正确做法**：
```text
- 避免SELECT *（只选择需要的列）
- 使用参数化查询（避免SQL注入、提升缓存命中率）
- 优化连接顺序（小表驱动大表）
- 避免子查询（转换为连接）
```

### 4. 忽略性能监控和优化

**错误示例**：
```text
不监控查询性能，导致性能问题发现晚
```

**正确做法**：
```text
- 监控关键指标（QPS、延迟、资源使用率）
- 分析慢查询（慢查询日志、执行计划）
- 优化查询（重写查询、调整连接顺序、选择索引）
- 定期性能调优
```

1. **系统化学习基础理论**：查询处理流程、查询解析、查询重写、查询优化、查询执行
2. **阅读经典论文和源码**：Volcano、PostgreSQL、ClickHouse
3. **深入理解关键组件**：CBO优化器、向量化执行
4. **持续监控和调优**：监控性能、分析慢查询、优化查询

随着数据量越来越大、查询越来越复杂，查询引擎技术将持续发展，包括更智能的查询优化器、更高效的查询执行模型、更强大的查询优化技术。
