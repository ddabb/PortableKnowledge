# 信贷风险控制系统设计

## 定义

**信贷风险控制系统**是指通过**数据、规则、模型**等手段，对信贷业务中的**欺诈风险、信用风险、操作风险**进行识别、评估、预警和阻断的系统。

对于金融信贷科技而言，风控系统是**核心护城河**，直接决定坏账率和盈利能力。

---

## 核心概念

### 1. 风控的主要风险类型

| 风险类型 | 说明 | 典型场景 |
|----------|------|----------|
| **欺诈风险** | 申请人有意骗贷（伪造身份、团伙作案） | 伪冒申请、中介骗贷、薅羊毛 |
| **信用风险** | 申请人还款能力不足（无意违约） | 收入虚报、多头借贷、负债过高 |
| **操作风险** | 系统或流程缺陷导致损失 | 系统漏洞、人工审核失误、流程绕过 |

### 2. 风控系统分层架构

```
┌─────────────────────────────────────────┐
│         业务层（授信/放款/还款）           │
└─────────────────────────────────────────┘
┌─────────────────────────────────────────┐
│         风控决策引擎                     │
│  - 规则引擎（Drools、Aviator）          │
│  - 模型服务（反欺诈、信用评分）           │
│  - 决策树/评分卡                        │
└─────────────────────────────────────────┘
┌─────────────────────────────────────────┐
│         特征工程层                       │
│  - 用户画像（人口属性、行为数据）         │
│  - 设备指纹（设备ID、IP、GPS）          │
│  - 社交网络（关系图谱、团伙识别）         │
│  - 外部数据（征信、运营商、电商）         │
└─────────────────────────────────────────┘
┌─────────────────────────────────────────┐
│         数据层                          │
│  - 实时计算（Flink、Spark Streaming）   │
│  - 离线计算（Hive、Spark）              │
│  - 存储（HBase、Redis、ClickHouse）     │
└─────────────────────────────────────────┘
```

### 3. 风控决策流程

**实时决策流程**（≤ 200ms）：
```
用户提交申请
  ↓
数据采集（实时 + 离线特征）
  ↓
规则引擎逐条执行
  ↓
模型评分（反欺诈分数、信用分数）
  ↓
决策结果（通过/拒绝/人工审核）
  ↓
风险提示（拒绝原因、风险标签）
```

## 详细内容

### 1. 反欺诈系统

#### （1）反欺诈核心手段

**身份核验**：
- **四要素验证**：姓名、身份证、手机号、银行卡
- **活体检测**：人脸识别（支付宝、微信人脸核身）
- **设备指纹**：设备ID、MAC地址、IMEI

**行为异常检测**：
- **设备异常**：频繁更换设备、多账号同设备
- **位置异常**：GPS定位与IP地址不一致
- **操作异常**：短时间大量申请、填写速度异常快

**团伙欺诈识别**：
- **关系图谱**：通过手机号、设备、IP、地址建立关联
- **社区发现算法**：识别欺诈团伙（Louvain、Label Propagation）
- **异常聚集检测**：同一地点大量申请

#### （2）反欺诈模型

**有监督模型**（已知黑/白样本）：
- **LR（逻辑回归）**：简单、可解释，适合评分卡
- **XGBoost / LightGBM**：非线性关系，特征自动筛选
- **深度学习**：DNN、Wide & Deep（适合大规模稀疏特征）

**无监督模型**（无标签，发现异常）：
- **孤立森林（Isolation Forest）**：检测异常行为
- **AutoEncoder**：重构误差识别异常样本
- **图神经网络（GNN）**：识别欺诈团伙

### 2. 信用评分系统

#### （1）信用评分卡

**评分卡开发流程**：
1. **数据准备**：样本定义（好/坏用户）、特征工程
2. **变量分箱**：WOE（Weight of Evidence）编码
3. **模型训练**：Logistic Regression
4. **评分转换**：将概率转换为分数（如 300-900 分）
5. **模型评估**：KS、AUC、PSI（Population Stability Index）

**评分卡公式**：
```
Score = Base Score + Sum(Weight_i * WOE_i)
```

**示例**：
```
年龄 = 25-30岁 → WOE = 0.8 → 加分 = 20
收入 = >10000元 → WOE = 1.2 → 加分 = 30
历史逾期 = 有 → WOE = -2.0 → 减分 = -50
...
总分数 = 650分 → 通过授信
```

#### （2）A卡/B卡/C卡

| 评分卡类型 | 使用阶段 | 预测目标 |
|----------|----------|----------|
| **A卡（申请评分卡）** | 授信申请时 | 未来12个月违约概率 |
| **B卡（行为评分卡）** | 放款后 | 未来违约概率（动态调整额度） |
| **C卡（催收评分卡）** | 逾期后 | 还款意愿（催收优先级） |

### 3. 规则引擎

#### （1）规则引擎作用

**规则引擎**是将业务规则（if-then）从代码中解耦，支持**动态配置、实时生效**的系统。

**核心价值**：
- **灵活性**：业务人员可自行配置规则，无需改代码
- **可追溯**：规则执行日志，方便审计和复盘
- **性能**：规则快速执行（Drools 可支持 10万+ 规则/秒）

#### （2）常见规则类型

| 规则类型 | 说明 | 示例 |
|----------|------|------|
| **硬规则** | 必须满足，否则直接拒绝 | 年龄 < 18岁 → 拒绝 |
| **软规则** | 加分/减分，影响评分 | 收入 > 10000 → +20分 |
| **名单规则** | 黑名单/白名单 | 身份证在黑名单 → 拒绝 |
| **频率规则** | 限制申请次数 | 7天内申请 > 3次 → 拒绝 |

#### （3）规则引擎选型

| 引擎 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **Drools** | 功能强大、生态成熟 | 学习曲线陡 | 复杂规则、高性能要求 |
| **Aviator** | 轻量级、高性能 | 功能相对简单 | 简单规则、快速上线 |
| **Easy Rules** | 简单易用、Java原生 | 性能一般 | 小规模规则 |
| **自建规则引擎** | 完全可控 | 开发成本高 | 定制化需求强 |

### 4. 特征工程

#### （1）特征分类

| 特征类别 | 说明 | 示例 |
|----------|------|------|
| **人口属性** | 年龄、性别、学历、职业 | 年龄 = 25岁 |
| **经济能力** | 收入、资产、负债 | 月收入 = 15000元 |
| **信用记录** | 历史逾期、贷款笔数 | 历史逾期次数 = 2 |
| **行为数据** | 申请次数、点击行为 | 7天内申请次数 = 5 |
| **设备信息** | 设备ID、IP、GPS | 设备ID = abc123 |
| **社交图谱** | 关系网络、团伙特征 | 一度联系人中有3个黑名单 |

#### （2）特征计算

**实时特征**（决策时计算，≤ 100ms）：
- 用户年龄、收入、历史逾期次数
- 设备指纹、IP地址、GPS定位

**离线特征**（T+1 或 T+N 计算）：
- 用户近30天申请次数
- 社交网络特征（图计算）
- 外部数据（征信、运营商）

**流式特征**（Flink 实时计算）：
- 用户近1小时点击次数
- 同一设备近10分钟申请次数

## 示例/应用场景

### 示例1：蚂蚁集团风控系统（蚁盾）

**架构特点**：
- **实时决策**：每笔申请 ≤ 100ms 返回结果
- **大数据画像**：整合淘宝、支付宝、芝麻信用数据
- **图计算**：关系图谱识别欺诈团伙
- **机器学习**：XGBoost、深度学习模型

**核心技术栈**：
- **流计算**：Blink（Flink）实时特征计算
- **图数据库**：GeaBase（自研图数据库）
- **规则引擎**：Drools + 自研规则引擎
- **模型服务**：PMML、TensorFlow Serving

### 示例2：小额信贷风控系统（普惠金融）

**业务特点**：
- 额度小（1000-50000元）、周期短（7-30天）
- 用户缺乏征信记录（下沉市场、蓝领、农户）
- 风控依赖**替代数据**（运营商、电商、社交）

**风控策略**：
```
准入规则：
  - 年龄 18-55岁
  - 手机号实名认证 ≥ 6个月
  - 无严重逾期记录

反欺诈规则：
  - 设备指纹异常 → 拒绝
  - 7天内申请 ≥ 3次 → 拒绝
  - GPS定位频繁变更 → 拒绝

信用评分：
  - 收入 > 5000元 → +30分
  - 电商消费活跃 → +20分
  - 无逾期记录 → +50分
  - 评分 ≥ 600 → 通过授信
```

## 【对应领域考点】

### 1. 风控系统架构设计

**考点**：如何设计一个高可用、低延迟的信贷风控系统？

**答题要点**：
1. **分层架构**：业务层、决策引擎、特征工程、数据层
2. **高性能**：规则引擎优化、特征预计算、缓存热点数据
3. **高可用**：多机房部署、熔断降级、熔断策略
4. **可扩展**：规则动态配置、模型快速迭代

### 2. 信用评分卡开发

**考点**：如何开发一个信用评分卡？

**答题模板**：
1. **样本定义**：好/坏用户定义（如：逾期 > 90天 = 坏）
2. **特征工程**：特征筛选、WOE 分箱、IV 值计算
3. **模型训练**：Logistic Regression、XGBoost
4. **模型评估**：KS、AUC、PSI（稳定性指标）
5. **上线部署**：PMML、模型服务化

### 3. 反欺诈手段

**考点**：如何识别欺诈风险？

**答题要点**：
- **身份验证**：四要素、活体检测、设备指纹
- **行为分析**：异常操作检测、频率限制
- **关系图谱**：团伙识别、社区发现算法
- **机器学习**：有监督（XGBoost）、无监督（孤立森林）

## 最佳实践

### 1. 风控系统开发原则

- **业务优先**：先理解业务逻辑，再设计系统
- **数据驱动**：所有决策都要有数据支撑
- **快速迭代**：规则/模型快速上线、快速验证
- **可解释性**：拒绝原因必须可解释（监管要求）

### 2. 模型开发规范

- **样本平衡**：坏样本过少时，使用 SMOTE 过采样或下采样
- **特征筛选**：删除 IV < 0.02 的特征（预测能力弱）
- **模型融合**：LR + XGBoost + 深度学习，投票决策
- **A/B 测试**：新模型上线前必须 A/B 测试

### 3. 系统运维

- **规则监控**：规则命中率、拒绝率异常时告警
- **模型监控**：PSI > 0.2 时模型需重新训练
- **性能监控**：决策延迟 > 200ms 时告警

## 【常见错误】

### 错误1：忽视样本不平衡

**表现**：坏样本只有 1%，模型倾向于预测"好用户"，导致欺诈漏过。

**正确做法**：
- 使用 **SMOTE** 过采样或**下采样**平衡样本
- 调整 **class_weight**（如：class_weight = {0: 1, 1: 10}）
- 使用 **Focal Loss** 损失函数

### 错误2：特征泄露

**表现**：训练时 AUC = 0.95，上线后效果很差。

**原因**：使用了"未来特征"（如：放款后才有的还款记录）。

**正确做法**：
- 严格区分**训练特征**和**上线特征**
- 训练时使用 **T-1 天及以前**的数据
- 上线时只使用**实时特征**和**离线特征（T-1）**

### 错误3：规则与模型冲突

**表现**：规则通过，但模型拒绝；或规则拒绝，但模型通过。

**正确做法**：
- **规则优先**：硬规则（如：黑名单）优先于模型
- **模型打分**：规则通过后，模型输出评分
- **决策融合**：规则和模型结果加权决策

### 错误4：监控不足

**表现**：模型效果下降 2 个月后才发现，坏账率飙升。

**正确做法**：
- **实时监控**：决策延迟、 rule hit rate
- **模型监控**：PSI、AUC、KS（每日计算）
- **业务监控**：通过率、坏账率（按日/周/月）
