# 裁剪

## 一、什么是裁剪

**裁剪（Tailoring）**：根据项目的独特性，选择和调整适用的项目管理过程、工具、技术、输入和输出，以适应项目环境的过程。

PMBOK 指南本身不是方法论，而是提供了"良好实践"的框架。"良好实践"并不意味着这些知识一成不变地应用于所有项目——每个项目都有其独特的环境、约束和干系人需求，因此裁剪是必要的。

> **核心原则**：并非每个项目都需要《PMBOK 指南》所确定的每个过程、工具、技术、输入或输出。项目经理应根据项目环境选择恰当的组合。

## 二、裁剪的六个维度

PMBOK 第7版提出裁剪项目管理的六个关键维度：

### 维度一：项目生命周期方法（Life Cycle Approach）

选择适合项目的生命周期模型：

| 生命周期类型 | 特点 | 适用场景 |
|------------|------|---------|
| 预测型（瀑布型） | 范围固定，变更严格管控 | 需求明确、风险较低 |
| 迭代型 | 范围固定，时间和成本迭代调整 | 技术探索性项目 |
| 增量型 | 时间固定，功能逐步增加 | 需要尽早交付部分价值 |
| 适应型（敏捷型） | 范围动态，固定迭代周期 | 需求不确定、变化频繁 |
| 混合型 | 预测+敏捷组合 | 部分清晰、部分变化大 |

### 维度二：开发方法（Development Approach）

选择软件的开发方式：

| 开发方法 | 特点 | 与生命周期的对应 |
|---------|------|----------------|
| 预测型开发 | 详细设计后实现 | 通常配合预测型生命周期 |
| 迭代型开发 | 循环式开发，逐步完善 | 通常配合迭代型生命周期 |
| 增量型开发 | 渐进式增加功能 | 通常配合增量型生命周期 |
| 敏捷开发 | 小步快跑，持续交付 | 通常配合适应型生命周期 |
| 混合型开发 | 预测+敏捷组合 | 通常配合混合型生命周期 |

### 维度三：规划与交付节奏（Planning and Delivery Rhythm）

确定规划和交付活动的频率与方式：

| 节奏类型 | 规划频率 | 交付频率 | 适用场景 |
|---------|---------|---------|---------|
| 阶段性规划 | 每个阶段大规划 | 阶段末交付 | 预测型项目 |
| 迭代式规划 | 每轮迭代规划 | 每轮迭代交付 | 敏捷项目 |
| 持续规划 | 实时更新 | 持续集成/交付 | DevOps实践 |

### 维度四：管理层审批（Management Approvals）

确定需要审批的节点和层级：

- 哪些里程碑需要正式审批
- 变更审批的权限层级（项目经理/CCB/发起人）
- 审批流程的复杂程度
- 文档审批的要求程度

### 维度五：治理（Governance）

建立项目治理结构，考虑：

- 需要几个阶段的关口审查
- 指导委员会的角色和参与度
- 审计和合规要求
- 报告层级和频率

### 维度六：干系人参与方式（Stakeholder Engagement）

确定干系人如何参与项目：

- 沟通频率和方式（每日站会/周报/月报）
- 评审和演示的安排
- 干系人反馈的收集方式
- 参与门槛的设定

## 三、裁剪决策流程

裁剪不是随意的增删，而是有章可循的决策过程：

```
┌─────────────────────────────┐
│ 1. 分析项目环境             │
│   · 组织文化                │
│   · 项目复杂度              │
│   · 干系人需求              │
│   · 治理要求                │
└──────────┬──────────────────┘
           ↓
┌─────────────────────────────┐
│ 2. 选择项目管理方法论        │
│   · 自研/采购/行业协会/政府  │
│   · 组织可能有强制要求       │
└──────────┬──────────────────┘
           ↓
┌─────────────────────────────┐
│ 3. 裁剪项目管理过程          │
│   · 保留哪些过程            │
│   · 合并哪些过程            │
│   · 调整过程的详细程度       │
└──────────┬──────────────────┘
           ↓
┌─────────────────────────────┐
│ 4. 确认裁剪的合理性          │
│   · 是否满足治理要求         │
│   · 是否覆盖关键风险         │
│   · 是否适合组织文化         │
└──────────┬──────────────────┘
           ↓
┌─────────────────────────────┐
│ 5. 文档化并持续审查          │
│   · 记录裁剪决策的理由        │
│   · 项目中根据变化调整       │
└─────────────────────────────┘
```

## 四、裁剪需考虑的关键因素

### 4.1 项目特征

| 因素 | 预测型倾向 | 敏捷型倾向 |
|------|-----------|-----------|
| 需求稳定性 | 稳定，明确 | 不确定，变化频繁 |
| 交付频率 | 一次或少数几次 | 频繁，持续交付 |
| 干系人参与 | 里程碑点参与 | 持续参与 |
| 风险类型 | 早期可识别 | 过程中逐步显现 |
| 团队位置 | 通常集中 | 通常分散 |

### 4.2 组织文化

- 组织的风险偏好（保守型组织倾向于更多管控）
- 对变更的容忍度
- 文档重要性的认知
- 跨部门协作传统

### 4.3 干系人需求

- 客户是内部还是外部（外部客户通常需要更正式的过程）
- 客户对信息透明度的要求
- 客户参与项目的能力和意愿

### 4.4 治理层级

- 需要几层审批
- 每个阶段的关口要求
- 审计和合规要求

## 五、预测型 vs 适应型（敏捷）裁剪对比

### 裁剪差异对比表

| 维度 | 预测型 | 适应型（敏捷） |
|------|--------|--------------|
| **生命周期** | 阶段式，早期确定范围 | 迭代式，范围逐步明确 |
| **规划粒度** | 详细计划，覆盖全项目 | 高层规划，迭代内细化 |
| **变更处理** | 变更控制流程，审批后实施 | 持续接受变更，调整代办列表 |
| **阶段关口** | 正式阶段审查 | 迭代评审（Sprint Review） |
| **文档要求** | 完整、正式文档 | 必要时文档，轻量级 |
| **质量验证** | 阶段末测试 | 每迭代结束时演示 |
| **干系人参与** | 里程碑评审 | 持续反馈（每日站会、评审会） |
| **团队结构** | 角色明确，分工清晰 | 跨职能自组织团队 |
| **进度控制** | 甘特图、关键路径 | 燃尽图、看板 |
| **风险管理** | 详细风险评估，覆盖全周期 | 迭代回顾中持续识别和应对 |

### 何时选择预测型

- 需求在项目开始时相对稳定且清晰
- 可交付成果明确定义
- 合同要求固定范围和价格
- 法规合规要求严格
- 长期项目，需要详细计划

### 何时选择适应型（敏捷）

- 需求不确定或预期会发生大量变更
- 干系人希望持续参与和反馈
- 需要尽早交付部分价值
- 快速变化的市场环境
- 创新性或探索性项目

## 六、各知识领域的裁剪示例

裁剪原则适用于所有知识领域，以下以范围管理为例（详细裁剪见《范围管理裁剪指南》）：

### 范围管理裁剪思路

**可精简的情况（小型/简单项目）：**
- 合并"规划范围管理"和"定义范围"为一个规划过程
- 范围基准可以是非正式的
- 省略详细的需求跟踪矩阵

**不可精简的内容：**
- 无论如何都必须明确项目范围（防止范围蔓延）
- 范围基准一旦建立，变更必须走变更控制流程
- 确认范围（验收可交付成果）不可省略

### 其他知识领域裁剪提示

| 知识领域 | 可精简 | 不可精简 |
|---------|--------|---------|
| 进度管理 | 小项目可合并规划过程 | 关键路径必须识别 |
| 成本管理 | 简单项目可用类比估算 | 成本基准建立必须批准 |
| 质量管理 | 小项目可减少质量审计 | 验收测试不可省略 |
| 风险管理 | 小项目可简化风险登记册 | 关键风险必须识别和应对 |
| 沟通管理 | 简单项目可口头沟通为主 | 重要决策必须书面记录 |

## 七、软考答题要点

### 考题形式一：判断裁剪是否合理

**题目关键词**："是否可以裁剪""是否可以省略""项目管理方法论选择"

**答题框架**：
```
【判断】
本项目可以/不可以裁剪该过程，理由如下：
1. 裁剪依据：项目规模（大型/小型）、复杂度（高/低）
2. 组织文化：组织对正式过程的重视程度
3. 干系人需求：客户对规范性的要求
4. 风险考量：省略该过程可能带来的风险

【结论】
建议：保留/精简/合并该过程，因为XXX
```

### 考题形式二：预测型与敏捷型裁剪选择

**答题框架**：
```
【分析项目特征】
- 需求稳定性：高/低
- 交付频率要求：高/低
- 干系人参与能力：强/弱
- 变更频率：多/少

【推荐方法】
基于以上特征，推荐采用XXX方法，理由XXX

【裁剪建议】
采用该方法后，应重点裁剪以下内容：
1. 规划粒度：从详细计划调整为高层计划+迭代细化
2. 变更流程：从正式变更控制调整为持续变更管理
3. 评审方式：从阶段关口调整为迭代评审
```

### 考题形式三：裁剪决策过程

**答题框架**：
```
【裁剪决策五步】
1. 分析项目环境（规模/复杂度/干系人/文化）
2. 选择方法论（考虑组织强制要求）
3. 裁剪过程（保留/合并/调整详细程度）
4. 确认合理性（满足治理要求、覆盖关键风险）
5. 文档化记录（记录裁剪理由，便于审查）
```
