# 案例分析 - 进度管理问题

## 一、常见问题类型

### 1.1 进度延误分析

**问题特征**：
- 项目实际进度落后于计划
- 关键路径上的活动延期
- 资源不足或资源冲突

**答题框架**：

```
【问题原因分析】
1. 计划制定不合理：
   - 任务时间估算过于乐观
   - 未考虑风险缓冲
   - 依赖关系设置错误

2. 执行过程问题：
   - 需求变更频繁
   - 资源分配不足
   - 团队经验欠缺
   - 沟通不畅导致返工

3. 外部因素：
   - 供应商延期
   - 不可抗力因素

【改进措施】
1. 重新分析关键路径
2. 采用进度压缩技术：
   - 赶工：增加资源缩短工期（成本增加）
   - 快速跟进：并行执行原计划串行活动（风险增加）
3. 优化资源分配
4. 加强变更控制
```

### 1.2 关键路径识别与优化

**识别步骤**：
1. 列出所有活动及持续时间
2. 确定活动间的依赖关系
3. 计算最早开始(ES)、最早结束(EF)
4. 计算最晚开始(LS)、最晚结束(LF)
5. 计算总浮动时间 = LS - ES
6. 浮动时间为0的路径为关键路径

**答题示例**：

```
【关键路径计算】
活动A：ES=0，EF=3 → 关键活动
活动B：ES=3，EF=7 → 关键活动
活动C：ES=3，EF=6 → 浮动时间=2
活动D：ES=7，EF=10 → 关键活动

关键路径：A→B→D，总工期=10天

【压缩方案】
压缩关键路径上耗时最长的活动D（3天→2天）
压缩后关键路径：A→B→D，总工期=9天
增加成本：5000元
```

## 二、进度压缩方法对比

| 方法 | 适用场景 | 优点 | 缺点 | 成本影响 |
|------|---------|------|------|---------|
| 赶工 | 关键路径活动可压缩 | 见效快 | 可能增加风险 | 增加成本 |
| 快速跟进 | 串行活动可并行 | 缩短工期 | 可能返工 | 可能增加成本 |
| scope reducing | 范围可调整 | 成本最低 | 影响范围 | 减少成本 |
| 资源平衡 | 资源冲突 | 优化资源配置 | 可能延长工期 | 无显著变化 |

## 三、典型案例真题

### 案例一：系统集成项目进度延误

**背景**：某系统集成项目原计划工期6个月，第4个月末检查发现：
- 进度绩效指数(SPI)=0.8
- 关键路径上的"数据库开发"延期2周
- 需求变更导致"界面设计"返工

**问题**：
1. 造成进度延误的原因有哪些？
2. 可以采取哪些措施追赶进度？
3. 如何避免类似问题再次发生？

**参考答案**：

```
【原因分析】
1. 内部原因：
   - 需求调研不充分，导致后期变更频繁
   - 估算活动持续时间时未考虑风险
   - 资源分配不合理，关键路径资源不足

2. 过程问题：
   - 缺少有效的变更控制流程
   - 沟通机制不完善，需求传递有偏差
   - 里程碑检查不及时，问题发现滞后

【追赶措施】
1. 进度压缩：
   - 对关键路径活动赶工，增加开发人员
   - 快速跟进，将部分串行活动改为并行

2. 资源优化：
   - 从非关键路径调拨资源支持关键活动
   - 申请外包部分非核心模块

3. 变更控制：
   - 冻结后续需求变更
   - 优先完成已有需求

【预防措施】
1. 改进估算方法，增加风险缓冲时间
2. 建立变更控制委员会(CCB)
3. 每周进行进度绩效监控
4. 加强需求评审，减少返工
```

## 四、答题技巧总结

### 4.1 答题结构

1. **问题定位**：先判断考查哪个知识领域
2. **原因分析**：从人、机、料、法、环五个方面分析
3. **解决方案**：提出具体可操作的措施
4. **预防建议**：给出长效机制

### 4.2 常用术语

- 关键路径法(CPM)
- 赶工(Crashing)
- 快速跟进(Fast Tracking)
- 资源平衡(Resource Leveling)
- 里程碑(Milestone)
- 浮动时间(Float/Slack)

### 4.3 计算题要点

- 掌握关键路径计算方法
- 会计算SPI、SPI、CPI、CV
- 理解进度压缩的成本-效益分析
