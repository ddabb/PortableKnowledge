# 风险分类

## 定义

**风险分类**是指依据风险来源、受影响的项目领域以及其他实用类别，对项目风险进行系统归类的方法。

项目风险可依据风险来源（如采用风险分解结构 [RBS]）、受影响的项目领域（如采用工作分解结构 [WBS]），以及其他实用类别（如项目阶段、项目预算、角色和职责）来分类，确定哪些项目领域最容易被不确定性影响；风险还可以根据共同的根本原因进行分类。

## 核心概念

### 1. 风险分类的目的

**主要目的：**
- 确定哪些项目领域最容易被不确定性影响
- 把注意力和精力集中到风险敞口最大的领域
- 针对一组相关的风险制定通用的风险应对措施
- 有利于更有效地开展风险应对

**关键价值：**
- 提高风险识别的系统性和全面性
- 提高风险分析的结构化和针对性
- 提高风险应对的效率和效果

### 2. 风险分类的维度

**按风险来源分类：**
- 使用风险分解结构（RBS）作为分类框架
- RBS按风险来源逐级分解，形成层次结构
- 常见风险来源：技术风险、管理风险、组织风险、外部风险等

**按受影响的项目领域分类：**
- 使用工作分解结构（WBS）作为分类框架
- WBS按项目可交付成果逐层分解
- 确定哪些WBS要素面临的风险最大

**按其他实用类别分类：**
- 项目阶段：启动、规划、执行、监控、收尾
- 项目预算：成本风险
- 角色和职责：谁负责应对哪些风险
- 共同的根本原因：具有相似根本原因的风险归为一类

### 3. 风险分解结构（RBS）

**RBS的定义：**
风险分解结构是对潜在风险来源的层次化描绘。

**RBS的典型结构：**
```
风险分解结构（RBS）
├── 1. 技术风险
│   ├── 1.1 需求风险
│   ├── 1.2 设计风险
│   ├── 1.3 编码风险
│   └── 1.4 测试风险
├── 2. 管理风险
│   ├── 2.1 范围风险
│   ├── 2.2 进度风险
│   ├── 2.3 成本风险
│   └── 2.4 质量风险
├── 3. 组织风险
│   ├── 3.1 资源风险
│   ├── 3.2 优先级风险
│   └── 3.3 文化风险
└── 4. 外部风险
    ├── 4.1 市场风险
    ├── 4.2 政策风险
    ├── 4.3 自然风险
    └── 4.4 法律风险
```

**使用RBS的好处：**
- 确保风险识别的系统性和全面性
- 帮助识别风险来源之间的相互关系
- 为风险应对提供结构化框架

### 4. 工作分解结构（WBS）在风险分类中的应用

**WBS风险分类法：**
- 将风险映射到WBS的各个要素
- 确定哪些WBS要素面临的风险最大
- 集中精力管理高风险WBS要素

**WBS风险分类示例：**
```
WBS
├── 1. 需求分析
│   └── 风险：需求变更频繁
├── 2. 系统设计
│   └── 风险：设计缺陷
├── 3. 编码实现
│   └── 风险：代码质量差
└── 4. 系统测试
    └── 风险：测试不充分
```

### 5. 风险分类的其他实用类别

**按项目阶段分类：**
- 启动阶段风险：项目目标不明确、可行性研究不充分
- 规划阶段风险：计划不周、资源分配不合理
- 执行阶段风险：执行偏差、资源不足
- 监控阶段风险：监控不到位、变更控制不力
- 收尾阶段风险：验收不合格、文档不完整

**按项目预算分类：**
- 成本超支风险
- 现金流量风险
- 汇率波动风险

**按角色和职责分类：**
- 项目经理风险：决策失误、领导力不足
- 项目团队风险：技能不足、人员流动
- 发起人风险：支持不足、决策延迟
- 相关方风险：期望不一致、抵制变更

**按共同的根本原因分类：**
- 将具有相似根本原因的风险归为一类
- 例如：所有由"需求不明确"引起的风险归为一类
- 有助于制定针对性的风险应对措施

## 详细内容

### 1. 风险分类的方法

**风险分解结构（RBS）法：**
- 使用RBS作为分类框架
- 将风险按照来源逐层归类
- 确保风险识别的系统性和全面性

**工作分解结构（WBS）法：**
- 使用WBS作为分类框架
- 将风险映射到WBS的各个要素
- 确定哪些WBS要素面临的风险最大

**阶段法：**
- 将风险按照项目阶段归类
- 确定哪个阶段的风险最大

**根本原因法：**
- 将风险按照共同的根本原因归类
- 有助于制定针对性的风险应对措施

### 2. 风险分类的步骤

**第一步：选择分类维度**
- 根据项目特点和风险管理需求，选择合适的分类维度
- 可以组合使用多个分类维度

**第二步：建立分类框架**
- 建立风险分解结构（RBS）或选择其他分类框架
- 确保分类框架覆盖项目风险的各个方面

**第三步：归类风险**
- 将识别出的风险归入相应的类别
- 确保每个风险都归入至少一个类别

**第四步：评估风险敞口**
- 评估每个类别的风险敞口（风险发生概率和影响程度）
- 确定哪些类别的风险敞口最大

**第五步：制定应对措施**
- 针对风险敞口最大的类别，制定通用的风险应对措施
- 提高风险应对的效率和效果

**第六步：更新分类**
- 随着项目进展，风险会发生变化
- 定期更新风险分类，确保其持续有效

### 3. 风险分类的注意事项

**注意事项1：分类维度要合适**
- 选择的分类维度要适合项目特点
- 不要使用过于复杂或不相关的分类维度

**注意事项2：分类要全面**
- 确保识别出的风险都归入相应的类别
- 不要遗漏任何风险

**注意事项3：分类要清晰**
- 各类别之间要有清晰的界限
- 不要出现风险归类模糊的情况

**注意事项4：定期更新**
- 随着项目进展，风险会发生变化
- 定期更新风险分类，确保其持续有效

### 4. 风险分类在风险管理计划中的规定

**风险管理计划中应规定：**
- 可用于项目的风险分类方法
- 风险分解结构（RBS）或分类框架
- 风险分类的责任人
- 风险分类的更新频率

**风险分类方法的选择：**
- 根据项目规模、复杂度、风险特征选择合适的方法
- 可以组合使用多种分类方法

## 示例/应用场景

### 示例1：IT项目的风险分类

**项目背景：**
某软件开发项目，需要识别和管理项目风险。

**风险分类过程：**

**第一步：选择分类维度**
- 选择RBS和WBS作为分类维度

**第二步：建立分类框架**
- 建立RBS：技术风险、管理风险、组织风险、外部风险
- 使用WBS：需求分析、系统设计、编码实现、系统测试

**第三步：归类风险**
- 需求变更频繁 → RBS：技术风险；WBS：需求分析
- 设计缺陷 → RBS：技术风险；WBS：系统设计
- 代码质量差 → RBS：技术风险；WBS：编码实现
- 测试不充分 → RBS：技术风险；WBS：系统测试
- 进度延误 → RBS：管理风险；WBS：所有阶段
- 成本超支 → RBS：管理风险；WBS：所有阶段

**第四步：评估风险敞口**
- 技术风险敞口最大，尤其是需求分析和系统设计阶段

**第五步：制定应对措施**
- 针对技术风险，制定通用应对措施：加强需求评审、设计评审、代码评审、测试评审

**第六步：更新分类**
- 每月更新一次风险分类，确保其与项目进展保持一致

### 示例2：建设项目的风险分类

**项目背景：**
某地铁建设项目，需要识别和管理项目风险。

**风险分类过程：**

**第一步：选择分类维度**
- 选择RBS和项目阶段作为分类维度

**第二步：建立分类框架**
- 建立RBS：技术风险、管理风险、组织风险、外部风险
- 使用项目阶段：启动、规划、执行、监控、收尾

**第三步：归类风险**
- 地质条件复杂 → RBS：技术风险；阶段：执行
- 施工进度延误 → RBS：管理风险；阶段：执行
- 成本超支 → RBS：管理风险；阶段：执行
- 安全事故 → RBS：外部风险；阶段：执行
- 政府审批延误 → RBS：外部风险；阶段：规划

**第四步：评估风险敞口**
- 执行阶段的风险敞口最大，尤其是技术风险和管理风险

**第五步：制定应对措施**
- 针对执行阶段的技术风险，制定通用应对措施：加强地质勘探、优化施工技术、强化安全管理

**第六步：更新分类**
- 每周更新一次风险分类，确保其与项目进展保持一致

   - 可以组合使用多个分类维度

2. **建立清晰的分類框架**
   - 确保分类框架覆盖项目风险的各个方面

   - 随着项目进展，风险会发生变化
   - 定期更新风险分类，确保其持续有效

   - 风险分类不是目的，而是手段

## 常见错误

1. **分类维度不合适**
   - 错误表现：选择的分类维度不适合项目特点
   - 后果：分类结果不实用，无法指导风险应对
   - 正确做法：根据项目特点和风险管理需求，选择合适的分类维度

2. **分类不全面**
   - 错误表现：识别出的风险没有全部归入相应的类别
   - 后果：遗漏风险，风险管理不全面
   - 正确做法：确保识别出的风险都归入相应的类别

3. **分类不清晰**
   - 错误表现：各类别之间没有清晰的界限，风险归类模糊
   - 后果：风险分类混乱，无法指导风险应对
   - 正确做法：确保各类别之间要有清晰的界限

4. **不更新分类**
   - 错误表现：风险分类后不再更新
   - 后果：风险分类与项目进展脱节，无法指导风险应对
   - 正确做法：定期更新风险分类，确保其持续有效

5. **分类后不用于风险应对**
   - 错误表现：风险分类后，没有用于制定风险应对措施
   - 后果：风险分类流于形式，没有实际价值
   - 正确做法：将分类结果用于制定有针对性的风险应对措施

## 总结

风险分类是项目管理中风险管理的重要工具，是指依据风险来源、受影响的项目领域以及其他实用类别，对项目风险进行系统归类的方法。

风险分类的主要目的是确定哪些项目领域最容易被不确定性影响，把注意力和精力集中到风险敞口最大的领域，或针对一组相关的风险制定通用的风险应对措施。

风险分类的维度包括：按风险来源分类（如采用风险分解结构 [RBS]）、按受影响的项目领域分类（如采用工作分解结构 [WBS]）、以及其他实用类别（如项目阶段、项目预算、角色和职责）。

在软考中，风险分类是项目风险管理知识领域的考点，可能涉及选择题、案例分析题。考生应理解风险分类的定义、目的、维度、步骤、注意事项等内容，能够根据项目场景进行风险分类。

对于项目经理来说，掌握风险分类是必备的技能。它有助于提高风险识别的系统性和全面性，提高风险分析的结构化和针对性，提高风险应对的效率和效果。
