# 用户旅程编排系统设计

## 定义

用户旅程编排系统（Customer Journey Orchestration, CJO）是营销自动化平台的核心模块，用于**设计、执行和优化**用户在整个生命周期中与企业的互动流程。

**核心目标**：
- **自动化**：减少人工操作，自动执行复杂营销流程
- **个性化**：根据用户信息、行为、偏好，实时调整旅程路径
- **多渠道协同**：整合Email、短信、Push、社交等渠道，提供一致体验
- **数据驱动优化**：通过A/B测试、效果分析，持续优化旅程设计

---

## 核心概念

### 1. 用户旅程（Customer Journey）

**定义**：用户从首次接触到最终转化的全过程，包括多个**触点和互动**。

**典型阶段**：
1. **认知阶段**（Awareness）：用户首次知道品牌（广告、搜索、社交）
2. **考虑阶段**（Consideration）：用户研究产品/服务（浏览、对比、咨询）
3. **转化阶段**（Conversion）：用户完成购买/注册
4. **留存阶段**（Retention）：用户持续使用产品/服务
5. **倡导阶段**（Advocacy）：用户推荐给他人（口碑传播）

**旅程设计要素**：
- **触发条件**（Trigger）：什么事件触发旅程？（注册、加购、生日）
- **分支条件**（Branch）：根据用户属性/行为，走不同分支（已购/未购）
- **动作**（Action）：发送邮件、短信、Push、更新标签
- **等待**（Wait）：延迟执行（3天后、每周一）
- **目标**（Goal）：旅程的最终目标（购买、激活、留存）

### 2. 旅程编排系统的核心能力

**可视化设计器**：
- 拖拽式组件（Trigger、Branch、Action、Wait、Goal）
- 实时预览与验证
- 版本管理与回滚

**规则引擎**：
- 条件判断（IF-THEN-ELSE）
- 复杂逻辑（AND、OR、NOT）
- 动态属性（用户标签、行为事件）

**调度与执行**：
- 定时任务（Cron表达式）
- 事件触发（实时响应）
- 批量执行（百万级用户）

**可观测性**：
- 实时效果监控（各节点转化率）
- 漏斗分析
- 异常告警

### 3. 旅程编排 vs 传统工作流

| 维度 | 传统工作流 (Workflow) | 旅程编排 (Journey Orchestration) |
|------|------------------------|-----------------------------------|
| **焦点** | 流程执行 | 用户体验 |
| **分支逻辑** | 固定规则 | 动态个性化 |
| **渠道** | 单一渠道 | 多渠道协同 |
| **优化** | 手动调整 | AI驱动优化 |
| **实时性** | 批量处理 | 实时响应 |

#### 2. 触发器匹配引擎 (Trigger Matching Engine)

**功能**：
- 实时监听用户事件
- 匹配旅程触发器条件
- 创建旅程实例（Journey Instance）

**技术选型**：
- **事件接入**：Kafka（高吞吐）
- **实时计算**：Flink（低延迟）
- **匹配规则存储**：Redis（高速查询）

**匹配流程**：
```
用户事件 → Kafka → Flink实时计算 → 触发器匹配 → 创建旅程实例
```

**触发器类型**：
- **事件触发**：用户注册、加购、购买
- **时间触发**：生日、节假日、固定日期
- **属性触发**：标签变更、积分变更
- **组合触发**：多个条件同时满足

#### 3. 分支条件评估引擎 (Branch Evaluation Engine)

**功能**：
- 评估分支条件（IF-THEN-ELSE）
- 支持复杂逻辑（AND、OR、NOT）
- 动态获取用户属性/行为

**技术选型**：
- **规则引擎**：Drools / Easy Rules / 自研
- **属性存储**：Redis（实时属性）+ HBase（历史属性）

**条件表达式示例**：
```
# 简单条件
user.total_purchase > 10000

# 复杂条件
user.total_purchase > 10000 AND user.last_login_days <= 7

# 行为条件
user.behavior.opened_email IN last 3 days

# 组合条件
(user.tag == "VIP" OR user.total_purchase > 10000) AND user.last_login_days <= 7
```

**评估流程**：
```
分支节点 → 获取用户属性 → 评估条件表达式 → 选择分支路径 → 执行下一节点
```

#### 4. 状态机引擎 (State Machine Engine)

**功能**：
- 管理旅程实例的状态流转
- 持久化状态（防止丢失）
- 支持暂停、恢复、跳过

**技术选型**：
- **状态存储**：Redis（热数据）+ MySQL（冷数据）
- **状态机框架**：Spring State Machine / 自研

**状态定义**：
```java
public enum JourneyState {
    PENDING,      // 待执行
    RUNNING,      // 执行中
    WAITING,      // 等待中（Wait节点）
    COMPLETED,    // 已完成（达到Goal）
    FAILED,       // 执行失败
    PAUSED        // 已暂停
}
```

**状态流转**：
```
PENDING → RUNNING → WAITING → RUNNING → COMPLETED
             ↓
          FAILED
          
RUNNING → PAUSED → RUNNING
```

**状态持久化**：
```sql
CREATE TABLE journey_instances (
    instance_id VARCHAR(64) PRIMARY KEY,
    journey_id VARCHAR(64),
    user_id BIGINT,
    current_state VARCHAR(20),
    current_node_id VARCHAR(64),
    context_json JSON,  -- 上下文（用户属性、变量）
    created_at TIMESTAMP,
    updated_at TIMESTAMP
);
```

#### 5. 动作执行器 (Action Executor)

**功能**：
- 执行各类动作（发送邮件、短信、Push、更新标签）
- 调用渠道适配器（Channel Adapter）
- 处理重试与失败

**技术选型**：
- **任务队列**：Kafka / RabbitMQ
- **执行器**：线程池 / 分布式任务调度（XXL-Job）

**动作类型**：
- **通信动作**：发送Email、短信、Push、微信、钉钉
- **数据动作**：更新标签、更新用户属性、添加积分
- **流程动作**：跳转、暂停、恢复、终止
- **Webhook动作**：调用第三方API

**动作执行流程**：
```
动作节点 → 获取动作配置 → 调用渠道适配器 → 发送成功？ → 更新状态 → 执行下一节点
                      ↓
                   失败 → 重试（指数退避）→ 仍失败 → 记录错误 → 告警
```

#### 6. 调度器 (Scheduler)

**功能**：
- 定时任务调度（Cron表达式）
- 延迟任务调度（Wait节点）
- 批量任务调度（百万级用户）

**技术选型**：
- **调度框架**：Quartz / XXL-Job / Temporal
- **延迟队列**：Redis Sorted Set / Kafka延迟主题

**调度类型**：
- **定时调度**：每天9:00发送日报
- **延迟调度**：3天后发送提醒邮件
- **周期调度**：每周一发送周报
- **事件驱动**：实时响应（无延迟）

**延迟调度实现（Redis Sorted Set）**：
```python
import redis
import time

r = redis.Redis()

# 添加延迟任务（3天后执行）
task_id = "send_reminder_email_123"
execute_at = time.time() + 3 * 24 * 3600  # 3天后
r.zadd("delayed_tasks", {task_id: execute_at})

# 轮询执行（每秒检查一次）
while True:
    now = time.time()
    tasks = r.zrangebyscore("delayed_tasks", 0, now)
    for task_id in tasks:
        execute_task(task_id)
        r.zrem("delayed_tasks", task_id)
    time.sleep(1)
```

### 三、高级功能

#### 1. 实时个性化 (Real-time Personalization)

**功能**：
- 根据用户信息（姓名、性别、城市）个性化内容
- 根据实时行为（浏览、加购）调整推荐
- 动态调整旅程路径

**实现方案**：
- **内容模板**：使用变量占位符（`{{user.name}}`）
- **实时特征**：Flink实时计算用户行为特征
- **动态分支**：规则引擎实时评估，选择最优路径

**示例**：
```
邮件模板：

  THEN 发送产品推荐邮件
  ELSE 发送通用促销邮件
```

#### 2. 多渠道协同 (Multi-channel Coordination)

**功能**：
- 避免多渠道冲突（同时发送邮件和短信，用户觉得被打扰）
- 渠道优先级（邮件 → 短信 → Push）
- 渠道疲劳度控制（每天最多2条消息）

**实现方案**：
- **全局频控**：每个用户每天最多N条消息
- **渠道频控**：每个渠道每天最多M条消息
- **渠道选择策略**：根据消息紧急程度、用户偏好选择渠道

**频控实现（Redis）**：
```python
import redis
import time

r = redis.Redis()

def can_send(user_id, channel):
    today = time.strftime("%Y-%m-%d")
    
    # 全局频控：每天最多2条
    global_key = f"freq:{user_id}:{today}"
    if r.incr(global_key) > 2:
        return False
    
    # 渠道频控：每个渠道每天最多1条
    channel_key = f"freq:{user_id}:{channel}:{today}"
    if r.incr(channel_key) > 1:
        return False
    
    return True
```

#### 3. AI驱动优化 (AI-driven Optimization)

**功能**：
- 自动优化旅程设计（哪个分支转化率更高？）
- 自动选择最佳发送时间（用户什么时候打开率最高？）
- 自动选择最佳渠道（邮件 vs 短信 vs Push）
- 预测用户行为（哪些用户可能流失？）

**实现方案**：
- **A/B测试**：对比不同旅程设计的效果
- **多臂老虎机**（Multi-Armed Bandit）：动态分配流量到最优分支
- **强化学习**（Reinforcement Learning）：持续优化旅程策略
- **预测模型**：预测用户转化概率、流失概率

**多臂老虎机示例**：
```python
import numpy as np

class MultiArmedBandit:
    def __init__(self, n_arms):
        self.n_arms = n_arms
        self.counts = np.zeros(n_arms)  # 每个分支的展示次数
        self.values = np.zeros(n_arms)  # 每个分支的平均转化率
    
    def select_arm(self):
        # UCB1算法：选择上置信界最高的分支
        total_counts = np.sum(self.counts)
        ucb_values = self.values + np.sqrt(2 * np.log(total_counts) / (self.counts + 1e-5))
        return np.argmax(ucb_values)
    
    def update(self, arm, reward):
        # 更新分支的转化率
        self.counts[arm] += 1
        n = self.counts[arm]
        value = self.values[arm]
        self.values[arm] = ((n - 1) / n) * value + (1 / n) * reward

# 使用
bandit = MultiArmedBandit(n_arms=3)  # 3个分支
for i in range(1000):
    arm = bandit.select_arm()
    reward = execute_branch(arm)  # 执行分支，返回是否转化（0/1）
    bandit.update(arm, reward)
```

## 示例/应用场景

### 场景1：新用户欢迎系列

**业务流程**：
1. 用户注册（触发旅程）
2. 立即发送欢迎邮件（包含优惠券）
3. 3天后，如果用户未打开邮件，发送提醒短信
4. 7天后，如果用户未购买，推送App通知（含专属优惠）
5. 30天后，如果用户仍未购买，加入"流失预警"分群

**技术实现**：
- 使用**可视化设计器**设计欢迎系列旅程
- 使用**触发器匹配引擎**监听`USER_REGISTER`事件
- 使用**分支条件评估引擎**判断用户是否打开邮件
- 使用**动作执行器**发送邮件、短信、Push
- 使用**调度器**实现延迟发送（3天、7天、30天）

### 场景2：购物车弃单召回

**业务流程**：
1. 用户加购但未下单
2. 1小时后，发送提醒邮件
3. 24小时后，如果仍未下单，发送优惠短信
4. 72小时后，如果仍未下单，推送App通知（含专属优惠）
5. 如果用户下单，立即终止旅程

**技术实现**：
- 使用**触发器匹配引擎**监听`CART_ABANDONED`事件
- 使用**调度器**实现延迟发送（1小时、24小时、72小时）
- 使用**状态机引擎**监听`USER_PURCHASE`事件，如果发生则终止旅程
- 使用**多渠道协同**避免同时发送多个渠道消息

### 场景3：用户生日营销

**业务流程**：
1. 用户生日当天，发送生日祝福邮件（含专属优惠）
2. 3天后，如果用户未使用优惠，发送提醒短信
3. 7天后，如果用户仍未使用优惠，推送App通知

**技术实现**：
- 使用**调度器**定时扫描生日用户（每天凌晨执行）
- 使用**动作执行器**发送生日祝福邮件
- 使用**分支条件评估引擎**判断用户是否使用优惠
- 使用**可视化设计器**设计生日营销旅程

## 最佳实践

### 1. 旅程设计最佳实践

**保持简单**：
- 避免过度复杂的分支逻辑（不超过3层嵌套）
- 每个旅程聚焦一个目标（不要试图做所有事情）

**模块化设计**：
- 将常用逻辑封装为**子旅程**（Sub-journey）
- 复用已有旅程组件

**测试先行**：
- 上线前使用**模拟用户**测试旅程逻辑
- A/B测试验证旅程效果

### 2. 性能优化最佳实践

**异步化**：
- 非核心逻辑异步化（记录日志、更新标签）
- 使用消息队列解耦

**缓存策略**：
- 热点旅程定义缓存（Redis）
- 用户属性缓存（Redis）

**批量处理**：
- 批量发送消息（邮件、短信）
- 批量更新用户标签

### 3. 可观测性最佳实践

**关键指标监控**：
- **旅程级别**：触发次数、完成次数、转化率
- **节点级别**：每个节点的进入次数、退出次数、停留时间
- **渠道级别**：发送成功、打开、点击、转化

**日志规范**：
- 结构化日志（JSON格式）
- 关键字段：journey_id、instance_id、user_id、node_id、timestamp

**链路追踪**：
- 使用OpenTelemetry / Jaeger
- 每个旅程实例分配唯一trace_id

### 4. 用户体验最佳实践

**尊重用户偏好**：
- 允许用户设置接收频率（每天最多N条）
- 允许用户退订（Unsubscribe）

**避免过度打扰**：
- 设置**全局频控**（每天最多2条）
- 设置**渠道频控**（每个渠道每天最多1条）

**个性化内容**：
- 使用用户姓名、城市等个性化内容
- 根据用户行为实时调整推荐

## 【常见错误】

### 错误1：旅程逻辑死循环

**现象**：
旅程实例卡住，无法结束。

**原因**：
- 分支逻辑设计错误（A→B→C→A）
- 缺少终止条件

**解决方案**：
- 使用**可视化设计器**的循环检测功能
- 设置**最大步数限制**（如最多100步）
- 设置**超时终止**（如30天未完成则自动终止）

### 错误2：消息发送过度

**现象**：
用户投诉"消息轰炸"。

**原因**：
- 缺少**频控机制**
- 多个旅程同时触发，发送多条消息

**解决方案**：
- 实现**全局频控** + **渠道频控**
- 旅程设计时，检查是否与其他旅程冲突
- 提供**用户偏好设置**，允许用户控制接收频率

### 错误3：状态机状态丢失

**现象**：
旅程实例重启后，状态丢失，从头开始执行。

**原因**：
- 状态未持久化
- 或持久化失败

**解决方案**：
- **必须持久化状态**（Redis + MySQL）
- 使用**事务**保证状态更新的原子性
- 使用**幂等性设计**，即使状态丢失也不影响最终结果

### 错误4：分支条件评估错误

**现象**：
用户明明打开了邮件，但分支条件评估为"未打开"。

**原因**：
- 分支条件写错（`user.opened_email == true` vs `user.opened_email == "true"`）
- 或用户属性未实时更新

**解决方案**：
- 使用**规则引擎**的可视化编辑器，避免手写条件
- 确保用户属性**实时更新**（Flink实时计算）
- 上线前**充分测试**分支逻辑

### 错误5：调度器任务堆积

**现象**：
延迟任务未及时执行，用户投诉"优惠已过期"。

**原因**：
- 调度器性能不足（单线程）
- 或任务过多（百万级）

**解决方案**：
- 使用**分布式调度器**（XXL-Job、Temporal）
- **分片执行**（每个节点处理部分任务）
- 使用**延迟队列**（Redis Sorted Set、Kafka延迟主题）

## 总结

用户旅程编排系统是营销自动化平台的核心，涉及**可视化设计、规则引擎、状态机、调度、多渠道管理**等多个方面。

**设计关键**：
- 采用**事件驱动架构**，实时响应用户信息
- 使用**状态机**管理旅程实例的生命周期
- 引入**AI优化**，持续提升旅程效果
- 建设**可观测性体系**，保障系统稳定性

**技术选型建议**：
- **可视化设计器**：React + React Flow
- **规则引擎**：Drools / Easy Rules
- **状态机**：Spring State Machine / 自研
- **调度器**：Quartz / XXL-Job / Temporal
- **实时计算**：Flink

**未来演进方向**：
- **低代码/无代码**：让业务人员自主设计旅程
- **AI Native**：将LLM融入旅程设计（自动生成旅程、自动优化）
- **跨渠道协同**：整合线上（Email、短信）与线下（门店、电话）渠道
- **实时化**：从"批量处理"向"实时决策"演进
