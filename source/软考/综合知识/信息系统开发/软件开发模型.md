# 软件开发模型

## 瀑布模型

**特点**：阶段顺序推进，每个阶段完成后才进入下一阶段，有严格的文档输出。

**阶段**：需求分析 → 系统设计 → 编码实现 → 测试 → 运行维护

**优点**：
- 文档完整，便于理解和维护
- 适合需求明确、技术稳定的项目

**缺点**：
- 需求变更成本极高
- 交付物晚，风险后置
- 不适合需求不明确的项目

**适用**：需求明确且稳定、技术成熟的大型项目

## 增量模型

**特点**：将系统功能按模块拆分，每个增量模块独立开发、测试、交付。

**与瀑布的区别**：瀑布是全量开发后一次性交付，增量是分模块逐步交付。

**过程**：第一个增量（核心功能）→ 运行 → 第二个增量 → 运行 → …… → 最终系统

**优点**：
- 降低需求变更风险（早期即可交付核心功能）
- 客户可以尽早使用并反馈
- 便于分阶段投资

**缺点**：
- 需要系统设计时考虑模块独立性
- 增量模块的接口可能成为瓶颈

**适用**：需求可拆分、项目周期长、希望尽早交付的项目

## 迭代模型

**特点**：对同一功能进行反复设计与实现，通过多轮迭代逐步完善。

**与增量的区别**：
- **增量**：横向扩展功能模块
- **迭代**：纵向深化同一功能的实现质量

**过程**：迭代1（需求→设计→实现→测试）→ 迭代2（优化扩展）→ 迭代3（完善）→ …

**优点**：
- 早期即可验证技术可行性
- 便于在迭代中积累经验、调整方向

**缺点**：
- 迭代次数难以预估
- 可能导致范围蔓延

**适用**：技术不确定、需要探索和学习的项目

## 喷泉模型

**特点**：以用户需求为驱动，面向对象的生命周期模型。各开发活动（分析、设计、编码、测试）可以迭代进行，像喷泉一样循环往复。

**核心特征**：
- 强调**复用**和**对象**概念
- 各阶段没有严格界限，可以重叠和迭代
- 适用于面向对象的软件开发过程

**与瀑布模型的区别**：瀑布是线性顺序，各阶段严格分界；喷泉是非线性迭代，各阶段可重叠。

**适用**：面向对象开发项目

## 原型模型

**特点**：先快速开发一个原型系统，通过用户反馈逐步完善需求，再正式开发。

**两种原型**：
- **抛弃型原型**：原型只用于明确需求，不作为最终产品（**最常见**）
- **演化型原型**：原型直接演化为最终产品

**优点**：解决需求不明确的问题，用户参与度高  
**缺点**：容易产生"原型即产品"的误解，需严格管理

## 螺旋模型

**特点**：将开发过程分为多个螺旋周期，每个周期包含：制定计划→风险分析→实施开发→用户评估。

**核心**：**风险驱动**，每个迭代都要进行风险评估

**优点**：适合大型复杂高风险项目，早期发现风险  
**缺点**：需要风险评估专业知识，成本高，周期长

## V模型

**特点**：瀑布模型的扩展，强调测试与开发阶段的对应关系。

```
需求分析    ←→  验收测试
系统设计    ←→  系统测试
概要设计    ←→  集成测试
详细设计    ←→  单元测试
            编码
```

**优点**：测试计划早介入，质量有保障  
**缺点**：仍不适合需求变更，迭代性差

## RUP（统一软件开发过程）

**特点**：用例驱动、以架构为中心、迭代增量的软件工程过程。由Rational软件公司提出，分四个阶段：

| 阶段 | 英文 | 核心任务 | 里程碑 |
|------|------|---------|--------|
| **初始阶段** | Inception | 确认项目范围、愿景、风险 | 生命周期目标（LCD） |
| **细化阶段** | Elaboration | 分析需求、确定架构、降低风险 | 生命周期架构（LCA） |
| **构建阶段** | Construction | 编码、测试、集成 | 初始运行能力（IOC） |
| **交付阶段** | Transition | 部署、培训、支持 | 产品发布（PR） |

**三维生命周期**（横跨四个阶段）：
- 核心过程工程流：业务建模→需求→分析设计→实施→测试→部署
- 支持流：项目管理、配置管理、环境支持
- 迭代：每个阶段内部可多次迭代

**优点**：风险可控，架构清晰，适合大型面向对象项目  
**缺点**：流程重，文档多，不适合小型项目

## RAD（快速应用开发）

**特点**：在极短周期内（60-90天）完成系统开发，强调快速迭代。

**阶段**：
1. 业务建模 → 明确业务流程
2. 数据建模 → 整理数据需求
3. 过程建模 → 将数据流转换为处理流程
4. 应用生成 → 快速生成应用组件
5. 测试与交付 → 快速测试，交付使用

**适用**：需求明确、业务相对稳定的中型系统

**限制**：不适用于技术风险高、需要新技术的项目

## 敏捷开发

**核心价值观**（敏捷宣言）：
- 个体和互动 > 过程和工具
- 可工作的软件 > 详尽的文档
- 客户合作 > 合同谈判
- 响应变化 > 遵循计划

### Scrum框架

- **Sprint**：迭代周期，通常1-4周
- **Product Backlog**：产品待办清单（产品负责人维护）
- **Sprint Backlog**：本次迭代的任务清单
- **每日站会**：15分钟，三个问题：昨天做了什么/今天做什么/有什么障碍

**三个角色**：
- **产品负责人（PO）**：代表客户，管理Product Backlog
- **Scrum Master**：服务型领导，清除障碍
- **开发团队**：自组织，3-9人

### 极限编程（XP）

敏捷的一种实践方式，核心实践：
- **结对编程**：两人一组，一人写代码，一人review
- **持续集成**：代码频繁集成，自动测试
- **测试驱动开发（TDD）**：先写测试，再写实现代码
- **简单设计**：只做当前需求最简单的实现
- **重构**：持续优化代码结构
- **计划游戏**：快速估算故事点

**与Scrum的区别**：Scrum管"做什么"，XP管"怎么做"

## 模型选择原则

| 场景 | 推荐模型 |
|------|---------||
| 需求明确稳定 | 瀑布模型 |
| 需求可拆分、希望分阶段交付 | 增量模型 |
| 技术不确定、需要探索 | 迭代模型 |
| 面向对象开发 | 喷泉模型 |
| 需求不明确 | 原型模型 |
| 高风险大型项目 | 螺旋模型 |
| 强调测试质量 | V模型 |
| 大型面向对象项目 | RUP |
| 短周期快速交付 | RAD |
| 需求频繁变化 | 敏捷/Scrum |
| 追求代码质量与协作 | XP极限编程 |

## 各模型核心特征速记

| 模型 | 核心关键词 |
|------|-----------|
| 瀑布模型 | 线性、顺序、文档驱动 |
| 增量模型 | 分模块逐步交付 |
| 迭代模型 | 纵向深化、反复完善 |
| 喷泉模型 | 面向对象、迭代重叠 |
| 原型模型 | 快速原型、用户反馈 |
| 螺旋模型 | 风险驱动、每轮风险评估 |
| V模型 | 测试与开发对应 |
| RUP | 四阶段、用例驱动、以架构为中心 |
| RAD | 快速（60-90天）、分阶段建模 |
| Scrum | Sprint、Product Backlog、三个角色 |
| XP | 结对编程、TDD、持续集成 |
